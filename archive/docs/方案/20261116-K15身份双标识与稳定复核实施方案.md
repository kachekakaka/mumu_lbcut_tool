## 1. 背景、目标与主要取舍

当前比较函数只要存在一对可比较且匹配的标识、其余可比较项没有冲突，就返回 `VERIFIED`。隔离复现已证明缺少预期 UID 或 room_id 时可沿此规则继续定位。当前需求要求双项匹配，早期方案则以同类可靠标识匹配为准，两者应在实施时统一。

实机调查确认：两个目标的真实开播查询、稳定后的 Fragment，以及一次成功的资料页取证均取得了双标识；但首次进房可暂缺 UID，切房可短暂出现新 room_id 与旧 UID 的组合。后续样本约两三秒恢复一致，不代表所有客户端或网络均在该时限内稳定。此次没有证明单个字段在过渡期与实际播放画面同步，也没有观察到真实开播查询长期缺标识。

目标是默认只在本场 room_id 和主播 UID 均经可靠、连续取证匹配时确认身份，同时容忍有限时间的页面参数就绪过程，减少不必要的重新导航。明确错房仍需纠偏，超时未确认不得伪装成已核验。

主要取舍：

- 默认双标识：增加一次或数次取证开销，换取主播与场次两个维度的交叉检查；不声称两字段是完全独立的证据。
- 初始不一致先等待：避免把过渡状态立即当成稳定错房；持续冲突有明确上限，不能无限等待。
- 不自动降级为单标识 `VERIFIED`：本次没有足够实机依据支持该模式；不新增多套可选核验策略。
- 只保留现有显式未确认放行能力，不扩展为忽略错房的开关；其目标缺失和证据缺失边界见第 5 节。

## 2. 范围与非目标

本次拟实施：

1. 单次比较的完整性与冲突分类。
2. 首次导航、开录准备重定位及已有运行期重定位共用的稳定复核流程。
3. 调度查询、启动复核与独立 Worker 的预期标识完整性处理。
4. 原因、事件、必要的控制台解释和对应自动化、实机验收。
5. 实施完成后同步需求、设计、运行说明与验证记录。

不包括：

- 新增运行期周期强身份复核；这是 [K17](../../../docs/待办.md#已知缺陷与未验证事项)。不因本次完成就宣称同一 Activity 内切房必能及时发现。
- 改造采集、切片、音画质量、冻结检测或登录风险策略。
- 增加 Worker 外网解析、自动登录、清理抖音数据或重装模拟器。
- 迁移旧数据库、批量修改历史任务的身份结果、清理已有录像或调查材料。
- 保证零帧错录、覆盖全部客户端版本、正式发布或分发。

## 3. 单次比较与最终裁决

### 3.1 证据前提

预期 room_id 必须来自本次独立直播查询，预期 UID 必须为目标主播的同类稳定 UID；不得用 web_rid、昵称或导航 Intent 参数冒充当前页面证据。

当前证据仍仅来自已校验的当前直播 Fragment 或新建资料页 Intent。取证器负责当前页面归属、字段内部一致性、资料页新鲜性及来源校验；比较函数负责字段完整性与同语义比较。不能仅凭调用方填写一个 source 字符串就认定证据可靠。

继续拒绝来源房间 `FROM_ROOM_ID`、历史资料页、不同任务的资料页和互相冲突的 Fragment 副本。两次观察不能拼接字段：不能用第一次的 room_id 加第二次的 UID 组成一份完整证据。

### 3.2 单次观察的规则

| 情况 | 单次结果 | 稳定复核的后续处理 |
| --- | --- | --- |
| 预期及当前两项齐全、合法且全部匹配 | 匹配候选 | 积累连续匹配，不立即最终确认 |
| 可靠证据中任一可比较标识与目标不同 | 冲突候选 | 在过渡等待后复读确认，不立即重导航 |
| 只有一项匹配，另一项缺失或不可比较 | 未确认 | 重读或回退取证，不能升级为匹配候选 |
| 无证据、来源不可靠、证据内部歧义或冲突 | 未确认 | 不把不可靠字段当作已确认错房 |

实现可以沿用 `IdentityStatus` 表示单次比较结果，不必新增对外状态枚举；必须明确单次 `VERIFIED` / `MISMATCH` 只作内部候选，最终状态由定位流程确认。默认等待期间对外仍为 `UNCONFIRMED`。

标识按数字字符串处理，不转浮点或跨语义比较；缺失、空字符串、非数字或零值不能作为可靠匹配依据。预期参数非法与远端暂缺数据分别处理，不把配置错误伪装为页面读取失败。

## 4. 稳定复核流程与预算

### 4.1 初始参数

以下是待实施验证的起始值，不是本次调查已经证明的普适时限；先作为模块内部常量，不增加设置页面或 CLI 参数。

| 参数 | 初始值 | 含义 |
| --- | --- | --- |
| 两次观察间隔 | 至少 1 秒 | 上次观察结束至下次开始，使用单调时钟；不是每秒强制发起慢资料页取证 |
| 确认匹配 | 连续 2 次完整匹配 | 两次为独立新观察，指向同一目标双标识 |
| 冲突宽限期 | 进入本轮身份阶段后 5 秒 | 宽限内不因单次或短暂混合值立即定案；匹配无需额外等满 5 秒 |
| 确认冲突 | 宽限结束后连续 2 次相同冲突证据 | 可比较的字段值及缺失情况均一致，且至少一项不匹配；不足两次不直接定为稳定错房 |
| 单轮身份阶段上限 | 60 秒 | 包含所有重读、快速路径、资料页回退及其清理，且不得超过现有 preparation_deadline |

观察失败、页面变化、字段变化或非匹配样本均打断连续匹配计数；冲突计数同样要求连续且一致。预算不足以完成第二次观察时，严格模式必须返回未确认，不能以“第一遍对了”代替稳定确认。

### 4.2 步骤

1. 每次实际导航使上一次身份结果、证据和稳定计数全部失效。记录导航代次及本轮身份截止时间。
2. 在当前直播页读取新证据，进行单次分类。快速路径有效时优先只读 Fragment；缺失或内部冲突才回退资料页。
3. 完整匹配连续达到两次，且中间未出现新的导航或非预期地离开目标直播页，最终确认 `VERIFIED`。取证器自己打开、关闭资料页属于受控取证步骤，须确认返回同一直播任务，不因该步骤本身让连续确认永远无法完成。
4. 宽限结束后稳定冲突达到条件，确认 `MISMATCH`，通过已有有限次数的 reset/重新进入流程纠偏；不新增并行导航。
5. 到期仍无稳定结论，保持 `UNCONFIRMED`；严格模式按已有总预算和最多三次导航处理，最终失败时不启动正式采集。
6. 核验通过后仍执行现有画面就绪与开录准备门禁。等待画面时若明确离开直播页、导航代次变化或启动门禁触发重定位，必须作废已有身份确认。
7. 停止请求、设备离线和登录阻断沿现有路径退出；所有读取、等待和清理均受截止时间与取消信号约束。

取证调用不得每次重新获得完整 60 秒。`navigator.observe_live_room` 内部的快速重试、资料页点击、ADB 超时和返回动作，都必须受本轮剩余时间限制；预算不足以开始一次有清理保证的操作时提前返回未确认。尚无匹配候选时，将扣除观察间隔后的剩余预算至多一半分给本次完整取证，另一半留给第二次独立取证；已有一次匹配后可使用剩余预算完成第二次。每次分配均包含自己的清理，不另外追加清理时长。该分配法须以两次资料页取证的实测耗时验证；若不适用，调整预算设计并重新验收，不能以放弃第二次确认来规避问题。

### 4.3 稳定性与取证新鲜性

两次相同值不自动证明新鲜：两次必须实际重新读取，不能重复返回同一缓存对象。Fragment 不要求 room_id 或 activity_token 每次变化；同一场正常复读本来就可能相同。资料页重复取证必须满足新页面证据条件，禁止复用上次 Intent。

完整资料页观察后可由一次新的 Fragment 双项匹配完成第二次确认；若快速路径不可用，第二次仍须取得新的可靠资料页证据。新证据若与前次冲突，清空连续匹配计数。

现有 `_profile_entry_clicked_generation` 在同一导航代次内抑制重复点击；它不能继续同时代表“资料卡还在加载”和“已完成一次取证”。必须在 `navigator.py` 明确以下生命周期：

- 已点击入口、尚未确认资料卡：保留待处理标记，后续观察先检查加载结果，不连点、不盲目 Back。
- 成功取证或明确关闭本轮资料页／资料卡，并确认返回同一直播任务：清除本轮入口点击标记，允许下一次观察重新打开资料卡；不清除稳定复核已取得的匹配候选。
- 返回失败、页面归属不明或取消：不宣称本轮完整取证成功，通知定位流程使匹配候选失效；已有未解决冲突记录继续有效，本轮已经取得的可靠冲突也必须交给定位流程记录，不能随清理失败一并丢弃。取消仍按正常停止收尾，不因记录冲突继续观察或录制。
- 重新导航：重置旧页面的点击与候选状态，但不解除未解决错房的放行阻断。

资料页观察结果与清理返回结果分别传递给定位流程：匹配证据只有在清理成功并确认返回同一直播任务后，才能计入稳定复核；不能先返回成功对象、再把清理失败静默吞掉。已经通过来源、新鲜度及任务归属校验的可靠冲突，无论后续返回是否成功，都必须进入未解决冲突记录；清理失败不撤销此前成立的身份观察事实，来源或归属本就不可靠的内容则不得冒充可靠冲突。单次新冲突仍按下述冲突候选规则处理，不直接升级为稳定错房。验收必须包含快速路径持续不可用时，在同一导航代次内完成“新资料页取证—返回—再次新资料页取证—返回”的完整成功链。

已确认的错房在本次定位调用内形成阻断记录：之后仅证据消失、再次导航或开启显式放行都不能清除该记录；必须重新取得稳定的目标双项匹配才能解除。若最终仍无证据，保留未解决错房原因并阻断，不进入未确认放行。

首次冲突虽然尚未稳定确认，也不得被后续证据缺失直接转成显式放行。本方案选择保守边界：出现可靠冲突候选后，需稳定双项匹配解除疑点，或按失败处理；没有额外引入“忽略一次冲突”的模式。

### 4.4 Controller 状态和恢复终态

进入 `_locate_target_room()` 时，在第一次导航事件、等待回调或心跳之前，将 Controller 当前身份置为 `UNCONFIRMED`，同步 emitter 上下文，并清空当前有效证据来源与时间；定位函数内每次重新导航也必须保持这一失效语义。只在稳定复核的最终结果返回后发布新的已确认／错房状态。历史已封口切片保持其当时状态，不追溯改写。

运行期恢复仍先按原流程结束旧采集段，再进入重定位；不得把旧段的有效身份和本轮待复核状态混为一谈。核验中的心跳必须展示未确认，不能继续沿用上次 `verified`；经确认错房后的纠偏观察仍不得显示已核验，事件同时保留未解决冲突原因。

首次定位、开录准备阶段重定位、运行期恢复重定位三条入口统一调用失败原因映射：身份缺证据、未稳定、未解决冲突或确认错房均以身份失败退出码 18 结束；登录阻断为 15，设备离线为 20，用户正常停止按既有成功收尾语义处理。采集管线自身故障仍归原有类别，不全部改成身份失败。

实施时必须补齐 `ContinuousSession.recover()` 的专用退出码赋值，不能只设置 `_fatal_error` 后落到通用录制失败。新增身份原因必须进入 `_landing_exit_code()` 的明确映射；检查 `worker_failed`、`worker_stopped`、最终返回码和调度任务终态一致。

## 5. 目标缺失与显式放行

### 5.1 调度路径

调度器管理的是本场录制意图，创建或启动新任务必须有新鲜且完整的预期双标识。即使目标开启 `allow_unconfirmed_identity`，也不使用不完整的身份信息创建新录制任务；该开关只允许接受 Worker 当前页面无法完整确认的风险。已知新场可以被记录用于停止旧任务，与是否准许启动新任务分开判断。

#### 开播事实与启动准入分别处理

不再将 LIVE 缺标识统一改成 UNKNOWN。查询可信地报告在播，就保留在播事实；另以本次观测是否同时具备合法 room_id 和 UID 决定能否创建录制意图、派发和启动，缺项原因记为 `target_identity_incomplete`。

| 最新被接受的观测 | 场次与活动任务处理 | 新任务准入 |
| --- | --- | --- |
| LIVE、双标识完整 | 按当前场次处理；发现换场时按既有规则结束旧任务 | 可进入现有控制意图、实例和启动复核检查 |
| LIVE、新 room_id 已知、缺 UID | 记录新场次，按 `live_session_changed` 停止旧场任务；新场 UID 保持缺失 | 阻断，等待同一次新鲜观测取齐两项 |
| LIVE、room_id 与原场相同、缺 UID | 在播事实保留；不因缺 UID 单独停掉已运行任务 | 阻断，不复用历史 UID 启动 |
| LIVE、缺 room_id | 保留在播事实，不捏造新场；仅凭 UID 不能确认换场，不因此单独停止现有任务 | 阻断，不用 web_rid 或历史 room_id 替代 |
| ENDED 或 UNKNOWN | 保留现有下播确认或未知处理规则 | 不因历史双标识齐全而放行 |

用现有 `targets.room_id`、`anchor_uid` 保存最近一次已接受 LIVE 观测的同源字段：缺项写为空，不逐字段沿用旧值；历史任务的场次记录保持不变。当前观测缺 room_id 时可以保留原 `session_key` 供关联与控制，但它仅代表最近已知场次，不作为当前身份已齐的证据。重新取得 room_id 后，应与最近已知场次键比较换场，不能因为上一条观测的 room_id 为空而漏判新场。首次在播但缺 room_id 时不生成基于 web_rid 的场次键。

扫描、手动开录、启动复核和登录优先查询使用一致的字段规则，沿用观测序号与控制修订的接纳检查；在事务内完成观测更新和场次处理。`_reconcile_targets` 创建任务、`_dispatch` 占用实例／按需开机及 `_launch` 启动前均核对新鲜度和双项完整性，防止只限制最终 Popen 却仍为缺项目标开模拟器。`_launch` 必须使用当次复核结果，不拼接历史字段。

登录优先查询报告 LIVE 但标识缺项时仍表示主播在播，同时记录身份未齐原因；不改写为“开播状态未知”或“已下播”。其场次变化仍走上述规则，Worker 的实际身份准入不因在播结论而跳过。

#### 缺项或证据过期后的恢复触发

- 手动查询缺项时返回明确错误，不创建新录制意图。对于已经存在的、因身份缺项或证据过期而停在 pending 且尚无 Worker 的任务，后续手动开录必须重新查询；这也包括创建时双标识完整、因等待空闲实例等原因排队到证据过期的任务，不能仅根据先前记录的缺项原因决定是否刷新。查询取得新鲜完整双标识且仍为同一场时复用该任务，不制造重复任务；发现换场则按既有规则结束旧任务，不把旧任务重新绑定到新场。已运行任务的普通幂等返回保持原义。
- `scheduler.py` 的 `_commands` 与 `_manual_result` 两处 `existing_record` 提前返回都必须覆盖上述刷新例外：命令入口确实发出必要查询，结果入口在观测序号、控制修订和任务状态检查通过后接纳查询结果并重新判断准入，不能仅因同场已有任务就丢弃刷新结果。查询期间若任务已启动、用户已停止／停用或已有更新观测，按现有并发控制规则处理，不重复启动或复活旧意图。
- 启动复核缺项且未换场时，调用 `defer_start` 释放实例占用、保留 pending，并记录缺项原因。已换场则先结束旧任务，不能把旧任务重新绑定到新场。
- 自动扫描开启时，依靠下一轮正常扫描补齐或刷新身份；扫描取得新鲜完整身份、控制意图仍有效且 `retry_at` 已到后，重新派发并做启动复核。缺项或证据过期期间不反复占用实例、不以固定 5 秒循环发起查询。
- 自动扫描关闭时，不承诺后台自动补齐或刷新；由用户后续再次手动开录触发查询，按上述手动规则恢复。页面／命令反馈须区分身份缺项与证据过期，并说明等待重新查询，避免呈现为正在自动重试；无需新增持久化重试队列。
- 现有 `defer_start` 设置的 5 秒只是最早可派发时间，不是定时器，也不保证 5 秒后一定发出查询。正常扫描周期决定通常恢复延迟，本次不顺带改写全局退避。
- 目标停用、停止本场、下播或新场替换，仍优先于恢复。迟到的完整查询不得覆盖更新的缺项观测或撤销用户控制意图。

这会牺牲标识缺失时的新任务可用性，但保留已有可靠的在播和换场事实。实施须覆盖 `Store._observe` 原有 room_id 回退、场次比较、各派发入口及操作反馈；仅在 `_launch` 加一次判断不足以满足本节。

### 5.2 独立 Worker

Worker 仍不做外网解析。严格模式下，要求可明确解释的内部 room_id 以及显式传入的 `--expected-anchor-uid`；`auto` 已能识别的内部场次 ID 可以保留，网页入口不能冒充场次 ID。

独立 Worker 缺少严格模式所需预期项时，在启动模拟器和创建录制任务产物前以参数错误退出，指出缺失字段与正确调用方式；CLI 之外直接构造 Worker 配置的路径也必须执行同等验证。无需新增参数或兼容旧错误行为。

显式 `--allow-unconfirmed-identity` 可保留预期项不足或页面证据不足时的独立调试入口，但有以下限制：

- 始终按所有已有同类标识比较，不能忽略已知冲突。
- 先完成有界复核；没有可靠冲突，最终仍无法完整核验时，才允许 `UNCONFIRMED` 进入后续画面门禁。
- 任一可靠冲突候选尚未由稳定双项匹配解除时，禁止例外放行。
- 未确认放行的原因、心跳及切片身份状态必须为未确认，不得因某一项匹配变为 `verified`。

以上是对现行例外文字的具体化，实施前需作为本方案的一部分确认，实施时同步修改需求，不能只改代码扩大例外。

## 8. 验收标准

### 8.1 自动化

| 场景 | 必须满足的结果 |
| --- | --- |
| 四种缺失：预期 room_id、预期 UID、当前 room_id、当前 UID | 默认均不得仅凭另一项升级为最终 `VERIFIED` |
| 双项稳定匹配、昵称变化 | 连续两次匹配后放行，昵称不参与身份判定 |
| 缺 UID→完整匹配；新 room_id＋旧 UID→目标匹配 | 宽限内等待并最终通过，不因第一帧混合值立即纠偏 |
| 宽限后连续相同可靠冲突 | 进入错房纠偏，绝不经例外开关直接放行 |
| 稳定错房→重导航→证据缺失；单次可靠冲突→证据缺失 | 不得因证据消失、状态重置或例外开关绕过阻断 |
| 错房→纠偏→连续完整匹配 | 可重新通过，不能把错房记录变成永久不可恢复状态 |
| 匹配→缺失→匹配；匹配→冲突→匹配 | 连续计数正确重置，一次新匹配不足以通过 |
| 两个局部证据拼接、重复缓存、过期资料页、来源 URI、冲突 Fragment | 不产生稳定确认；保留来源与任务归属约束 |
| 快速路径持续不可用、同一导航内两次资料页取证 | 首次完成后允许重新打开入口；两份新证据及两次清理均成功，按双项连续匹配通过 |
| 资料卡加载中、已关闭、返回失败及第二次预算不足 | 分别保持防连点、允许新取证、使候选失效或未确认退出；不超共享预算 |
| 资料页读到可靠冲突→返回失败→后续缺证据，且开启显式放行 | 本轮新冲突必须保留并阻断放行；返回失败不能使冲突消失，只有后续稳定双项匹配才能解除疑点 |
| 缺证据但显式放行，且从未存在未解决可靠冲突 | 有界复核后允许未确认，事件／心跳／切片不误标 verified |
| 稳定等待中取消、设备离线、登录提示、慢 ADB／资料页操作 | 有界退出并清理；不超总预算，不启动正式录制 |
| 调度 LIVE 缺项及其后补齐 | 缺项不启动、不污染场次与历史身份；释放占用，后续新鲜完整复核才启动 |
| 活动 A 场→LIVE 的 B room_id／缺 UID | 保留 LIVE 与换场事实，停止 A 任务，不用 A 的 UID 启动 B；B 补齐后按新场意图处理 |
| LIVE 同场缺 UID；缺 room_id→恢复同场／新场 | 不因缺字段单独中止现有任务；新任务仍阻断，补齐后正确区分同场与换场 |
| 自动扫描开启／关闭时的缺项 pending 恢复 | 开启时等新扫描；关闭时再次手动请求确实查询并复用同场任务；不存在 5 秒高频占槽循环 |
| 自动扫描关闭，完整查询→等待空闲实例→证据过期→再次手动开录 | 过期时不占用实例或启动；命令与结果入口均不吞掉必要刷新，新鲜完整且同场时复用原任务并恢复派发；换场则结束旧任务，不重复创建或重绑旧任务 |
| 登录优先查询返回 LIVE 缺标识 | 上报仍在播及身份未齐，不误报 UNKNOWN／下播，场次处理及录制门禁不被跳过 |
| 迟到复核、停止本场、新场替换、手动重复命令 | 保留现有序号、幂等和控制意图语义，旧结果不能重新开录 |
| 初始定位、开录准备重定位、运行期重定位 | 一致使用最终稳定结果，失败时不继续登记正式切片 |
| 已 verified 的任务进入重新核验 | 第一个新导航事件／心跳即为 unconfirmed，旧证据时间失效；新结果完成后再更新，历史切片不改写 |
| 三条定位入口的身份失败、登录阻断、设备离线和取消 | 返回码、失败／停止事件、调度终态一致；身份为 18、登录为 15、设备为 20，取消按正常收尾 |

测试入口沿用 [tests/README.md](../../../tests/README.md)。优先运行 room_locator、worker_target_navigation、navigation_budget、room_resolver 及相关调度控制／集成测试；涉及前端原因映射时再运行对应前端测试和类型检查。只按受影响范围扩展，不把测试通过替代实机结果。

### 8.2 实机

实机前重新确认允许使用的空闲实例、共享锁、目标在播与完整预期身份；游客状态，独立仓外日志及产物目录，不复用或覆盖已有数据。

1. 冷启动进入目标：保存首次缺项、后续稳定匹配和最终裁决的时序，确认连续两次要求真实执行。
2. 同一实例 A→B→A 至少两轮：保存新旧字段混合和最终目标字段；暂态不触发过早 reset，稳定后可通过。若本轮未重现混合值，明确标为未复现，自动化时序覆盖不冒充新实机证据。
3. 单独触发资料页回退：通过仓外探针的进程内测试开关持续隔离快速路径，在同一导航代次完成两次新鲜资料页取证及返回，确认最终稳定通过并记录总耗时；另验加载中防连点和返回失败，不把这种注入描述成自然故障。
4. 保持错误房间并以另一目标核验：在隔离探针中观察、不给出伪造正确证据，验证宽限后阻断；真实导航纠偏另测，不把探针阻断等同于产品纠偏成功。
5. 获准使用实例和目标后，至少一轮真实 Worker 短录：确认稳定身份事件先于正式采集准入，目标正确、切片与任务正常收尾；检查画面而不只看日志。若此步骤尚未授权或条件不足，本专项保持待验证。
6. 记录各阶段耗时、观察次数和额外导航次数，确认相比旧流程的延迟来自必要复读，没有反复打开资料页或重新导航造成明显退化。阈值调整须有样本依据并复验。

实际发生目标查询缺项、稳定错房及登录提示不一定能自然复现；未发生时分别标为未复现，自动化只证明注入条件下的逻辑。调查阶段没有录制的历史结果不能代替本方案短录验收。

## 9. 风险、待确认项与完成条件

- 1 秒、5 秒和 60 秒为初始设计值；慢设备、客户端变化及资料页成本可能要求调整，不能按两次实机样本宣称普适。
- 连续两次相同证据仍可能有延迟或陈旧风险；当前任务归属与来源校验必须保留。本方案不提供画面逐帧身份保证。
- 调度阶段完整性要求比旧实现严格；必须在实施时同步调用示例和失败提示，不保留隐式单项放行兼容层。
- 第 5 节将调度的“本场信息完整”和 Worker 的“当前页面允许未确认”分开，是本方案提出的明确边界；实施前须确认这一具体语义。
- 开播事实与身份齐全分别判断，会涉及现有场次存储和派发入口；应使用现有字段表达最近 LIVE 同源标识及最近已知场次，不能靠全局改成 UNKNOWN 掩盖建模问题。缺 room_id 时无法证明换场的限制需如实展示。
- 关闭自动扫描时采用手动重新查询恢复，必须打通缺项及证据过期 pending 在命令和结果入口的幂等例外并准确提示；不承诺无扫描条件下自动恢复。
- 对尚未解决的可靠冲突，即使只观察到一次，本方案也不允许随后证据缺失触发例外放行；这是可用性与误录风险之间的保守选择。
- 更改核验规则不自动解决同一 Activity 内运行期切房未被触发复核的问题，K17 不随本方案关闭。

完成条件：约定代码和文档一致、自动化覆盖通过、必要实机验收通过、未复现场景和覆盖限制明确记录；满足后才更新 K15。若用户另行确认转交余项，按文档生命周期注明归档类型和后续去向，不把未验项标为通过。
