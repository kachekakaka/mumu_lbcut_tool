## 阶段一　先让任务和切片结算正确

### 1.1　旧 Worker 的 PID 尚未入库时，等它退出再交还实例

`_launch` 先提交任务的房间和事件日志路径，再调用 `Popen`，最后由 `mark_launched` 写入 PID、进程创建时间和命令行。主控在后两步之间退出，库里会同时出现“PID 为空”和“实例已分给该任务”。定向复核中，重启对账已把任务标为 `waiting_old_worker_exit`，同一轮的 `_dispatch` 又按“启动前取消”结算，旧 Worker 仍存活，实例已变为 `idle`。[启动、对账、派发和关闭](../../../src/orchestrator/scheduler.py) · [进程启动参数](../../../src/orchestrator/worker_process.py)

| 时点 | 怎么改 | 实例何时能再用 |
| --- | --- | --- |
| 新主控启动 | 从库中恢复 `starting`、`running`、`stopping`、`needs_reconcile` 任务及其 `vmindex`、启动意图、日志路径和实例归属。有已存 PID 时核对进程创建时间和命令行。PID 为空或已被复用时，按完整的 `-m src.worker.cli`、`--job-id`、实例号和本任务的 `--event-log` 参数查找进程。对确有可能属于本任务却无权核验的进程，返回“归属不明”。 | 保留原 `instances.job_id`。PID 为空、内存句柄消失或日志文件已存在，都不能单独证明进程退出。 |
| 找到旧 Worker | 持久记录 `stopping / waiting_old_worker_exit` 及首次等待期限。新主控每 2 秒复查一次，最长自动等 120 秒。等待采用调度轮询，其他实例继续工作。旧 Worker 在输出管道断开后将最近事件补写到原 NDJSON，平滑封尾片，写停止事件并退出。新主控不向旧进程发停录信号或强杀。 | 标为 `busy`，仍绑原任务。`_dispatch` 的取消及启动复核分支、迟到的复核回调、实例刷新和 `Scheduler.close` 都须尊重这个占用。 |
| 归属不明，或到期仍存活 | 只登记 `needs_reconcile` 和具体原因（归属不明或等待超时），实例设为 `reconcile`。后续手动对账或主控再次启动先核验进程。相同观察不刷新首次等待期限。 | 继续保留原任务和日志。单凭超时不能封账、强杀或放行下一任务。 |
| 确认进程已退出，日志写方已结束 | 核对旧 Worker 及已知占用本实例的自有录制子进程均已退出，进入 1.2 合并库内事件与日志。即使已看见 `worker_stopped`，也须读完、判完整并提交。日志暂时打不开则保留占用等待重读。若文件确定缺失，从库内已有证据判定能否结账，并记录缺失原因。 | 全部可确认事件入库后，在同一事务内写入最终任务结果、执行一次目标更新并核对 `instances.job_id = 旧任务 ID` 后解绑。正常可用实例变 `idle`，设备失联退出码 20 的实例变 `offline`。事务提交后才允许派发。 |

**区分真正的启动前取消。** 仅在任务尚无已提交的启动意图、无本主控启动句柄，且待执行的启动复核已经撤销或失效时，才可走 `cancelled_before_launch`。已有启动意图，即使原主控可能在 `Popen` 之前退出，也应先查进程再查事件。恢复中的任务不能被重新启动。进入等待、回放时均沿用原任务号和实例号，重启后从库内状态接续。[调度器](../../../src/orchestrator/scheduler.py)

**等待和结算分开写。** 等待只更新占用、原因和等待期限。`finish_job` 仅结算尚未终结的任务，保护实例归属，并按原目标场次执行适用的抑制或退避。若手动停止入口已经登记过抑制，结算时不得重复推进控制版本。回放切片的开始事件也不能把恢复中的任务重新置为运行或再清零目标计数。这样在事件提交一半、或全部事件已提交但结算事务尚未提交时再次重启，均可从原日志继续。[任务结算和目标状态](../../../src/orchestrator/storage.py)

**怎么验收**

1. 在独立数据库和输出目录启动测试主控与可控的真实 Worker 子进程，沿用生产启动参数、进程探测和事件发射器，采集输入使用合成媒体。把旧主控停在 `Popen` 成功、`mark_launched` 尚未提交处，只结束该测试主控。用独立连接确认任务 A 的数据库 PID 为空、日志路径和实例归属仍在，同时从系统确认进程仍活着。新主控打开同一数据库，先在第二个实例启动 C，再排入另一目标的任务 B。B 已满足开录条件且无退避，只等 A 的实例空出来。
2. 用同步点让 A 暂不退出。经过至少两次存活探测及完整的调度轮次（含 `_watch_old_workers`、`_dispatch`），A 始终为 `stopping`、实例为 `busy` 且归属 A，B 没有启动，C 仍有进度。另用仅含 A、B 和单个实例的样本，在等待中关闭、重启新主控，A 的占用和 B 的等待均应保留。再用真正未启动的取消任务作对照，确认它无需等满 120 秒，迟到的启动复核也不能发起 `Popen`。
3. 放行 A，使它在断管后补写重复事件、封尾片并退出。分别在“已回放一部分”和“最后事件已提交、结算事务尚未提交”处暂停或再重启。从独立连接检查两处实例仍指向 A，并核对 B 的启动记录为空。放行结算后核对唯一事件数、切片正式路径和质量标记、停止时间、退出码及实例归属。成功样本只释放一次，B 此后才取得该实例。B 启动后再对账 A，B 的占用保持不变。
4. 用可控时钟分别制造归属不明和存活超过 120 秒。隔 60 秒再次手动对账并经过重启，核对 A 的 `ended_at`、`exit_code`，目标的 `retry_at`、`attempts`、`control_revision`、`suppressed_session`、`record_session_key` 均未被等待操作改写，实例仍指向 A。确认 A 退出后再对账才发生一次最终更新。用普通退避和手动停录两种目标验证各自的字段。[调度集成测试](../../../tests/test_scheduler_integration.py) · [真实子进程交付测试](../../../tests/test_real_process_delivery.py)

### 1.2　在线收尾和重启回放共用一套完整性判定

两个已复现的结果需要一并纠正。封片、质量告警和停止事件排在 4,000 条心跳之后时，任务能先失败、切片随后才补成成功。两片都带 `is_final` 时，当前结算还会同时写出 `failed`、退出码 30、`collection_complete=1` 和原因 `completed`。[事件接收](../../../src/orchestrator/worker_process.py) · [任务结算](../../../src/orchestrator/storage.py)

- **在线收尾**　确认进程已退出且该 Worker 的回调全部结束后，在同一先进先出队列放入该任务的收尾标记。按每轮上限消费，前一事件提交后才能越过它处理标记。仅标记暂时放不下时下轮再放。真正发生回调丢失、强制停止或超时，记下原因，在写方关闭后从日志补证。数据库出错按 1.4 处理。[调度器](../../../src/orchestrator/scheduler.py)
- **重启回放**　`_finish_orphan` 按物理行读取字节，逐行解码 UTF-8、解析并校验任务和运行归属。半行、截断的中文字符或无效 JSON 记录位置后继续。将合法事件与库内已有事件合并，按任务和 `event_id` 去重。长日志按调度轮次分批回放，提交成功后才推进读取位置。读取或提交失败保留原文件和已提交事件，重启可安全从头重放。审查样本三条唯一有效事件，原回放遇残行只记了一条。[事件发射器](../../../src/worker/events.py) · [事件入库](../../../src/orchestrator/storage.py)
- **共同判据**　在 Worker 发射锁内为每次运行从 1 分配连续的 `event_seq`，补写沿用原 `run_id`、`event_id` 和序号。在两条路径的同一结算入口，从已提交事件核对同一运行的序号能否从 1 接到最后的 `worker_stopped`，每个已开始切片是否有一个一致的终态，终态是否有对应的开始，整项任务是否至多一个 `is_final`。相同事件重发只计一次，缺少中间的质量告警也要能查到缺号。仅有 `worker_failed` 可保留失败信息，不能替代最后的停止事件。无序号的遗留日志只恢复可确认事实，不能证明完整时明确记为不完整。
- **写入结果**　证据完整则 `collection_complete=1`，按 Worker 的退出码、原因和现有录制规则区分正常结束、带告警结束和失败。Worker 报 0、没有早停请求且切片台账确实为空时，仍按 `no_recorded_segment` 失败。证据不足或矛盾则 `failed`、`collection_complete=0`，保留已有非零退出码，否则用 30。主原因写明缺失序号、片号或冲突类型，Worker 原因另存作上下文。已确认切片和质量标记保留。两条路径都经 1.1 的一次性结算事务释放实例。[录制端停止事件](../../../src/worker/controller.py) · [事件及切片存储](../../../src/orchestrator/storage.py)

**怎么验收**　让同一组有编号的事件分别经过在线自然结束、在线停服收尾和重启日志回放。逐项比较任务状态、退出码、`collection_complete`、主原因、每片终态、正式路径和质量标记。以下结果均须成立。[调度集成测试](../../../tests/test_scheduler_integration.py) · [质量事件事务测试](../../../tests/test_quality_delivery.py) · [断流补写测试](../../../tests/test_worker_events.py)

| 输入或交错 | 应得到的结果 |
| --- | --- |
| 完整无告警、有告警、Worker 自身非零失败 | 前两者分别为 `finished` 和 `finished_with_warnings`，退出码均为 0。后者保留 Worker 的失败码和原因。三者收集完整性均为 1。另用 Worker 报 0、无早停且无任何切片的完整样本，核对业务结果为 `no_recorded_segment`、退出码 30、完整性 1。 |
| 两任务事件交错，其中一项的封片、告警、停止排在 4,000 条心跳之后，收尾标记一度进不了队列 | 标记处理前任务仍占用实例。之后与相应完整样本逐字段一致，每片只记一次，其他任务仍能推进。 |
| 残行或断裂 UTF-8 后有合法事件，并重发丢失的原事件 | 读到后续封片和停止，唯一事件数与干净样本一致，完整性为 1。连续重放两次，任务、切片及目标业务字段不变。 |
| 去掉中间一条质量告警但保留开始、封片、停止，或缺停止、缺开始、缺切片终态 | 即使队列标记已到或文件已读完，也应为 `failed`、完整性 0，给出缺号或未配对的片号。 |
| 两个不同切片都标为最后一片，Worker 报 0 和 `completed` | 两条路径均为 `failed`、退出码 30、完整性 0，原因列出重复尾片的片号。单片终态互相冲突时另按 1.3 隔离该片。 |

### 1.3　同一片出现两种终态时，保留证据并拦住这片的投稿

当前先到 `segment_finished(A.mp4)`、后到同片的 `segment_aborted` 时，第二条事件随异常回滚。数据库仍把 A.mp4 当作已封口文件，网页和投稿接口仍可使用它。[事件入库](../../../src/orchestrator/storage.py) · [投稿资格](../../../src/orchestrator/segment_uploads.py)

- **怎么改**　同一任务同一片的两个独立事件若终态、成品路径或尾片标识矛盾，在一笔事件事务中保留第二条原始证据，并把该切片持久标为 `conflicted`。两条事件 ID、各自路径和原因可追查。列表、详情和筛选显示“终态冲突”，正式可用路径留空，查询层也不能回退展示原始文件为成品。其他片继续正常记账。任务按 1.2 记不完整。若冲突在原任务结算后才查出，只修正旧任务和该片的结果，已执行的实例释放和目标退避不能再执行。[切片查询](../../../src/orchestrator/queries.py) · [切片接口](../../../src/orchestrator/api.py) · [切片页](../../../web/src/views/SegmentsView.vue)
- **怎么拦投稿**　网页关闭争议片的新安排入口。后台打开弹窗、旧弹窗确认、修订和实际派发前都按任务号和片号重查。把冲突提交与同片的新建安排、`mark_sent` 放行操作排出先后顺序，短临界区内核对并登记本次发送权，远端调用放在临界区外。注册和提交各自核对。即使注册已发，冲突一旦先于提交放行，仍须拦下该次提交。已先派发的原单保留查询能力，不自动撤单或重发。普通质量告警仍可按原流程确认。[安排与派发](../../../src/orchestrator/segment_uploads.py) · [安排存储](../../../src/orchestrator/segment_upload_store.py)
- **怎么验收**　同一任务录两片。在第一片分别注入“完成后中止”“中止后完成”和“完成路径不同”，重复回放并重启。两份原始证据均在，冲突状态和空正式路径一致。让冲突分别先于弹窗确认、晚于确认但先于派发，通过实际 HTTP 入口核对前者新增安排为零、两者新增 Core 注册或提交均为零。另给已发原单返回可查结果。第二片仍可由切片页正常安排一次，使用隔离的 Core 替身核对调用数。[投递测试](../../../tests/test_segment_uploads.py) · [网页上传测试](../../../web/tests/upload.test.ts)

### 1.4　数据库暂忙或写入失败时，从实际服务入口验收

- **怎么改**　调度库沿用现有 5 秒 SQLite 写锁等待。锁在期限内释放就继续提交当前事件，提交成功再消费下一事件或收尾标记。超时仍返回 `SQLITE_BUSY`，或遇磁盘 I/O、提交错误时，让 `SchedulerRuntime._run` 走受控停服，保留运行日志、每个任务的 NDJSON 和库中最后已提交状态。停止本主控拥有的 Worker，旧主控遗留的进程继续按 1.1 核验。存储恢复后重新启动，用同一库和日志补账。切片冲突按 1.3 记业务事实，不触发停服。[调度服务主循环](../../../src/orchestrator/server.py) · [SQLite 连接及事务](../../../src/orchestrator/storage.py)
- **怎么验收**　从测试服务启动两个录制任务，用独立 SQLite 连接在其中一项封片前取得写锁。第一组在 5 秒内放锁，确认服务继续运行、另一 Worker 持续产出、两项最终账目各记一次。第二组持锁到超时，另测提交报 I/O 错误，确认服务记录失败并收尾自己的 Worker，两项保留日志，未提交的事件不获成功确认，相关实例不能提前复用。恢复可写后重启同一服务，逐项按 1.2 核对，确实缺证的那一项保留具体原因。须经过服务的异常和关闭分支，单独重调 `_collect` 无法验收这一项。[服务入口](../../../src/orchestrator/server.py) · [真实子进程交付测试](../../../tests/test_real_process_delivery.py)

### 1.5　读不到前台页面时保住正在录的尾片

两次空的前台观测目前就会触发“已离开直播页”，消耗一次恢复机会，并可能把当前尾片标为中止。[录制会话](../../../src/worker/continuous_session.py) · [页面识别](../../../src/worker/live_overlay.py)

- **怎么改**　在 `poll_surface` 分开处理“确认仍在直播页”“确认在其他页面”“本次没读到页面”。连续两次确认离页才用 `runtime_left_live_page`，连续三次读不到才用 `surface_probe_unavailable`。中间出现另一种结果就中断原计数，切换采集代次时清零，过时代次结果丢弃。每次观测最多触发一次恢复。

### 2.5　网页能结束本页跟踪，活动命令不会被历史记录挤掉

### 3.1　分析器重启时，录像继续写入且每个音视频包都对得上

### 3.2　无新切片时，整个录制循环都不再翻看历史

- **怎么改**　把 `apply_identity_risks` 移出逐片循环，按本轮变化批量更新。每个采集代次保存 CSV 已读位置及末尾半行，只消费完整的新行。平时检查当前打开、下一个预期文件、刚封口和待校验的片段。最新封口片先保留，下一片出现时按普通片处理，停录时才确定尾片。启动探测仍能发现第一个已写入的文件，并将首次开始事件交付一次。清单替换、截短或收尾才按需全量核对。[切片清单与启动探测](../../../src/worker/continuous_pipeline.py)
- **另外两处全表扫描**　`check_stream_quality` 每轮遍历台账找本代最新片号，心跳到期时 `get_current_segment_elapsed` 又遍历全部片段找封口时间。分别缓存本代最新已出现的片号、已封口切片最大的有效结束时间戳（PTS）。新增、封口时增量更新，换代先清空，清单异常时重新核对。时间轴缺失、非有限或回退时按本代保守标风险，保留迟到风险回标所需的片号、代次和区间。未出现首片的新代不能给上一代最后一片打标。[录制循环与质量判断](../../../src/worker/continuous_session.py) · [心跳片长](../../../src/worker/continuous_pipeline.py)
- **怎么验收**　分别放入 32、128、512、1,024 条已终结历史和一个当前打开的片。实际跑 `ContinuousSession.run` 的正常迭代，启用质量监控并让心跳到期，逐处统计 `sync`、质量判断、心跳访问的历史行、重读的清单字节和目录枚举次数。无变化且风险稳定时，上述三处重访历史行均为零，旧字节重读与全目录枚举为零，工作量不随历史增长。单独记录处理耗时与主动休眠。原 1,024 片约 314 毫秒是 `sync` 的中位数，只与同口径复测比较。整轮另测同机中位处理耗时，目标低于 100 毫秒，不计轮询休眠。[连续录制测试](../../../tests/test_continuous_and_overlay.py)
