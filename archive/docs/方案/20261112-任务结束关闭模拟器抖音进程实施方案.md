## 问题陈述 (Problem Statement)

本方案实施前，调度器已实现“热实例保持开机、不自动关机”（[ADR 0019](../../../docs/adr/0019-scheduler-on-demand-instance-boot.md)），但除退出码 `15`（登录强阻断）外，其他结束场景只停止底层采集进程与 Worker，不关闭模拟器内的抖音应用。以下保留问题背景与实施决策，当前状态以上方标注为准。

这导致录播结束后模拟器内的抖音仍持续停留在直播间页面或推荐流首页播放音视频，在“不关模拟器”的前提下长期空耗宿主机 CPU、显存、内存与网络带宽，也会把上一场可能出现的界面/弹窗脏状态留到下一次录制。

---

## 解决方案 (Solution)

按照“只清理应用进程、保留热模拟器实例”的原则，将结束时关闭抖音统一收归到 **Recording Worker 的退出收尾阶段**执行，并同步精简调度器历史遗留的独立复位状态：

1. **统一“只杀不重开”**：任务结束时仅向目标模拟器发送 `am force-stop com.ss.android.ugc.aweme` 彻底退出抖音回到桌面，不主动重开抖音首页；下次任务来临时继续由 `WorkerNavigator` 既有的冷启动逻辑自行打开首页、消解弹窗并进入目标直播间。
2. **Worker 收尾统一覆盖全结束路径**：只要 Worker 已拿到实例锁并建立 ADB 连接，无论因手动平滑停止、下播、到时、换场、普通失败、登录阻断 `15`，还是主控 `Ctrl+C` 停止或主控断开后旧 Worker 自行封口退出，都在停止采集、完成切片封口之后、释放实例锁之前发送短超时 `am force-stop`。
3. **短超时容错保终态**：若设备已离线或关闭命令失败，仅记录警告日志，不覆盖原任务终态与退出码；关闭尝试及超时后的命令进程回收结束后仍释放实例锁。正常收尾会增加这段有界等待，不承诺零额外耗时。
4. **合并简化 `resetting` 复位流程**：退出码 `15` 与其他结束路径统一由 Worker 在退出前尝试关闭抖音，不主动重开首页；已移除调度器的 `resetting`（「复位中」）状态、后台 `reset_app` 队列及相关展示。关闭失败也允许实例回到 `idle`，不新增永久阻断；这表示清理尝试完成，不保证抖音已经关闭。

## 用户故事 (User Stories)

1. 作为录播操作者，当我在控制台对一个正在录制的任务点击「平滑停止」后，我希望对应模拟器内的抖音立刻退出回到桌面，不再继续停留在直播间空放音频和画面占用电脑 CPU、显存与带宽。
2. 作为录播操作者，当主播正常下播、到达预设录制总时长或因直播场次切换结束本次任务时，我希望抖音同样被关闭释放资源，以便热保持开机的模拟器处于真正静默的空闲状态。
3. 作为录播操作者，当某路录制因为导航失败、画面卡顿耗尽或录制异常（包括登录强阻断 `15`）退出并等待调度器重试时，我希望实例上旧的抖音进程被清理掉，避免残留页面或卡死进程干扰下次接单。
4. 作为录播操作者，当我在终端按 `Ctrl+C` 关闭整个调度服务时，我希望每个正在收尾封口的 Worker 顺手关掉各自模拟器里的抖音后再退出，不会在停服后留下好几个直播间继续挂机。
5. 作为录播操作者，当我单独通过命令行直接运行 Worker 进行单路录制测试并结束时，我希望它也同样在收尾时关闭模拟器内的抖音，与受调度器管理时的行为一致。
6. 作为录播操作者，当同一台空闲模拟器再次接到新任务时，我希望系统能够从桌面自动冷启动抖音、消解冷启动弹窗并顺利进房开录，不因上次彻底关掉了抖音而进不了直播间。
7. 作为录播操作者，即使遇到模拟器突然掉线或关闭抖音命令超时，我也希望已经录好的完整切片、任务状态和退出码不受干扰，且实例能够正常按掉线/空闲状态释放。

## 实现决策 (Implementation Decisions)

### 1. Worker 收尾关闭抖音机制（`Recording Worker` 与 `ADB 客户端`）

- **关闭能力封装与复用**：
  - 在严禁缺省 `-s` 的 `AdbDeviceClient` 层补充轻量的强制停止包命令方法（如以默认约 `4` 秒短超时执行 `adb -s <serial> shell am force-stop com.ss.android.ugc.aweme`），并完善命令分类统计；复用既有底层命令执行器与单设备绑定约束，不另建独立 ADB 执行包装。
- **执行时机与前提条件**：
  - `WorkerController` 在建立 ADB 连接并生成设备客户端后即保存该清理入口；在 `_cleanup()` 中按固定先后顺序执行：
    1. 停止看门狗并将 Worker 状态推进至 `STOPPING`；
    2. 停止录制采集管线（确保正在进行中的 MP4 封装与切片安全封口先彻底完成）；
    3. 若本次运行已成功建立单设备 ADB 客户端，执行一次强制关闭抖音进程（仅关闭、不重启首页）；
    4. 最后释放 `WorkerInstanceLock` 实例独占锁并将状态推进至 `STOPPED`。
  - **时序保障**：关闭尝试及其命令进程回收位于锁释放与 Worker 进程退出之前；下一单不能与上一次关闭命令并行。调度器收到进程退出后，能确认清理尝试结束、锁已释放，但不能仅凭 Worker 正常退出断言抖音已经关闭。
  - **异常收尾结构**：使用嵌套 `try/finally`，确保看门狗停止、状态推进或管线 `teardown` 抛错时，仍进入关闭尝试和最外层锁释放。原采集/收尾异常继续按既有规则上报，关闭抖音异常只记警告，不遮蔽原异常；不得把未封口切片标为完成。
- **豁免与容错边界**：
  - **未拿锁或未连上设备跳过**：若因锁抢占失败或 `launch_player` / `connect_adb` 失败直接退出，不执行关闭抖音；
  - **强杀与人工对账不动现场**：若 Worker 被外部强杀未进入收尾阶段（例如停机超时触发 `needs_reconcile` / `reconcile`），本就不自动动模拟器现场；
  - **失败隔离**：关闭抖音调用必须完整捕获超时与所有执行异常并仅输出警告日志，绝不覆盖 `controller` 的原始返回码、事件终态或阻止 `finally` 中的 `instance_lock.release()`。
  - **日志与状态口径**：警告包含实例编号、目标 serial、超时或非零退出码及原始错误详情；清理失败后仍允许复用实例，下一单照常经过页面导航和身份门禁，不能以“已清理”替代这些检查。

### 2. 调度器与实例池移除 `resetting` 机制（直接简化演进）

- **状态模型与持久化精简**：
  - `InstanceStatus` 移除 `RESETTING`；数据库实例状态不再产生 `resetting`。
  - `Storage.finish_job` 中对退出码 `15`（登录强阻断）的处理不再切为 `resetting`，改为与普通结束一致：非 `hold_instance` 且非退出码 `20` 时统一直接更新为 `idle`（`hold_instance` 保持 `reconcile`，`20` 保持 `offline`）。
  - 清理 `Storage` 中围绕 `resetting` 的专有方法与判断：移除 `finish_reset()`，以及 `_instance_busy_or_reconcile`、实例同步 `sync_instances` 与控制校验 `_check_instance_control` 对 `resetting` 的特殊保护（旧库中若残留 `resetting` 行的情况在首次刷新同步时即被真实在线状态自动覆写，不做额外迁移脚本）。
- **实例池与调度循环精简**：
  - `InstancePool` 移除 `reset_app()` 及仅服务于该方法的抖音拉起逻辑，保留实例状态探测 `refresh()` 与按需开机 `boot_instance()`。
  - `Scheduler` 移除 `self._resets` 并发跟踪表及 `_instances()` 中对 `resetting` 实例的扫描、提交与回收调用。

### 3. HTTP 接口契约、前端控制台与文档同步

- **后端查询与校验契约**：
  - `GET /api/instances` 的 `status` 筛选枚举收窄为 `idle | busy | booting | offline | reconcile`；
  - `GET /api/overview` 的 `instance_counts` 返回字典不再包含 `resetting` 键。
- **前端界面与交互同步**：
  - 移除前端状态标签枚举、Tag 配色映射、`disableInstanceReason` 停用拦截提示、以及本地 Mock 初始计数中的 `resetting` / 「复位中」相关定义；前端实例与总览页面同步保持 5 个实例状态。
- **文档与待办更新**：
  - 同步更新 [控制台接口契约](../../../docs/控制台接口契约.md)（实例状态枚举与总览字段）与 [最小调度运行说明](../../../docs/最小调度运行说明.md)（退出码 `15` 说明与实例状态说明）；
  - 更新 [待办](../../../docs/待办.md) 中 `T10` 的状态为“代码与自动化验证完成，待实机结束关闭抖音及随后冷启动再录验收”（实机验收通过后再从待办移出）。

## 测试决策 (Testing Decisions)

优先复用项目已有最高层测试边界，仅聚焦外部可见行为与状态流转：

1. **Worker 层测试 Seam（复用现有 `WorkerController.run()` + `worker_harness`）**：
   - **Seam 选择**：通过既有 `worker_harness.build_worker` 替身隔离真实 `MuMuClient`、采集管线与 ADB 命令行执行边界，驱动完整的 `WorkerController.run()` 生命周期。
   - **覆盖场景**：
     - 定时结束、手动平滑停止、下播/失败退出（含 `15`、`16`、`17`、`18`、`30`）结束后，验证正常路径先完成采集 `stop/teardown` 再发出针对该设备序列号的 `am force-stop com.ss.android.ugc.aweme`；仅在收尾阶段断言未发出 `am start`，启动和导航阶段允许正常拉起首页；
     - 模拟 `am force-stop` 抛出超时或返回非零退出码，验证 Worker 依然正常释放实例锁并返回原定退出码与完整终态事件；
     - 模拟连接 ADB 失败直接以 `20` 退出时，不会发出 `am force-stop`。
     - 模拟看门狗停止或管线 `teardown` 抛错，验证关闭尝试仍执行、实例锁仍释放、原异常未被关闭错误覆盖；通过后续 Worker 能否获取同一实例锁核验归还结果。
     - 单独覆盖关闭成功、非零退出、超时回收三条路径；下一单使用相同实例从桌面重新启动并通过正常导航与身份校验。
2. **调度器与控制台 API 层测试 Seam（复用现有 `Scheduler` 周期驱动、`TestClient` HTTP 接口与 `InstancePool` 测试先例）**：
   - **参考先例**：沿用既有 `Scheduler` 集成测试与 FastAPI `TestClient` 控制台接口测试体系，以及 `InstancePool` 单元测试模式。
   - **覆盖场景**：
     - 退出码 `15`（登录强阻断）任务结束后，实例立即回到 `idle` 并允许在退避到期后重新认领任务，不再经过 `resetting` 或触发 `reset_app`；
     - `GET /api/overview` 不再返回 `resetting` 计数，`GET /api/instances?status=resetting` 按非法枚举返回 HTTP `422`；
     - `InstancePool` 不再暴露已废弃的 `reset_app`，既有 `refresh` 与 `boot_instance` 行为不受影响。
3. **前端编译与测试 Seam（复用 `vitest` 单测与 `vue-tsc` + `vite build`）**：
   - 更新并运行前端标签映射与实例停用校验的 `vitest` 单元测试，以及完整前端类型检查与构建。

## 范围外说明 (Out of Scope)

- 不在本方案中关闭或休眠 MuMu 模拟器本身（模拟器关机控制继续遵守 [ADR 0019](../../../docs/adr/0019-scheduler-on-demand-instance-boot.md) “按需开机、不自动关机”）。
- 不调整抖音冷启动进房的弹窗消解或导航等待策略（沿用既有 `WorkerNavigator` 冷启动保护；如实机复测发现冷启动等待时间不足再单列调整）。
- 不处理因外部硬强杀进程导致已进入 `reconcile` 人工对账状态的实例（保留现场由人工核查）。
- 不迁移旧版本 `orchestrator.sqlite3` 数据文件（内部开发阶段保持简洁演进，依赖周期刷新覆写）。

## 补充说明与验收标准 (Further Notes)

### 验收标准

1. 自动化验收：新增及调整后的 Python 全量测试与前端 `vitest` + `vue-tsc` + `vite build` 全部通过（无跳过、无放宽断言）。
2. 实机验收（对应 [待办 T10](../../../docs/待办.md#待做) 未验证闭环）：
   - 控制台点击「平滑停止」或触发一次任务结束后，核实对应模拟器内抖音进程确实已退出回到桌面（不再停留直播画面播放），实例随即显示为 `idle`；
   - 随后立即在同一台热实例上再发起下一次录制，确认 Worker 能从桌面冷启动抖音、通过弹窗消解与身份核验并正常开录；分别记录关闭耗时、下一单导航耗时与首片开始时间，不能以命令成功或进程退出代替实机功能验收。

### 风险与留意事项

- 每次成功关闭抖音后，下一单会经历冷启动。2026-11-13 台式机样本的导航耗时 9.746 秒、Worker started 事件到首片开始 16.454 秒，300 秒预算内完成；详见实机记录。单次样本与代码固定等待均不代表所有冷启动耗时保证。
