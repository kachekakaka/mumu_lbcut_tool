## 1. 要解决的问题

现有便携包分别启动录播和上传，录播端首次只让用户选录像位置。两边的默认业务数据分别在 `%LOCALAPPDATA%\MuMuLBCut\data` 和 `%LOCALAPPDATA%\fileUploadPlatform\MuMu\data`。源码版的调度数据库默认在仓外 `mumu_lbcut_tool_dev/runtime-console-unified`，运行示例把录像放在同级的 `recordings`。当前正式录像的目录使用任务号和 Worker 运行号，文件名又重复运行号，投稿清单则在 `sessions/<作品 UUID>/upload.yaml`。用户很难在资源管理器里找到某位主播的某一场。[现行运行说明](../../../docs/最小调度运行说明.md) · [现行文件存放表](../../../README.md#项目目录与文件存放)

目标是首次只选一次工作目录，双击 MuMu 即可启动配套服务。平时按主播和时间找录像，录断的那一段也在原场次里。程序继续用内部编号识别任务和作品。用户已确认的规则见设计决定。总入口文件名、缺少昵称的备用名、同一分钟场次的短后缀，以及手动清单按片号分目录，是本方案补充的实施细节。[目录设计决定](../../../docs/adr/0023-recording-workspace-and-session-directories.md)

## 2. 在资源管理器里会看到什么

下面是新整合包使用默认位置的例子。第一场正常结束并安排整场投稿，第二场跨过午夜，第 003 片中断，后来只手动安排了第 004 片。

```text
解压所在目录/
├─ MuMu录播与上传/
│  ├─ 启动MuMu.cmd                    拟增的总入口
│  ├─ workspace.json                  首次确认后生成，只记工作目录
│  ├─ 录播/                           程序、网页和随包工具
│  └─ 上传/                           上传程序和引擎
└─ mumu_lbcut_tool_dev/               默认工作目录，可选别处
   ├─ runtime-console-unified/        录播设置、调度库、任务日志
   ├─ upload-platform/                上传任务库、登录状态、上传日志
   └─ recordings/                     默认录像根，也可以单独选另一个盘
      ├─ _录制中/                     正在写入的文件、采集过程材料
      └─ 小林/
         ├─ 2026-11-24_1930/
         │  ├─ 001.mp4
         │  ├─ 002.mp4
         │  └─ upload.yaml            整场投稿清单
         └─ 2026-11-24_2350/
            ├─ 001.mp4
            ├─ 002.mp4
            ├─ 003-中断.mp4           断线前实际留下的文件
            ├─ 004.mp4                恢复后新录的一段
            └─ 投稿/004/upload.yaml   手动安排第 004 片，引用原视频
```

`_录制中` 专供程序在录像所在卷写入和核对材料。有来源可核对、已结束写入的中断原片归入场次目录。投稿清单按实际安排生成，单纯录制只产生录像和必要的运行记录。

## 3. 工作目录、启动入口与换包

首次让用户选工作目录、以后从启动器旁读取 `dataDirectory`，参考 videoCutTool 的桌面启动方式。MuMu 的录播库、上传部署和录像盘分别核验。[videoCutTool 首启选择目录](../../../../videoCutTool/electron/desktop.ts) · [指针的读写](../../../../videoCutTool/src/main/services/ConfigService.ts)

| 位置 | 谁决定，存什么 |
| --- | --- |
| 程序目录 | 总启动器以自身所在的包根目录定位 `workspace.json`，从快捷方式或其他命令行目录启动结果一致。文件只保存 `dataDirectory` 的绝对路径。独立录播包以自己的包根作为入口，整合包的录播入口遵循总入口的同一份选择。开发机指针不进入 Git 或发行包。 |
| 工作目录 | 首次提供「使用默认目录」和「选择其他目录」。默认位置是整合包的**同级** `mumu_lbcut_tool_dev`。录播程序内部的同名 `mumu_lbcut_tool_dev/tools` 保存随包工具。仓外已有的临时、打包、工具目录沿用 [README 的职责表](../../../README.md#项目目录与文件存放)。 |
| `runtime-console-unified` | 录播端管理 `orchestrator.sqlite3`、事件、任务日志和录播设置。单独指定录像盘时，把录像根保存到这里的 `settings.json`。启动调度器时显式传录播数据目录与生效的录像根。 |
| `upload-platform` | MuMu 启动 `fileUploadPlatform` 时传入这个子目录的绝对路径。上传端自行管理 `core`、`bilibili-private`、`logs` 等内容，核验自己的数据库与部署编号。账号、登录状态和运行库只由上传端读写。 |
| 录像根 | 默认取工作目录的 `recordings`。有专用录像盘时，只需指定一次，主播目录、场次、清单以及录制中的媒体都落在选定的录像根。录像根须与程序、两边的私有数据目录分开，防止把登录资料放进素材范围。 |
| 本机互斥和进程记录 | 同一 Windows 用户的便携副本继续共用 `%LOCALAPPDATA%\MuMuLBCut` 下的启动锁和实例锁。上传端保留识别进程和部署所需的启动记录。切换工作目录也要能识别仍在运行的旧服务。 |

- **新建与重开。** 首次确认后核对实际要用的子目录、可写性和录像盘的无覆盖落盘能力。已有 `_dev` 可以含工具和打包产物。复用录播数据时核验原库，复用上传数据时由上传端核验原部署。新设置先完整写入临时文件再原子就位，取消选择时不建库。程序目录无法保存指针时给出具体路径，用户可换到可写的位置启动。
- **原路径不可用。** 已有指针损坏时提示 `workspace.json` 的位置。数据盘离线、设置丢失或已有库版本不符时，显示原路径和原因，保留现场。换包时可保留指针，也可在新解压位置重新选择原工作目录。新布局下再次换包应能看到原来的主播、账号和任务。旧部署的 `core-v2/core.sqlite3` 与上传便携版的 `core/core.sqlite3` 布局不同。选择到旧布局时提示回原部署，不在旁边初始化一份空库。
- **整合启动。** 总入口向上传启动器显式传 `--data-dir`。首次新建须确认上传专用目录为空，已识别的同版部署可直接核验复用。上传端用现有启动记录中的 `data` 和 `deployment_id` 提供可核对的结果。MuMu 核对指定路径、健康接口报告的部署编号和就绪状态，将核实过的编号记在本工作区的录播设置里。
- **再次启动。** 已有绑定时，MuMu 随路径交给上传端预期部署编号。上传端在任何建库动作前只读核验原库，再启动或复用同一部署。新投稿请求也带上这个编号。端口由其他部署占用、原库丢失或编号不符时，提示原路径并保全已有任务。上传端未就绪时录播仍可启动。独立录播包可单独录制，单独启动上传包时沿用上传端自己的已保存设置。[录播端目前的部署核对](../../../src/orchestrator/upload_platform.py) · [上传端的便携启动实现](../../../../fileUploadPlatform/src/upload_platform/portable.py)
- **面板打开后仍认原工作区。** MuMu 打开内嵌的账号、作品或任务页时，把本工作区保存的预期部署编号传给页面。页面读取业务数据、管理账号、预览、提交和查回时都携带这个编号，由上传端在返回数据或执行操作前核对。页面刷新、服务重连或更新面板会话时沿用原编号。从健康接口读到的编号只用于比对。缺少绑定时提示尚未绑定，编号不符时提示部署冲突，两种情况都停止加载业务数据和提交。[MuMu 面板入口](../../../web/src/components/UploadPanel.vue) · [面板就绪检查](../../../src/orchestrator/segment_upload_api.py) · [上传端作品页](../../../../fileUploadPlatform/web/src/features/works/Works.vue) · [面板请求](../../../../fileUploadPlatform/web/src/api/client.ts) · [上传端接口核验](../../../../fileUploadPlatform/src/upload_platform/api/app.py)
- **窗口只退出自己核验过的部署。** 上传启动窗口在成功启动或复用服务时记住数据目录和部署编号。点击「退出上传平台」时，在现有操作锁内核对这两项以及仍在运行的 API、Worker 进程记录。核对通过才向对应进程发退出请求。窗口尚未绑定或共享启动记录已指向另一套部署时，拒绝退出并提示当前目录。[上传启动窗口](../../../../fileUploadPlatform/src/upload_platform/portable_window.py) · [退出进程的实现](../../../../fileUploadPlatform/src/upload_platform/portable.py)

## 4. 主播名、片号与归档时机

1. **一个主播一个固定目录。** 用已核实的主播身份关联目录。首次用昵称命名，重名依次分配 `小林`、`小林-2`。主播改名时控制台更新昵称，以后录到的场次仍归原目录。生成 Windows 名称时替换非法字符、处理保留名、尾部点和空格，并限制过长组件。昵称缺失或处理后为空时用短名 `主播` 并按相同规则避让。`_录制中` 是保留目录。大小写、截短或字符替换造成的重名按同一规则处理，未知已有目录不自动归给主播。
2. **同一场只定一次日期。** 以本场首片实际开录的北京时间生成 `YYYY-MM-DD_HHmm`，依据是已有的首片开始事件。排队时间、程序启动时间、午夜和换机续录都不会改变这场的目录。不同场恰在同一分钟首次开录时，再加短后缀 `-2`、`-3`。数据库记录这场确认的录像根与目录，后面的事件和查单使用原记录。
3. **片号属于整场。** 在调度数据库中，把既有的任务、运行与任务内片号关联到唯一的场内片号。以 `001` 起步，至少三位，超过 `999` 自然继续。通常在接受开始事件时分配片号。若原片先落盘、开始事件未入库，恢复时按下述规则核实归属。两种情况都在事务内查找已有片号，仅在首次登记时分配新号。重复对账和迟到事件都取回原号。同场续录分配新号前，先核对上一轮实际写出的片段，再从已登记的最大号继续。任务内的事件编号和 API 查询键继续用于对账。
4. **中断也保留原来的位置。** 正常收尾且通过媒体检查的短尾片和普通成片一样保存。异常中断时，确认写入已结束、原文件属于该场后，把实际留下的内容以 `NNN-中断.mp4` 原样归档。原文件可能只能播放一部分，也可能无法播放。只有事件而没有文件时保留片号和原因，不生成占位视频。恢复从下一号开始，不拼接或覆盖前一段。其他校验失败、身份不明或终态冲突保留各自的证据和原因，不能只凭扩展名认成正常切片。
5. **写入前登记，封口后保留原名。** 每次启动采集进程前，先在重启可读的台账登记任务、Worker 运行、本次采集使用的独占暂存目录、起始任务内片号和原片命名规则。这样即使 Worker 还未来得及上报开始事件，也能在限定目录内找到已写出的原片。Worker 封口校验时保留已登记的原文件名，直到调度器确认正式文件已归档入账。[采集与事件](../../../src/worker/continuous_session.py) · [片段发现](../../../src/worker/continuous_pipeline.py) · [封口检查](../../../src/worker/segment_verifier.py)
6. **落盘与重启对账。** 调度器分别记录事件来源、预定最终路径和归档状态。先持久化归档意图，再同卷无覆盖发布，最后登记成功并释放内部暂存名。可复用硬链接，已有目标须核对是否为上次归档的同一文件。源和目标不符时保全两侧并报出路径。重启后重放已保存事件、补做未完成的归档，事件去重仍使用原始来源。[事件入库](../../../src/orchestrator/storage.py) · [场次和切片对账](../../../src/orchestrator/session_ledger.py)

恢复缺少事件的片段时，先确认原 Worker 和采集进程都已退出，再按本次采集登记的目录、片名规则和身份记录核对原片。能重放正常封口事件的，按原终态处理。归属明确但缺少终态的，保留为该场的 `NNN-中断.mp4`，记录「缺少终态，待核对」。仍在写入或归属不明的文件留在原处。日常恢复依据台账和文件身份归档，逐字节比对只用于第 7 节的短样本验收。

## 5. 投稿清单、预览和打开文件夹

- 整场清单位于 `<场次>/upload.yaml`，手动单片清单位于 `<场次>/投稿/<片号>/upload.yaml`。两种提交都显式传清单的绝对路径和该场次目录作为 `asset_root`，清单里的视频路径写成 `001.mp4` 这样的场内相对路径。两种入口引用同一份正式视频。作品 UUID、部署编号、请求键仍承担作品识别和原单查回。相同安排复用原记录，发现已有清单属于其他作品或已被修改时保留原件并提示冲突。[MuMu 清单生成](../../../src/orchestrator/upload_manifest.py) · [上传平台按任务读取清单和素材](../../../../fileUploadPlatform/src/upload_platform/application/submissions.py)
- **录像根和投稿素材根分别保存。** 手动预览和生成整场安排时，分别保存本场登记的录像根、场次目录（`asset_root`）以及各片的身份和文件快照。替换两处 `录像根/<任务号>` 检查，并同步修改共用的发送前检查 `preflight` 和手动预览过期后的原片检查 `check_revision_source`。先确认录像根属于本工作区，再确认素材根就是该根下登记的场次目录。每个视频的规范化路径须与本场、本片登记的正式文件一致。实际发送前还要核对封口和归档结果、文件快照及清单版本。已发请求先按原部署和请求键查回。已受理的关联原任务。明确未受理且预览过期的，复核原片后可重新预览并确认。[手动投稿与共用发送检查](../../../src/orchestrator/segment_uploads.py) · [整场投稿检查](../../../src/orchestrator/session_deliveries.py)
- **打开文件夹。** 从原切片记录取路径，接口继续按切片身份寻址。录制中的文件只在登记的暂存位置查看。跨盘打开历史记录时核验本工作区已确认的原录像根，盘离线则提示原路径。[打开文件夹的接口边界](../../../docs/adr/0021-console-desktop-reveal-for-segments.md)
- **等最后一片归档后再固定整场清单。** 自动投稿开启时，最后一个录制任务退出只是收场的第一步。若还有切片正在归档，持久保存收场原因和当时的投稿绑定，保持等待归档，暂缓固定清单和创建投稿任务。归档完成时重新检查该场，重启对账也检查已收场但仍在等待的场次。全部切片的归档结果明确后，再核验封口、身份和顺序。有中断、确认缺片或终态冲突时整场进入待核对。全部正常时按场次复用同一投稿安排和请求键，重复通知只关联同一任务。等待期间已停用的投稿按原停止规则处理。[收场时记录切片](../../../src/orchestrator/session_ledger.py) · [整场交付与重查](../../../src/orchestrator/session_deliveries.py)
- 正常多片按录制顺序提交，`001.mp4` 默认显示分 P 标题 `001`。整场标题沿用现行规则，单片手动投稿沿用现有可投稿条件。同一片多账号的清单结构留给上传平台后续讨论。[整场标题规则](../../../docs/最小调度运行说明.md#在主播页启用自动投稿)

## 6. 实施顺序和改动入口

| 顺序 | 改动入口 | 完成条件 |

## 7. 验收、风险与边界

以下是实施后的验收标准。用隔离工作目录、测试账号数据和既有测试入口取证，历史录像与真实任务保留原位。

| 场景 | 要检查的结果 |
| --- | --- |
| 首启、取消、换包 | 取消后没有新工作库。选默认或有中文和空格的其他目录后，实际文件落在第 2 节的位置。保留指针或在新解压位置重选同一工作目录后，能看到同一批主播、上传账号和任务。实际检查包目录和隔离的用户目录，无意外生成的业务库或录像。 |
| 专用录像盘与异常目录 | 把录像指定到另一个本地卷，过程媒体和成片都在该卷，两边数据库在工作目录。原盘离线、指针损坏、原库丢失或数据目录与解压目录重叠时，指出具体路径，没有新空库替代旧记录。 |
| 主播和场次重名 | 两位同名主播各有自己的目录，一位改昵称后新旧场次仍能一起找到。同一天两场及同一分钟两场各归各处。含 Windows 保留字符的昵称、正常文件和预先放入的未知同名文件都不会导致覆盖。 |
| 短尾、中断与续录 | 正常短尾通过检查后保存为 `003.mp4`。中断且有原片时，同场保存 `003-中断.mp4`，跨午夜续录产生 `004.mp4`。中断原片缺失时只记原因，不补假文件。中断场次显示待核对。 |
| 003 在事件入库前断电 | 用已录完 001、002 的测试场次，在两个时刻分别模拟断电。一次选在 003 原片已写出、开始事件尚未上报时，另一次选在 003 已封口、完成事件尚未持久化时。每次在模拟断电前，把当时已写入的短原片另存作对照。若无可重放的终态，重启并重复对账后，场内只有一份 `003-中断.mp4`，与对照样本逐字节相同，续录为 `004.mp4`。另用已保存正常终态的样本重放，得到一份 `003.mp4`。归属不明的文件留在暂存位置。 |
| 崩溃与重放 | 在登记意图后、文件已就位而归档状态尚未提交时分别重启，并重放同一事件。每个切片只占一个场内号，原视频不被替换，旧 Worker 尚在写的文件不会被提前归档。 |
| 手动和整场投稿实际受理 | 在隔离上传部署中，让完整的两片场次自动提交，另一场通过手动预览、确认提交。两份请求的素材根各自指向本场，清单分别位于场内的 `upload.yaml` 和 `投稿/<片号>/upload.yaml`。自动稿引用的 `001.mp4`、`002.mp4` 顺序和分 P 标题正确，手动入口的「打开文件夹」选中原片。两场各取得一个受理任务编号，重开按原请求查回同一编号。把引用换成邻场同名的 `001.mp4` 时，发送前拒绝，上传端任务数不增加。 |
| 手动预览过期后重试 | 让已发出的手动请求查回为空，重放时由上传端明确拒绝为预览已过期。原片未变时，重新预览并确认能得到一个受理任务。另用一份过期安排，在重新预览前替换原片，须提示原片变化，上传端没有新增任务。 |
| 收场时最后一片还在归档 | 开启自动投稿，最后一个录制任务退出时暂缓登记最后一片的正式路径。此时场次等待归档，尚未固定清单或发出请求。分别在本次运行中补齐和重启后补齐，再次重放归档完成通知，每场都只受理一个任务，清单含最后一片且顺序正确。若对账确认该片中断或缺失，则场次进入待核对，提交数为零。 |
| 上传不可用或已有其他部署 | 只启动录播仍可保存成片。整合包遇到另一个正在监听的上传部署时提示冲突，录播可用，投稿不会误送到其他库。 |
| 面板打开后切换上传部署 | 准备账号和任务可区分的 A、B 两个隔离工作区。在 A 的内嵌面板读到 A 的账号并预览作品后，停掉 A 的上传服务，让 B 接管同一端口。从旧面板刷新账号和任务、修改测试账号、发起新预览或确认原预览，都应提示部署冲突。重新取得会话后仍看不到 B 的数据，B 的账号记录与任务数保持测试前的值。 |
| 旧窗口退出上传平台 | 用 A 的上传启动窗口正常停服并保留窗口，再用 B 的窗口启动服务、处理一个隔离任务。从 A 的旧窗口再点「退出上传平台」，应提示部署不符。此时 B 的 API 仍可访问、Worker 心跳继续且测试任务能完成。从 B 自己的窗口退出时，其服务正常停止。 |

录播端的目录、切片和投稿用例可复用现有回归入口。涉及切换上传部署的两项，使用真实便携窗口和内嵌面板，核对接管端口后的上传库与运行进程。[便携设置](../../../tests/test_portable_settings.py) · [切片完整性](../../../tests/test_segment_integrity.py) · [手动投稿](../../../tests/test_segment_uploads.py) · [整场交付](../../../tests/test_session_deliveries.py)
