## 1. 目标

MuMu 负责录制、切片和生成符合统一 Manifest 契约的作品 `upload.yaml`，通过 fileUploadPlatform 的统一接口提交，并将平台作品和任务编号关联回原场次或手动选中的切片。

普通作品和自动直播场次作品统一使用 YAML：

- 普通作品使用独立的 `upload.yaml`。从 MuMu 切片页手动安排一片时，由 MuMu 生成这份文件。
- 自动直播场次在录制收尾、素材清单冻结后，由主播级模板和本场资料自动生成独立 `upload.yaml`。
- 主播级投稿设置只是生成模板，不是另一份作品级投稿配置。
- 上传平台负责读取、校验、预览、登记、任务快照和执行。

## 2. 非目标

MuMu 不再负责 B 站扫码登录、平台 Cookie、上传 Worker、平台 Adapter、上传重试、远端投稿核验、完整上传任务中心和平台投稿参数编辑器。MuMu 保留录制专业业务、场次交付资格判断、主播级自动投稿策略和最小关联记录。

## 3. 已确认架构决策

| 编号 | 决策 |
|---|---|
| R1 | YAML 是唯一作品投稿配置来源；新任务使用提交时配置快照；自动场次生成独立 YAML。 |
| R2 | fileUploadPlatform 是 Work/Task/Attempt/Event/Receipt 的唯一权威；MuMu 只管理录制场次和交付关联。 |
| R3 | Windows 本机、单用户。内嵌面板直接打开，B 站投稿账号的扫码和凭据由上传平台管理。 |
| R4 | MuMu `127.0.0.1:8000`，上传平台 `127.0.0.1:8765`，独立服务，iframe 集成。 |
| R5 | 上传平台采用轻量 Registry；MuMu 不实现上传插件或 Adapter。 |
| R6 | 上传平台提供 Overview、Accounts、Works、Tasks、Schedules、Settings；MuMu 保留录制控制台。 |
| R7 | MuMu 使用统一提交 API。请求与回执要求见第 7 节，联调时与目标服务发布的接口定义核对。 |
| R8 | 开发版的手动、自动投稿都直接使用新客户端。双项目联调通过后再切换日常使用的版本，正式产品只有一条投稿路径。 |

## 4. 职责与状态边界

### 4.1 MuMu 负责

1. 直播目标、录制任务、Worker、切片和场次生命周期。
2. 首片实际开录时记录主播身份、直播间标题和北京时间开录时间。
3. 判断自然下播/主动停录、Worker 收尾、事件收齐、切片封口和身份校验。
4. 判断场次是否符合自动交付条件。
5. 保存主播级自动投稿开关、默认账号和分区。
6. 为符合交付条件的场次冻结素材顺序和作品配置，生成独立 YAML。手动单片按[普通作品流程](#51-普通作品)生成 YAML 并取得用户确认。
7. 调用统一提交 API，把 Work ID、Task ID 关联回发起投稿的场次或切片。
8. 在 MuMu 页面展示简要交付状态；完整上传进度、Attempt、Event、Receipt 和核验通过 iframe 进入上传平台。

### 4.2 上传平台负责

Manifest 解析、路径安全、平台能力校验、Work 登记、幂等、Task 创建、Task Snapshot、账号登录、Worker/Adapter、重试、取消、远端查询、UNCERTAIN 处置和 Dashboard。

### 4.3 状态定义

MuMu 场次状态只描述录制和交付：

- `recording`：本场录制中。
- `checking`：等待收尾证据、标题补查或素材检查。
- `only_record`：只保留录像，不自动交付。
- `pending`：YAML 已生成，等待提交或查回。
- `delivered`：上传平台已受理并返回 Task ID。
- `review`：素材、配置或交接需要人工处理。

`delivered` 不代表视频上传或 B 站投稿成功。平台 Task 状态是唯一上传执行状态来源。MuMu 的 `observed` 只能是展示缓存，不能覆盖平台状态。

## 5. YAML 与素材目录

### 5.1 普通作品

已有作品目录的普通作品使用其中的 `upload.yaml`。从 MuMu 切片页手动发起时，若本次投稿已有安排就打开原单。尚无作品文件的切片由 MuMu 按以下步骤准备。

1. 用户在录制机本机选中一条已封口的切片，点击「安排上传」。MuMu 根据切片台账定位录像，展示质量提示，用该片资料预填投稿信息。用户核对账号、分区、可见范围，并补齐本次所缺的投稿字段。关闭主播自动投稿开关后，手动入口仍可使用。
2. MuMu 为本次单片作品生成独立 YAML，采用一个 `independent` 单元和一个选定账号。生成的文件沿用下节的作品 UUID 目录，素材路径相对于授权录像根目录。同一次安排重新预览时沿用原 UUID，同一 Job 的不同切片可各自保存作品文件。
3. MuMu 展示平台返回的预览。用户看过录像、账号和可见范围，点击「确认安排」后才提交。确认时服务端复核原部署、账号身份、文件和质量提示。资料或配置有变时须重新预览。打开、刷新或取消预览都不创建 Task。

手动入口在用户确认时、自动场次在冻结清单时，均在本地写事务中核对并记录切片归属，随后在事务外调用平台。仅打开预览不占用切片。并发时沿用[现有手动与整场冲突规则](../../../src/orchestrator/segment_upload_store.py)。

- 整场已占用该片时，切片行展示原安排，取得 Task ID 后可直接打开。
- 手动单片先确认时，若本场恰好只有这一片，且唯一原安排的部署、账号及 MID、素材和投稿字段均一致，自动场次关联原作品和任务。原单尚在途时沿该单查回。
- 多片场次仅有部分重合，或原安排不唯一、资料不一致时，场次转入 `review`，并指明冲突切片。

### 5.2 自动场次作品

场次在台账中以 `target_id + session_key` 标识。`session_key` 可能是 `room:123`，其中的冒号不能作为 Windows 目录名。首次冻结清单时，MuMu 在事务内为该场取得或保存唯一的作品 UUID（即 `work.id`）。目录使用这个 UUID，重复收尾和服务重启均从原记录取回。下例中的 MP4 文件名仅用于说明位置。

```text
<output_dir>/
├── job-a/000001.mp4
├── job-a/000002.mp4
├── job-b/000001.mp4
└── sessions/<work-uuid>/upload.yaml
```

YAML 中视频 ID 与相对路径按冻结清单生成，例如 `p1` 对应 `job-a/000001.mp4`，`p2` 对应 `job-a/000002.mp4`，`p3` 对应 `job-b/000001.mp4`。多个视频使用一个 `multipart` upload unit，`videos` 数组就是分 P 顺序。不得扫描邻场，不得以文件名排序替代录制台账顺序。

MuMu 按上图实现 YAML 写入和素材定位，并将 YAML 路径 `manifest_path` 与录像根目录 `asset_root` 分别传给平台。本地自测用 Windows 临时目录写出实际文件，核对重启后使用同一份 YAML、两份同名切片各指向正确的 Job、录像原件留在原处。

0.2.0 从允许的配置目录读取 YAML，以授权的 `<output_dir>` 读取素材。联调还须核对平台对配置或素材越界的拒绝结果。旧 dev6 从登记的 `directory` 读取 `upload.yaml`。不得通过 `../`、复制、移动或拼接 MP4 绕过目录约束。

### 5.3 YAML 内容与生成时机

YAML 必须符合上传平台现有 `manifest-v1` 契约，包含版本、Work 元数据、素材、`upload_units`、`mode`、`videos` 顺序、`targets` 和平台 options。

主播设置只作为模板：

- 自动投稿开关属于 MuMu 调度策略，不进入作品投稿配置。
- 默认账号、分区进入生成的场次 YAML。
- 本场标题、标签、版权、转载来源、可见范围进入 YAML。
- 当前自动投稿默认 `self_only`，但上传平台必须重新校验真实能力。

生成顺序：

1. 首片真实开始时保存本场标题和开录时间。
2. 等自然下播确认或主动停录，并等待相关 Worker 收尾、事件收齐、切片终态明确。
3. 校验切片完整性、身份和风险。身份不明、录错房、未封口、损坏、缺片时进入 `review`，不生成可提交的 ready YAML。
4. 冻结有序素材清单并核对切片归属。命中可复用的手动原单时，沿用其作品 UUID 和 YAML 版本，直接关联原任务或只读查回。仅新作品继续以下生成和提交流程。
5. 用已记入台账的作品 UUID 定位目标目录。通过临时文件原子写入 YAML，保存路径、本地配置修订和清单版本后转入 `pending`。若中途重启，按原 UUID 和冻结输入续办，核对已存在的文件再补记。内容有冲突时保留现场并转入 `review`。本步骤在上传平台离线时也能完成。
6. 预览和提交都以已保存的 YAML 为准。提交前绑定平台可核对的配置版本，后续重试引用同一版本。
7. YAML 在预览与提交之间变化时，旧预览失效，必须重新预览；不得静默换用新内容。
8. Task 创建后只使用上传平台 Task Snapshot。

媒体文件继续使用现有的存在性、可读性、大小、修改时间和切片台账证据校验。平台返回的配置版本用于核对 YAML。

## 6. 场次交付规则

沿用 `4fe8603` 的录制收尾和切片资格判断。原有隔离验证覆盖 dev6 交单，以下规则在新的 YAML 和统一提交链路上仍须验收。

- 首次真实 `segment_started` 记录的标题和开录时间优先；标题缺失才补查同一场次，不能混入下一场标题。
- 自然下播必须经调度器现有确认；主动停录可作为收尾原因。
- 正常轮转、`is_final`、设备掉线或主控退出单独都不能触发交付。
- 必须等待所有相关 Job 收尾、事件收齐和切片终态明确。
- 身份已核实且文件完整的短暂遮挡切片可按既定质量规则交付并保留提示。
- 身份未核实、录错房、文件损坏、未封口、片号中断、素材重复或顺序冲突，进入 `review` 并保留原始录像。
- 同场跨 Job 切片按首片实际开始时间、任务台账顺序和数字片号形成稳定顺序。
- 本场只生成一个 Work；多片使用一个 multipart unit，不拆成多份稿件。
- 账号、分区、可见范围来自场次 YAML；上传平台提交前重新校验账号、MID、分区和目标能力。
- 关闭自动投稿只影响尚未提交的场次，不停止录制，不取消平台已受理 Task。
- 提交结果不明时按原幂等键和原 YAML 版本查回，不得创建第二个 Work/Task。

## 7. 统一提交 API 与幂等

MuMu 使用 0.2.0 的统一接口。手动单片先通过 `POST /api/v1/submissions/preview` 取得 `preview_id`，用户看过并确认后提交这个预览编号。自动场次提交 `manifest_path`、`asset_root`、冻结的配置版本 `expected_version` 和 `execution.type=immediate`，可用 `source` 关联原场次。

两种交付都向 `POST /api/v1/submissions` 发送 JSON，请求头携带本地已保存的 UUIDv4 `Idempotency-Key`。查回时向原部署发送 `GET /api/v1/submissions/result`，在请求头中使用原 Key。[0.2.0 程序投稿说明](../../../../fileUploadPlatform/docs/operations/dashboard.md#程序和网页投稿) · [平台 OpenAPI](../../../../fileUploadPlatform/schemas/openapi.json)

手动提交绑定用户确认的预览及其配置版本。自动提交可由平台一次读取、校验和受理，但须能核对本次冻结的 YAML 版本。同一路径下文件已变更时，未受理的提交应返回版本冲突。已受理的原单仍可只读查回。

平台响应至少包含 Work ID、Task ID（或任务列表）、状态和配置版本。MuMu 核对原部署、作品和版本，将自动交付关联到 `target_id + session_key` 及其有序切片，将手动单片关联到 `job_id + segment_index` 和选定账号。手动单片和本轮自动场次各预期一个任务。普通作品如有多个投稿单元或目标，按平台回执保留各任务编号。

MuMu 以 BLAKE2b-256 核对 YAML 原始字节版本，从健康接口取得随数据库保存的 `deployment_id`。预览、提交和查回都通过 `X-Upload-Platform-Deployment` 指定预期部署。0.2.0 在同库重启后保留该编号，部署不符时在处理请求前返回 `409 binding`。[MuMu 侧接口说明](../../../docs/控制台接口契约.md#mumu-向统一平台交单)

恢复规则：

- 首次派发前持久保存原部署、Work ID、配置版本、`Idempotency-Key` 和原请求。手动和自动共用[切片归属规则](#51-普通作品)，重复点击或重复收尾回到原安排。
- 超时、重启或丢回包后先在原部署按原 Key 只读查回。平台已受理时应返回保存的原结果，即使 YAML 后来移走或预览已经过期。MuMu 核对原作品、配置版本和任务编号后再关联。无法确认原部署时保留待核对。查回本身不能创建 Work 或 Task。
- 重放时沿用原 Key、原配置版本和原请求正文。同一 Key 换正文或配置版本时，平台拒绝重放。自动场次须仍允许交付。手动单须由用户选择「继续原安排」。
- 已取得 Task ID 后只查询原任务。
- 手动单断线后，若原部署按原 Key 返回 `404 submission_not_found`，MuMu 保留原安排。用户继续原安排后，若原部署又以 `409 preview_expired` 明确拒绝这次原请求，MuMu 再按原 Key 查回。仍返回 `404 submission_not_found` 才记录拒绝并开放重新预览。若查到回执，关联原任务。
- 重新预览沿用原安排的作品编号、录像和账号，表单带回原投稿字段。用户保留原内容时，MuMu 沿用同一份 YAML 和配置版本。取得新的 `preview_id` 后展示预览，用户再次点击「确认安排」时才保存新的请求正文和新 Key 并提交。重复确认沿用这次确认的 Key。
- 其他明确拒绝且确认未产生 Work 或 Task 的情况记录拒绝原因。用户修改配置时生成新的 YAML 版本，再次确认后用新 Key 提交。原部署离线、部署标识不符或受理结果仍不确定时，保留原请求与原 Key 待核对（`review`）。

关闭开关和自动派发通过同一场次的事务或锁确定先后，分别按以下情况处理。

- 关闭先发生且尚未派发时，停止本场自动交付，释放该自动安排占用的切片。收尾后的场次转 `only_record`，仍可由用户手动选片。
- 关闭时若提交已经发出或可能已发出，后续只读查回。即使暂时查不到，也保留原请求待核对。此时重放 POST 可能在关闭后才首次建单，因此禁止重放。
- 平台已受理时，以原 Task ID 关联，平台继续执行。

## 8. 本地数据与代码调整

改造后的本地记录包括以下内容。

- `recording_sessions` 保存场次事实、标题、收尾和素材证据，并关联稳定的作品 UUID、YAML 路径及版本。
- `posting_settings`：主播级自动投稿开关和模板设置。

- 场次与 Job/segment 的有序关联，以及手动与自动交付共同使用的切片归属记录。
- 每次正式交付绑定的原部署、Work ID、Task ID、Idempotency-Key、配置版本、派发情况和最近一次可信状态。

- `ArrangementStore` 不再作为通用上传任务状态机。

- 移除 MuMu 平台扫码登录、完整任务历史和人工核验。
- 保留录制场次自身的交付状态，但不能复制平台 Task 状态。

### 8.1 旧数据保留与历史任务查询

新数据格式按项目约定在独立的新数据目录初始化空库。旧 MuMu 调度库、安排库、原上传平台数据和录像原件原地保留，新版不迁移、覆盖或清理这些数据。[项目数据边界](../../../AGENTS.md#实施与验证)

正式切换前先停止旧入口接收新投稿，核对在途旧单。已取得 Task ID 的任务由原部署继续执行。回包不明时，使用原安排中保存的部署和 Work ID 查询作品下的任务，只关联唯一匹配的结果。仍无法判定的保留原编号和素材范围供人工核对，核清前禁止从新入口重投。

确需核对旧单时，可在原部署按原 Work ID 或 Task ID 只读查询。新版的历史查询和断网查回验收使用新版创建的任务，旧库和旧账号记录按原样保留。[dev6 原单查回方式](../../../docs/控制台接口契约.md#mumu-向-dev6-交单)

## 9. iframe 页面迁移

MuMu 主播页保留自动投稿开关、默认账号/分区模板入口和最近场次摘要。切片页显示素材、质量和整场归属，在可手动投递的行提供「安排上传」，在已有任务的行提供「查看任务」。手动预览和确认遵循[普通作品流程](#51-普通作品)。

账号添加与重新登录、账号列表、完整 Works/Tasks 页面，以及任务取消、重试和核验由上传平台提供。0.2.0 的内嵌页面使用以下路由。

- `/embed/accounts`
- `/embed/works`
- `/embed/tasks`
- `/embed/tasks/{task_id}`
- `/embed/works/{work_id}`

MuMu 创建任务后打开 Task ID。消息只传版本化业务 ID，不传凭据、二维码 token、Cookie、YAML 全文或任意文件路径。双方校验 origin、source、协议版本和消息类型；`postMessage` 不是授权机制。

内嵌入口仅在录制机的 `http://127.0.0.1:8000` 控制台启用，子页面来自 `http://127.0.0.1:8765`。从组网地址或其他端口访问时，上传入口提示到录制机本机打开。打开面板直接进入目标页，仅在添加或重新登录 B 站投稿账号时扫码。管理写操作的来源校验和防跨站请求由平台处理，CSP `frame-ancestors` 仅允许上述 MuMu 来源。

## 10. 页面职责

MuMu 保留：

- 主播列表和录制控制。
- 主播自动投稿开关、默认账号/分区模板。
- 场次交付摘要：只录、待交付、已受理、待核验。
- 切片列表、质量信息、「安排上传」和打开原上传任务。
- 上传平台不可用时明确提示，不阻塞录制和本地 YAML 保存。

MuMu 不保留完整 B 站账号管理、投稿参数编辑器、上传任务列表/详情状态机和远端核验工具。

## 11. 实施顺序

开发版已从切片页「安排上传」和自动场次收尾接入统一客户端。第 3 步复验与第 4 步日常切换均已完成，真实 B 站验收继续由第 12 节跟踪。

1. **完成 MuMu 端开发。** 将现有场次台账和切片清单接到 YAML 生成、预览、统一提交、按原请求号查回和任务关联。完成主播设置、手动确认、场次摘要、账号与任务的内嵌窗口、消息校验及平台离线提示。在开发版移除旧的两步派发和重复表单。
2. **在平台开发期间完成 MuMu 自测。** 用真实临时文件和隔离数据库运行上述代码。在测试中用模拟服务返回预览、任务号、冲突、超时或断线，用测试子页面验证 MuMu 的窗口和跳转。模拟服务只用于测试，开发版和正式版使用同一套客户端代码。
3. **修复手动单恢复，用同一个 0.2.0 包复验。** 在 MuMu 的原单恢复逻辑中，按第 7 节记录平台明确拒绝过期预览的结果，让切片页能从原安排重新预览。按第 12 节复验首次请求未受理和已受理但回执丢失两种情形，并核对配置版本冲突、任务快照及其余适用的隔离联调用例。[MuMu 原单恢复逻辑](../../../src/orchestrator/segment_uploads.py)
4. **联调通过后切换日常使用的版本。** 手动单恢复修复并通过复验后，按旧单处理规则核对仍在途的任务，再启用新版 MuMu。平台概览和定时任务由上传平台独立交付。真实扫码及 B 站投稿按第 12 节另行验收。[旧单处理规则](#81-旧数据保留与历史任务查询)

原 dev6 已在隔离环境验过两步交单、跨 Job 组单和丢回包查回，这些记录可作回归对照。统一提交和真实内嵌页面的联调单独记录。[dev6 本地验证记录](../../../docs/证据/验证/20261120-MuMu按场次交付dev6本地验证.md)

## 12. 测试与验收

**MuMu 客户端自测。** 直接检验本机文件、数据库、页面状态及实际发出的请求。对平台负责的校验和受理行为，用模拟回执检查 MuMu 如何处理。

- 标题有/无、同主播连续场次、改题、同场补查、异场标题隔离。
- 同 Job 多片、跨 Job 多片、跨 Job 同名文件、邻场隔离和顺序稳定。
- 自然下播、主动停录、设备掉线、主控重启、Worker 未收齐、未封口、身份未核实、录错房、短暂遮挡。
- 主播开关、账号不可用、MID 变化、部署切换、分区非法、私密能力不可用。
- YAML 重复键、未知字段、配置或素材越界、预览后修改。使用含冒号的场次键，在写文件前和写完未记账时分别模拟中断，重启后均复用同一 Work UUID 和目录。
- 手动预览后取消、刷新、重复确认，以及手动确认和整场冻结的两种先后顺序。相同单片意图只产生一个 Task，多片部分重合须指出冲突。
- 提交前断网、受理后丢回包、重复收尾、重启恢复、同 Key 不同正文或版本。模拟标记派发后请求未到平台，此时关闭自动投稿，随后只读查回，平台任务数保持为零。
- 用独立新库启动并记录本版本的 Work/Task。重启后从原切片进入同一任务，检查没有改写旧库或补交旧素材。
- 用测试子页面验证内嵌地址、按 ID 打开任务、刷新时重新取状态、消息来源校验，以及平台不可用时的提示。

**双项目联调。** 使用真实上传平台的联调部署和本版本新建的任务，从 MuMu 的正常入口走完以下场景。

1. 普通作品用已有 YAML 预览并提交。另选一片尚无 YAML 的录像，点击「安排上传」并预览，取消后核对平台任务数为零。重新打开并确认，重复点击只产生一单，Task Snapshot 与确认的版本一致。
2. 自动单片场次 → 独立 YAML → 自动提交 → Task ID 关联。
3. 跨 Job A1/A2/B1 → multipart YAML → 一个 Work、一个 Task，顺序一致。
4. 平台已受理但回包丢失 → 关闭自动投稿并重启 MuMu → 只读查回同一 Task，任务数仍为一。
5. 关闭自动投稿 → 录制继续，尚未派发的场次不创建任务。
6. 首次打开和刷新时直接进入平台账号页。用测试账号完成添加或重新登录，核对 MuMu 收到通知后刷新账号状态。
7. 平台异常 → MuMu 只显示平台可信摘要。
8. 上传平台未启动 → 录制、收尾和本地 YAML 保存不受阻。
9. 手动确认时模拟请求未到达平台，核对这段录像的任务数为零。使旧预览失效（可重启使用同一数据库的平台），从原切片选择「继续原安排」。按第 7 节确认原单未受理后，应能保持投稿内容不变重新预览。重新预览和取消时均为零单。再次预览并确认后，平台应恰有一个 Work 和一个 Task。重复确认、重启 MuMu 后从原切片再打开，仍是同一 Task，任务数保持为一。

## 13. 交付物与完成定义

交付物包括手动单片与自动场次的 YAML 生成、双路径契约、统一提交客户端、幂等恢复、场次与切片关联、iframe 集成、[旧数据保留与历史任务查询说明](#81-旧数据保留与历史任务查询)、自动化报告和真实 B 站验收记录。

- 所有正式投稿配置来自独立 `upload.yaml`。
