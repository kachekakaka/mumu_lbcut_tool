## 一、结论与目标

本次采用“按事件防止重复入账、按标记汇总展示、保留多条风险证据”的规则。不同事件即使标记名称和疑似开始时间相同，也不自动合并；界面统计的是标记记录条数，不能解释成异常发生次数。

实施目标：

1. 明确并验证已有事件去重边界，防止重复投递增加切片风险记录。
2. 统一存储、API、前端和任务／概览汇总的含义，消除“发生 N 次”和“异常起止区间”的误导。
3. 修复乱序事件使切片 `updated_at` 回退，以及已成功结束任务收到新风险后仍显示无告警完成的边界问题；区分正常回标与新增不完整切片，后者不能继续显示成功且收集完整。
4. 保留 Worker 已有的多次异常、跨切片风险回标和低帧率恢复迟滞行为。

## 四、拟定契约

### 4.1 投递去重与风险记录

去重仍在 `Store.record_event` 的事务入口完成，原始事件与风险投影必须同时成功或同时回滚。

| 输入情况 | 处理规则 |
| --- | --- |
| 同一任务、同一非空 `event_id` 重投 | 首次成功入账生效；后续投递不追加风险、不刷新时间、不修改任务状态 |
| 同一任务、不同 `event_id`，其他字段相同 | 保留两条记录；不能仅凭内容相同证明是重复投递 |
| 不同任务使用相同 `event_id` | 各自独立入账，不做跨任务去重 |
| 无编号输入，完整规范化 JSON 相同 | 沿用当前内容比较去重；对象字段顺序不同不影响结果 |
| 无编号输入，时间或其他字段改变 | 视为不同记录，不猜测是否同一次异常 |
| 同一编号携带不同内容 | 沿用首次成功入账生效的现状；不覆盖首条内容，也不在本次新增冲突修复协议 |

生产 Worker 应生成编号并在回放中保留编号；无编号路径只说明现存输入的处理边界，不新增兼容层。若生产方错误地为重投生成新编号，存储无法可靠识别，本次不以内容合并掩盖该问题。

风险记录以 `(job_id, segment_index)` 归属切片，不跨切片汇总去重。相同风险期间可以影响多个切片；同一切片也可以保留多个同名风险记录。重复事件在事务入口返回，不能因为后续重复接收而“修复”历史投影。

### 4.2 各层计数口径

| 层级 | 明确含义 |
| --- | --- |
| `segments.risk_json` | 已接受的质量风险事件列表，包含内部调查所需的原始字段；不截断、不按名称合并 |
| API `quality_flags` | 每条风险记录对应一项，继续仅投影 `flag`、`suspected_start_time`；允许内容相同的多个元素 |
| 前端每个标签的数量 | 当前切片中该 `flag` 的记录条数，不是异常次数、受影响切片数或投递次数 |
| `has_quality_flags` | 是否存在至少一条风险记录，未知名称也算风险 |
| 任务 `finished_with_warnings` | 成功结束但存在质量风险或既有收尾告警；不表示媒体文件损坏，本次迟到风险引起的状态提升不额外触发重试 |
| 概览 `segment_quality` | 每个符合时间窗口的切片一条质量告警，不按风险条数或标签数生成多条 |

API 不新增聚合计数，前端统一使用共享组件分组。原列表维持现有存储顺序，前端标签维持首次出现顺序，不将列表顺序当成异常时间顺序。未知标记原样显示；`null` 与字面字符串 `__null__` 必须是不同分组，避免当前占位键与未知名称碰撞。

### 4.3 时间含义与展示

- `suspected_start_time` 是风险疑似开始时间，可能早于当前切片，不能裁剪为切片开始时间。
- 同组最小／最大值分别叫“最早疑似开始”“最晚疑似开始”，不是异常的起止区间；不据此计算持续时长。
- `null` 不参与时间范围计算；数值 `0` 不能因为真假值判断而当作缺失。前端仅使用有限数值计算范围，其他值按时间未知展示，不影响记录条数。
- API 在响应模型校验前归一化每条 `suspected_start_time`：仅保留有限的整数或浮点数，明确排除布尔值；缺失、`null`、字符串（包括数字字符串）、容器和非有限数值统一投影为 `null`。不把未知疑似时间替换成接收时间、事件时间或切片时间。此规则仅作用于查询投影，不修改原始事件或 `risk_json`，不删除记录、不改变计数；前端检查作为额外防护，不能代替 API 处理。
- `timestamp` 是事件时间，写入风险投影时沿用当前规范化规则：有效有限数值保留，缺失、布尔值或无效数值回退到本次接收时间 `now`。不将疑似开始时间用于告警新鲜度。
- `updated_at` 取该切片已接受事件的最大规范化事件时间，保证不回退；它不是每次重放的接收时间。该约束适用于共用更新路径的开始、完成、中止和质量事件。
- `created_at`、`started_at`、`ended_at` 继续各自表达原来的生命周期时间，不用 `updated_at` 反向覆盖。

前端具体文案：

| 情况 | 标签 | 提示内容 |
| --- | --- | --- |
| 单条记录 | `低帧率` | `标记 1 条；疑似开始：…` |
| 多条且有效时间不同 | `低帧率 · 3 条` | `标记 3 条；最早疑似开始：…；最晚疑似开始：…` |
| 多条且有效时间相同 | `低帧率 · 3 条` | `标记 3 条；疑似开始：…` |
| 全部时间未知 | 按条数显示 | `标记 N 条；疑似开始时间未知` |
| 仅部分时间已知 | 按全部记录条数显示 | 已知时间照常显示，追加 `另有 M 条疑似开始时间未知` |

非空标记代码继续附在提示末尾，便于定位未知标记；无标记列表继续展示 `—`。不再使用“发生 N 次”“首次／最近发生”或“起止时间区间”。

## 五、实施设计

### 5.1 存储：时间单调与迟到风险

在 [storage.py](../../../src/orchestrator/storage.py) 的切片公共事件路径，将覆盖 `updated_at` 改为当前值与规范化 `stamp` 的最大值。新切片插入行为不变；重复事件仍在进入该路径前返回。终态冲突仍抛错并回滚整个事务，不借本次修改放宽状态一致性。

处理新的质量事件时，先在事务内读取任务和已有切片，再执行切片插入／更新，避免新建占位记录后无法区分“此前未登记”。原始事件、风险记录、切片时间和本次任务摘要更新仍须原子提交；失败则全部回滚。同编号重投在入口返回，不重复改变摘要或报告异常。

**正常回标与未结束任务：**

- 对 `pending/starting/running/stopping`，保留风险先到时建立占位切片的行为，最终状态交给原 `finish_job` 判断。`needs_reconcile` 仍属于待对账流程，允许事件补录，不由质量事件提前改成成功或失败。
- 对已经结束的任务，正常回标要求切片在本次事件前已登记、`started=1`，且状态为 `finished` 或 `aborted`。成功任务还须已有 `collection_complete=1`。
- 满足正常条件且任务为 `finished`、`exit_code=0` 时，仅提升为 `finished_with_warnings`；已经为 `finished_with_warnings`、`failed` 或 `cancelled` 时保持原状态。
- 正常回标不修改任务退出码、结束时间、停止原因、错误原因和 `collection_complete`。切片的文件路径、媒体信息和终态保持不变。

**结束任务的异常切片输入：**

这里的“已经结束”明确指 `finished/finished_with_warnings/failed/cancelled`。若收到风险时对应切片不存在、`started=0` 或尚未终结，则走完整性异常路径；成功状态却已有 `collection_complete=0` 也走此路径，不当作正常回标。

1. 保留原始事件与风险证据。未知切片沿用占位记录，不伪造开始／结束事件；已有未完成切片不伪造终态。风险仍可通过切片查询查看。
2. 在同一事务中将任务 `collection_complete` 置为 `0`。原状态是 `finished` 或 `finished_with_warnings` 时，改为 `failed`，退出码为原非零值或 `30`，使用现有 `event_collection_incomplete` 原因类别，并在详情中注明迟到质量事件的切片编号及未知／未开始／未终结／原完整性标记异常；原错误详情如有内容一并保留。此退出码是调度结果汇总，与现有收尾对完整性失败使用非零结果的规则一致，不改写 Worker 原始退出事件。
3. 原任务已经 `failed` 或 `cancelled` 时，保持原状态、退出码和错误原因，避免覆盖原始失败或取消结论；仅收紧完整性标记并保留新增风险证据。
4. 提交成功后记录带 `job_id`、`event_id`、`segment_index` 和异常类别的警告日志。成功任务转失败的原因通过现有任务详情展示；已失败／取消任务的附加原因通过警告日志及持久风险记录排查。该业务异常完成入账后正常返回，不能抛出导致调度队列卡住或停止其他 Worker 的异常；数据库写入失败仍按原有错误处理。
5. 已保留的未完成切片不会自动补齐，不因重放同一风险自动恢复任务成功。之后如另有开始／终态记录入账，也不自动将此次失败改回成功；本次不新增历史任务修复或重新结算入口。

**两条路径共同约束：**不重新调用 `finish_job`，不改写任务结束时间或停止原因，不修改实例占用、目标控制版本、抑制会话、重试时间和次数，不安排新重试、不转为占用实例的 `needs_reconcile`。尤其要验证原实例／目标已经被新任务使用时，旧任务的迟到事件不会影响新任务。任务计数及失败原因等只读汇总可以随旧任务结果变化，不把这种展示更新解释成新的调度动作。

### 5.2 查询：保持告警数量与时间窗口一致

在 [queries.py](../../../src/orchestrator/queries.py) 的 `segment_object` 中按 4.3 节归一化 `suspected_start_time`，保持每条风险对应一项和原列表顺序。切片列表与单片详情共用这一投影；不放宽 API 响应模型的非有限值限制，也不只在前端兜底。非法时间与有效时间混在同一分页时，整个响应应正常返回，非法时间项保留为 `null`。

按切片生成质量告警的规则如下：

1. 有风险记录才生成 `segment_quality`，空列表不能因测试时钟接近零而生成虚假告警。
2. 告警时间取风险记录中最大的规范化 `timestamp`；有效零值按零处理，不使用 `timestamp or updated_at` 替换。
3. 对记录中缺失或无效事件时间，保留以切片 `updated_at` 作为查询兜底的有限处理；正常新入账风险已由存储规范化。该处理不改写历史数据，不构成历史数据修复承诺。
4. 继续使用现有最近 24 小时下界过滤；对于具有规范化事件时间的风险，不因重复接收或较新的非风险事件让旧风险重新变成新告警。缺失有效时间的记录只能采用上一条兜底，不能承诺同等时间精度。切片候选预筛选与风险时间复核都保留，单调 `updated_at` 避免乱序旧事件漏掉近期风险。
5. 同一切片同时有质量风险和中止事件时，继续允许分别展示质量与中止两类告警；原有排序和分页规则保持不变。

对于改动前已被回退的历史 `updated_at`，不执行数据库扫描修补；本次保证修改后的事件处理不再制造回退。异常未来时间的校正也不在范围内。

### 5.3 前端：只解释标记记录

在 [QualityFlags.vue](../../../web/src/components/QualityFlags.vue) 实现第四节文案，分组键直接使用 `string | null`，避免字符串哨兵碰撞。记录条数与已知时间数量分别计算，时间未知不丢弃记录。使用原有时间格式化和标签映射，不增加另一套页面专用汇总逻辑。

### 跨 24 小时边界的固定时间用例

固定查询时钟为 `T = 1_800_000_000`，下界 `B = T - 86400`；所有测试均显式提供有效事件时间，避免与缺失时间兜底混在一起。通过真实 `Queries.overview` 的 SQL 候选筛选和风险时间复核断言，不只测时间取最大值的辅助逻辑。

1. **防止近期风险被旧事件隐藏（A7）：**先写 `B+10` 的质量风险，再以新的事件编号写 `B-10` 的旧风险；另用独立场景分别写入 `B-10` 的旧开始事件和符合既有终态一致性规则的旧终态事件。每种顺序都断言 `updated_at >= B+10`，概览保留恰好一条该片质量告警，告警时间仍为 `B+10`。新编号旧风险应保留为第二条记录，但不能覆盖新风险时间。
2. **防止旧风险被新活动刷新（A8）：**先写 `B-10` 的质量风险，随后在更晚接收时间重投同一事件，再写 `B+10` 的非风险切片事件。断言风险仍只有一条，切片 `updated_at` 已进入候选窗口，但概览没有该片质量告警。选用完成事件可避免中止告警干扰；若测试中止事件，则分别断言两类告警。
3. **精确边界（A9）：**分别用独立切片写入 `B-1`、`B`、`B+1` 的质量风险，断言前者排除、后两者包含，告警总数和分页排序一致；零值、空风险列表及缺失事件时间兜底使用独立用例。

### 异常输入与 API 验证要求

A17 通过存储入口在隔离库构造风险，再调用实际 HTTP 列表与单片详情；非有限数值等不是控制台写入请求，不以请求校验失败代替响应验证。检查解析后的原始值保留时，对 NaN 等使用对应类型判定，不依赖其相等比较。至少混入一条正常时间记录，证明异常项不会拖垮整页，也不会让正常项丢失或被归一化为空。

A18／A19 分别覆盖切片不存在、已有占位但未开始、已开始未终结三种情况，并额外覆盖已有终态但 `started=0` 的不完整记录。事务失败注入要覆盖风险写入后、任务摘要更新阶段，验证异常路径没有只落风险而仍保留成功完整摘要的半完成状态。

测试实现可合并相关场景，不为每行单独搭建框架。存储和 API 使用真实隔离 SQLite 与可控时钟；不要仅模拟查询返回值来证明落库或事务正确。

必要回归至少覆盖事件发射、流质量检测、调度集成、控制台 API、质量标记组件及任务身份风险刷新相关测试。前端提示测试应展开真实提示或检查组件接收到的完整提示内容，不只断言标签数字。

隔离联验至少展示：同一事件重投计数不变，不同事件同名同时间计为两条，无效疑似时间不导致列表请求失败，正常迟到回标显示告警完成，未知／未完成切片使原成功任务显示收集不完整失败，以及跨窗口旧事件不隐藏近期风险、窗口内非风险事件不刷新过期风险。仅构建通过不能代替这些功能断言。

## 九、主要取舍、风险与完成条件

- **记录条数不等于异常次数。** 当前事件不足以可靠还原每种风险的独立异常期间，保留证据并准确命名比猜测合并更可靠；以后若确需异常次数，应另行设计生产端期间语义。
- **风险列表仍可能增长。** 本次不做压缩、截断或历史清理，避免损失多次异常证据；没有容量证据时不引入新存储模型。
- **迟到事件分流处理。** 已登记终态切片只增加风险摘要；未知／未完成切片保留证据并明确收集不完整，原成功任务转为失败。保留未完成切片用于排查，不自动修复历史任务；不重新执行收尾或安排重试，避免影响已复用的实例与新任务。
- **时钟与历史数据边界仍存在。** 单调更新时间防止新处理中的回退，不修正未来时钟、不修补既有回退数据；缺失事件时间的查询兜底不能提供精确历史发生时间。
- **无需新增设备动作。** 本次不改 Worker 检测或设备交互，必要验收是隔离存储、API、回放和界面联验；没有新增实机录制不影响该范围的完成结论，也不能声称自然异常触发能力获得了新实机证明。

本方案无依赖外部服务或数据迁移的前置事项。待确认的是上述契约和实施范围；确认方案本身不视为已完成实现。只有相关代码、必要验收和文档移交均完成，才能关闭 T20；本轮方案交付不关闭 T20。
