## 1. 背景与目标

调度器在登录强阻断、设备离线、身份核验失败、主控重启和多次启动失败后都会停下，等人执行 `unblock` 或 `record`；Worker 也有“整场最多恢复 3 次”的上限。离线回放还表明，“主播违规整改中”这类平台提示页会被当成画面冻结，几分钟内反复重新定位，最终耗尽恢复次数、整场停录。

目标：

1. 主播在播期间，大部分故障由软件自己恢复，不再需要人工 `unblock` 或 `record`。
2. 区分“画面冻结”和“画面静止”，提示页、主播长时间不动不再打断录制。
3. 修正三个小缺陷：录制中设备离线时的退出码（K5）、心跳 `segment_elapsed_sec` 恒为 0（K6）、设置总时长时多出几秒尾片。
4. 在台式机上完成实机验证，并做两路同时录制（T4 缩为两路）。

## 2. 范围与非目标

**范围内**：调度器的失败处理、本场抑制、实例状态与重启对账；Worker 的恢复次数限制、冻结/静止判断、离线退出码、心跳字段与总时长截止；对应测试、CLI、运行说明、待办；台式机测试环境搭建与实机验证。

**非目标**：

- 不自动开关模拟器（含 MuMu 崩溃后的开机）。
- 不放宽严格身份核验，不登录、不清应用数据、不重置模拟器。
- 不新增或克隆模拟器实例；三路同录留待以后。
- 不做 T3（其他面板注入）、T5（6～8 小时长测），不处理 K1、K3。
- 不改开录前导航流程和遮挡关闭流程。

## 3. 实施路径与主要取舍

### 3.1 调度器：任务结果与重试规则

主播在播期间，任务失败后按退避重试：间隔从 5 秒起按次翻倍，最长 5 分钟，不设次数上限。任务进入 running（收到首个 `segment_started`）后把失败计数清零，长时间录制后的偶发故障从短间隔开始重试。删除 `max_attempts` 及 `--max-attempts` 参数。

| 结果 | 处理 |
| --- | --- |
| 人工 `stop` | 本场抑制；再次 `record` 或下一场解除（不变） |
| 目标移除、调度器确认下播 | 停止并不再开录（不变） |
| 9 目标无效 | 目标标记为“需要修正”，不再自动录任何场次，直到用户 `record` 或重新添加；状态中显示原因 |
| 0 且设置了总时长 | 正常完成，本场抑制（用户要求的有限时长录制） |
| 10 Worker 自报未开播 | 不抑制，按退避重试；是否下播只看调度器的两次确认 |
| 15 登录强阻断 | 实例先复位抖音（3.2），任务按退避重试 |
| 18 身份核验失败 | 按退避重试；核验不通过照样不开录 |
| 20 设备不可用 | 实例置为离线（3.3），任务按退避重试并可分配到其他空闲实例 |
| 其他（含 30） | 按退避重试 |
| 主控正常退出（`scheduler_shutdown`） | 不再抑制本场，重启后照常开录 |

取舍：持续失败会每 5 分钟占用一次实例，换来不漏录；失败原因在 `status` 和事件日志中可见（ADR 0015）。

### 3.2 登录强阻断后的实例复位

Worker 以 15 退出后，调度器在后台查询线程中对该实例执行：`am force-stop com.ss.android.ugc.aweme`，再启动抖音首页 `MainActivity`。不清数据、不登录。复位期间实例状态为 `resetting`，不分配任务；复位命令成功后回到 `idle`，ADB 不通则按离线处理。删除 `blocked` 状态、`InstancePool.unblock` 和 `unblock` 命令。

### 3.3 实例在线状态自动同步

现状：`InstancePool.refresh()` 只在主控启动和 `unblock` 时调用；`list_available_instances()` 把未开机的实例也报成可用；离线状态一旦写入就不会自动恢复。

做法：调度器每个扫描周期刷新一次实例列表。允许列表内的实例按 MuMu 报告的 `is_android_started` 判断：已启动且无任务的置为 `idle`，未启动或未发现的置为 `offline`（有任务占用的不改）。这样离线实例重新开机后自动可用，关机的实例也不会被派任务。

### 3.4 重启对账

主控启动时对上次遗留的活动任务：

- 关联进程已消失：重放 NDJSON、记录中断结果后，不再抑制本场，按退避重新开录（新任务、新目录）。
- 进程仍存活且 PID、创建时间、命令行 job_id 都证实属于本主控任务：新主控与它不在同一控制台，无法直接发送 Ctrl+Break。改为由 Worker 自己处理——Worker 写事件到 stdout 失败（主控已不在）时，按停止请求平滑封口并退出，事件继续写入 NDJSON 日志。新主控把这类任务置为“等待旧进程退出”，进程消失后按上一条续录；超过 120 秒仍未退出才转为人工对账。
- 归属无法确认：保持 `needs_reconcile`，不杀未知进程（不变）。

### 3.5 Worker 恢复次数

删除 `MAX_RECOVERY_RETRIES`（整场 3 次），只保留“5 分钟内最多 2 次”的滚动窗口；超过时以 `recovery_budget_exhausted`（30）退出，交给调度器退避。

### 3.6 画面冻结与画面静止（K4）

现状：看门狗只看画面中部变化值是否低于 0.003，低变化满 10/20/45 秒分别发出三级动作，三级在持续采集里都会重新定位。

做法：

- **画面冻结**：录像流分析确认“没有新帧但字节仍在流入”（现有 `no_new_frames_confirmed`），或文件停止增长。保留现有 10/20/45 秒分级与重新定位。
- **画面静止**：仍有新帧，但画面中部变化低于阈值。不再触发冻结分级：
  - 静止满 10 秒，给当前切片打 `segment_quality_warning`，`flag=static_picture`（同一段静止对每个切片只标一次，沿用低帧率的标记方式）；
  - 静止满 120 秒，且窗口状态探针确认仍在直播页，重新定位一次（原因 `static_picture_timeout`）；
  - 每段连续静止只重新定位一次。重新定位后仍静止的，继续录制并标记，直到画面恢复变化后才重新计时。
- 登录页判断（前台 Activity）不受影响。

取舍：真正的播放器卡顿（卡在加载动画上）要 2 分钟才处理，比现在晚；换来提示页和静止画面不中断录制。

### 3.7 录制中设备离线（K5）

Worker 在恢复（`recover`）开始时，以及重建采集失败时，用 `adb get-state` 检查设备。确认离线时以 20（`device_offline`）退出，不在 Worker 里等待设备回来。调度器按 3.1、3.3 处理。

### 3.8 心跳字段与总时长截止（K6、尾片）

- `segment_elapsed_sec`：当前切片已录秒数，等于采集会话已运行时间减去上一片封口点在录像时间轴上的位置，取整。
- 总时长：设置 `--total-duration` 时，交给封装 ffmpeg 用 `-t` 在录像时间轴上截止，最后一片恰好在总时长处封口。封装器按时截止退出时，Worker 视为正常完成：停止 scrcpy，字节桥写入失败不算采集故障。不再用 Worker 墙钟计时判断结束。

## 7. 风险与待确认事项

- 1 号实例若查不出启动失败原因，L5 无法进行；不为此重置或重建实例，L5 记为未测，T4 保留在待办。
- UU 通道传输约 0.65 KB/s，大文件和录像留在台式机，只回传摘要和日志片段；通道断开时测试进程在台式机后台继续运行。
- 台式机抖音的无登录状态尚未实机确认，以首次 L1 的导航与身份核验结果为准。
- 3.4 中“进程仍存活、属于本主控”的处理，由原定“新主控发停止信号”改为“Worker 发现主控断开后自行封口退出”，因为新主控无法向另一控制台的进程组发送 Ctrl+Break；效果相同。
- 画面静止阈值沿用 0.003；真正的播放器卡顿最长 2 分钟才处理。
- 在播期间不限次数重试，持续失败会长期占用实例，需要靠状态查看发现。
