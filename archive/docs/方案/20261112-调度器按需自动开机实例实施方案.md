## 问题陈述 (Problem Statement)

目前调度器虽然已经支持在控制台动态选择哪些 MuMu 实例「参与录播（已启用）」，并会在 Worker 启动阶段尝试调用 `MuMuClient.launch_player()`，但调度器的实例派发逻辑仍然严格要求实例处于 `idle`（Android 已启动）才会分配任务；所有尚未开机的 MuMu 实例一律被刷新为 `offline（android_not_started）`：

1. 操作者每次启动控制台或重启电脑后，如果忘记提前手动把已启用的模拟器全部开机，即使主播已开播、任务已进入排队队列，系统也会一直停留在 `pending`，无法自动开录；
2. 无人值守期间一旦发生模拟器渲染器崩溃（如已知问题 `K9`）或意外关闭导致实例回到未开机状态，即使主播仍在播，调度器也无法把模拟器重新拉起来继续录播。

---

## 解决方案 (Solution)

允许调度器在真实需要时自动按需拉起「已启用且未开机」的 MuMu 实例，同时保持职责清晰与资源可控：

1. **按需开机、只开不关**：仅当存在可立即执行的 `pending` 任务且当前没有可用的已启用 `idle` 槽位时，调度器才拉起未开机的已启用实例；开机就绪进入 `idle` 后保留热实例运行，不自动关机。
2. **后台串行开机 + `booting` 独立状态**：开机动作由调度器在后台独立执行，单机同时最多拉起 `1` 台实例，避免多开冷启动抢占宿主机资源或引发 `MuMuNxMain` 启动竞争；开机期间实例进入独立顶层状态 `booting`（「开机中」），任务留在 `pending` 等待就绪后再认领，不连累任务失败计数，也不影响已被腾空的其他实例先接走任务。
3. **冷却退避与统一停用开关**：只要实例保持「已启用」，无论是初始未开机、崩溃掉线还是人为关闭后再触发，均允许在冷却结束后按需拉起；单台连续开机失败按 `30s → 60s → 120s → 240s → 300s` 冷却退避并优先轮转其他未冷却实例；人工手动开机或在控制台重设启用状态时立即清零冷却。

## 用户故事 (User Stories)

1. 作为录播操作者，我希望在无直播时段打开控制台并启用 2 个实例时，系统不要立刻把全部模拟器白白开机空转，以便平时节省宿主机 CPU、显存与内存。
2. 作为录播操作者，当我关注的重点主播开播（或我手动点击立即开录）、而当前没有已开机的空闲实例时，我希望调度器自动拉起一台已启用的未开机模拟器并在就绪后立即接单开录，以便真正实现无人值守冷启动开播录制。
3. 作为录播操作者，我希望调度器优先复用已经开机且空闲的实例，只有空闲实例不够用时才去拉起关机实例，以便减少不必要的启动等待时间。
4. 作为录播操作者，当有多个排队任务且多台已启用实例都关着时，我希望调度器一台接一台错峰拉起它们，以便避免多台模拟器同时冷启动把电脑拖卡死或触发主程序连接失败（`K13`）。
5. 作为录播操作者，当我停用某台实例（`enabled=false`）用于平时手动测试其他用途时，我希望调度器绝不会擅自把它自动开机，以便保留我手动模拟器的控制权。
6. 作为录播操作者，当某台已启用模拟器因为驱动崩溃（`K9`）或误关闭掉线、而此时仍有主播在播需要录播时，我希望调度器在刷新确认未开机后自动再次拉起它续录；若某台模拟器因故障反复拉不起来，能退避冷却并优先尝试另一台可用实例，不会死循环狂刷。
7. 作为录播操作者，我希望在网页控制台总览和「实例」页清楚看到实例处于「开机中（`booting`）」，并且在开机期间不允许误点停用该实例，以便明确区分“完全未开机离线”与“系统正在拉起开机”。
8. 作为录播操作者，我希望录播结束或主播下播后，调度器不要自动把我刚用过的模拟器关机，以便下场开播热接或我随时切回去查看画面。

## 实现决策 (Implementation Decisions)

### 1. 领域模型与持久化变更（内部开发阶段直接演化表结构，不做旧库迁移兼容）

- **实例状态与冷却持久化**：
  - 在实例状态模型及数据库 `instances` 表状态取值中新增 `booting`（与 `idle`、`busy`、`resetting`、`offline`、`reconcile` 并列）。
  - 在 `instances` 表新增开机退避字段 `boot_attempts`（默认 `0`）与 `boot_retry_at`（默认 `0`），用于持久化单台实例的连续开机失败次数与下次允许自动开机时间，避免进程短暂重启后立刻对已知坏实例高频重试，并使“重新启用/手动开机清零冷却”可追踪。
  - **初始化清理残留 `booting`**：调度器启动构造阶段调用首次实例同步时，若数据库因上次非正常退出残留 `status='booting'`（当时并无后台开机执行），首次同步将其视为非占用陈旧状态，直接按本次真实探测结果覆写为 `idle`（已开机）或 `offline`（未开机）。
- **冷却退避策略**：
  - 单台开机失败退避按 `30` 秒起翻倍、上限 `300` 秒计算：`30s → 60s → 120s → 240s → 300s`。
  - 当外部手动开机并被周期扫描探测到在线（`idle`）、本轮自动开机成功，或使用者在控制台通过控制命令提交实例启用状态变更时，重置 `boot_attempts = 0`、`boot_retry_at = 0`（重新启用同时清除旧的 `launch_failed` 原因以便立即可试）。
  - 带相同 `--instances` 重启不清零已启用实例的冷却；启动预设仅在实例由未启用变为启用时清零。

### 2. 实例池能力扩展与调度器开机闭环

- **实例池开机入口**：
  - 在调度器实例池模块新增 `boot_instance(vmindex: int, stop_event=None) -> bool` 方法，统一封装并复用 `MuMuClient.launch_player(vmindex, stop_event=stop_event)`（含拉起主程序、受理重试与 Android 就绪轮询）。
  - 后台入口接收停服取消信号；MuMu 命令单次硬超时最多 `10` 秒，开机流程使用单调时钟整体截止时间（默认最多 `120` 秒，含主程序准备、受理重试与 Android 等待），每次调用不能超过剩余预算。等待可取消，停服后不继续发起下一次重试，不关闭已经启动的模拟器。
  - `Scheduler.close()` 在释放主控锁前等待已提交的开机任务结束并收取结果。未完成开机被停服中断时记录 `offline / boot_interrupted`，保留原退避次数与时间；已成功的仍记为 `idle`。重启首先按实际实例状态重新探测，不把中断算成设备开机失败。
  - Worker 启动流程中的 `launch_player` 保持幂等兜底（实例已开机时直接快速返回成功），确保独立运行 Worker CLI 的既有能力不受破坏。
- **可开机条件与严格准入边界**：
  - 调度器每个 `tick` 先完成既有状态收取与任务派发（优先命中 `idle` 槽位），再检查是否需要触发按需开机，必须同时满足以下条件：
    1. 调度器未处于关闭流程（非 `_shutdown`）；
    2. 存在至少一个**具备立即派发资格**的 `pending` 任务（目标当前 `observed_status == 'live'` 且已过目标退避时间 `retry_at <= now`，与任务派发条件一致）；
    3. 当前**不存在**任何可立即派发的 `enabled=1 AND status='idle' AND job_id IS NULL` 槽位；
    4. 当前**没有**正在执行后台开机的实例（全局开机并发上限严格为 `1`）；
    5. 存在候选实例满足：`enabled=1`、`status='offline'`、`job_id IS NULL`、`boot_retry_at <= now`，且其离线原因为“已探测未开机”（`android_not_started`）或“此前开机失败冷却到期”（`launch_failed`），明确排除 `not_discovered`、`reset_failed` 与未知原因。
  - **退出口 20 刚掉线场景衔接**：当 Worker 因设备不可用退出码 `20` 结束任务把实例标为 `offline（原因非 android_not_started）` 时，调度器主动触发一次及时的实例探测刷新，由 `MuMuManager` 查清到底是临时 ADB 抖动（直接回 `idle`）还是模拟器真的已关闭/崩溃（更新为 `android_not_started` 后按需重新拉起），避免误对仍在开机的异常端口发 `launch`。
- **选槽优先级与并发互斥**：
  - 满足候选条件的多台离线实例按 `(boot_attempts ASC, vmindex ASC)` 排序选择第一台，既保证全部健康时按编号顺序（小号优先）开机，又能在某台曾经开机失败后优先轮转到健康未失败过的备用实例。
  - 选中后先通过数据库事务将实例原子更新为 `status='booting', reason='booting', updated_at=now`，再向查询线程池提交后台开机任务；仅允许单次唯一在飞开机任务。
- **同步覆写与停用保护**：
  - 实例定期刷新 `sync_instances` 在常规运行期保护 `booting`；主控重启后的首次初始化同步允许清理异常退出遗留的 `booting`。正常停服必须先结束旧后台开机调用，再释放主控锁，避免两个主控的开机调用重叠。
  - 调度器收尾方法收到开机完成结果后：成功则将处于 `booting` 的实例置为 `idle`（清零原因与退避计数），下轮立即正常派发 `pending` 任务；失败则累加 `boot_attempts`、设置 `boot_retry_at` 并置回 `offline（reason='launch_failed'）`，任务留在 `pending` 不受惩罚。
  - 若任务在数十秒开机等待途中被手动停止或主播下播取消，已开始的后台开机流程自然跑完进入 `idle`（不强杀开机进程，遵循不自动关机策略）。
  - 在控制事务校验与停用保护中，把 `booting` 与 `resetting` 同等视为活跃忙碌态，拒绝直接停用（返回业务错误 `instance_busy`，提示“实例正在开机中，请稍后再停用”）。

### 3. HTTP 接口契约与控制台前端适配

- **后端查询与契约扩展**：
  - `GET /api/instances` 查询筛选参数 `status` 新增合法枚举值 `booting`；实例对象允许返回 `status="booting"` 与结构化原因 `booting`、`launch_failed`。
  - `GET /api/overview` 返回的 `instance_counts` 固定字典键新增 `booting`；总览口径保持为已启用及 `reconcile` 实例。
- **前端界面适配**：
  - **标签与原因映射**：新增实例状态 `booting -> 开机中`（`warning` 样式标签），新增实例原因码 `booting -> 正在自动开机`、`launch_failed -> 自动开机失败（冷却重试中）`。
  - **停用保护提示**：实例页对处于 `booting` 的已启用实例禁用「参与录播」开关，悬停提示“实例正在开机中，请稍后再停用”。
  - **总览与筛选**：总览页「空闲 / 离线实例」统计卡片下方在 `counts.booting > 0` 时展示辅助状态 `开机中 N`（与 `待对账` 展示位置对齐）；实例页状态筛选下拉复用状态映射表自动支持按「开机中」筛选，前端 Mock 数据与单测同步补全。

### 4. 文档与实施步骤依赖

- **实施顺序**：
  1. **步骤 1（领域状态、持久化与调度器闭环）**：扩展实例枚举、数据库表字段与开机事务、实例池开机封装、`Scheduler` 串行按需开机/冷却轮转/退出码 20 刷新与初始化清理逻辑。
  2. **步骤 2（HTTP 接口与契约）**：放行 `booting` 筛选与总览计数、`reason` 说明与接口验证。
  3. **步骤 3（前端界面与构建）**：补齐状态映射、停用保护、总览辅助计数、前端单测并重建静态产物。
  4. **步骤 4（契约/文档同步与验证归档）**：更新 `控制台接口契约.md`、`最小调度运行说明.md`、`docs/待办.md`（移出已满足的 `T8` 规格确认项并在实机接录后收口）与 `ADR 0019` 状态。

## 测试决策 (Testing Decisions)

2026-11-12 审查修正的回归范围与结果见[验证记录](../../../docs/证据/验证/20261112-实例控制与按需开机审查修正验证.md)，实机冷启动接录仍保留在 T8。

- **良好测试标准**：只通过公开接口与外部行为边界断言系统结果（SQLite 持久化状态、HTTP 查询与错误码、任务是否被认领/拉起、冷却期是否避开坏机与轮转他机、界面标签/禁用态/参数传递），不测试私有辅助方法内部调用次序或 SQL 拼接细节。
- **测试边界（Seams）—— 复用现有两层高层边界，不新建额外测试替身框架**：
  1. **后端调度与控制台单一高层集成边界**：沿用现有集成测试与控制台 HTTP 测试边界（`FastAPI TestClient` + 真实 SQLite `Store` + `Scheduler.tick()` + 模拟 `Clock`，仅在 `InstancePool` 实例探测/开机、`RoomResolver` 与 `Worker` 子进程替身处做边界替换）。覆盖场景：
     - 有 `pending` 任务且全已启用实例处于 `offline（android_not_started）` 时触发开机、实例先入 `booting`、期间任务保持 `pending` 且不递增 `attempts`；就绪后立即派发并热复用不关机；
     - 存在 `idle` 槽位时不触发额外开机；仅未启用或 `not_discovered` 实例存在时不触发开机；
     - 多任务多离线实例并发场景严格串行（每次仅 1 台处于 `booting`）；
     - 同步刷新不覆盖正在 `booting` 的实例；若任务在开机途被取消，实例仍正常完成进入 `idle`；若程序异常重启遗留 `booting` 状态，初始化同步自动纠偏；
     - 开机失败进入冷却退避（30s→60s→…300s 封顶），冷却期轮转另一台健康离线实例；手动开机成功或重新启用实例后冷却清零；
     - 带同一启动预设重启仍保留开机冷却；停服中断开机后不再发命令、后台调用退出前主控锁不可重取；单次命令超时与整体截止时间均有效；失败扫描不改写既有实例；旧格式数据库被拒绝且内容不变；
     - `booting` 期间拒绝停用实例（409 `instance_busy`）、`GET /api/instances?status=booting` 与 `GET /api/overview` `instance_counts.booting` 口径准确。
  2. **前端单测边界**：沿用现有前端测试边界（静态辅助函数断言与组件/Mock 请求测试），覆盖 `booting` / `launch_failed` 中文标签、停用保护文案、总览 `booting` 展示以及实例状态筛选传参，并执行完整测试与生产构建检查。
  3. **实机本地验收**：在本机真实连接 MuMu 模拟器（在关闭状态且无 `--instances` 或仅在界面启用一台/两台未开机实例下），提交真实直播或测试开录任务，实测调度器拉起 `MuMuNxMain.exe`、进入 `booting`、等待 Android 就绪并自动启动 Worker 开始录制切片，确认任务结束后模拟器保持运行不自动关闭。
- **项目既有测试参考**：调度生命周期与故障恢复集成测试模式、控制台 HTTP 与命令幂等测试模式、以及现有实例启停与前端组件单测。

## 范围外说明 (Out of Scope)

- **不做空闲超时自动关机**：已明确本阶段只自动开机、不自动关闭闲置模拟器；若需释放闲置抖音资源，留待后续独立评估待办 `T10`（关闭抖音进程）。
- **不做旧运行数据库迁移兼容**：本次数据库格式版本为 `3`；旧版本在初始化时明确拒绝并提示使用新的独立数据目录，不覆盖或迁移旧库。
- **不将跨设备实机测试（`T6`）、三路并发（`T4`）、外部上传或切片打开目录（`T9`）并入本次实施**。

## 补充说明 (Further Notes)

- 实际实施前需留意已知问题 `K13`（冷启动 `MuMuNxMain.exe` 约 5 秒内可能收到 `-503`）及部分机器上 UU 远程可能自动拉起主程序的现场现象：因为本方案严格串行限制单机最多同时开机 `1` 台并复用 `MuMuClient.launch_player()` 的 `45` 秒重试窗口，可显著降低冷启动竞争概率，但仍需在实机冷启动验收中重点核查首台拉起耗时与成功率。
- 如方案确认实施完成后需打包验证，再按需生成新的独立自用测试包，不覆盖既有打包目录与运行库。
