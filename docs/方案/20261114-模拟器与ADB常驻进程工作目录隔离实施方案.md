## 1. 背景与目标

Windows 下控制台退出后，便携包或临时源码目录仍可能无法移动、删除。既有 K14 取证记录指出，PID 21404、30572 对应的 MuMu 常驻进程继承了调用方目录，并持有 `CurrentDirectory.Handle`；涉及 `MuMuManager.exe` 经 `nemu-api.dll` 拉起 `MuMuNxMain.exe --from-oem` 的路径。该历史结论由 K14 承接，本轮未重新进行实机取证，实施时需补充可追溯的前后对照材料。

当前 `_run_manager` 没有传入 `cwd`。直接 ADB 调用及 scrcpy 间接启动 ADB 的路径也可能把运行包目录传给常驻服务，须一并覆盖。ADB 分支目前属于需要验证的风险路径，不能把 MuMu 的取证直接当作所有 ADB 分支的实测结果。

目标是在控制台、Worker 和本次采集子进程正常退出后，让本次新启动的外部常驻进程不再因继承 CWD 而占用测试包目录；不改变录像、数据库、事件日志和截图的预期位置。Windows 当前目录占用及多线程下全局切换目录的风险见[微软说明](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-setcurrentdirectory)。

## 2. 选择与边界

1. **逐个子进程显式传入 `cwd`**：MuMu 管理命令使用已解析的管理程序父目录；直接 ADB 命令使用已解析的 ADB 父目录。当前默认探测路径是 MuMu 的 `nx_main`，不硬编码 `shell` 或某台机器的安装位置。
2. **覆盖 scrcpy 的间接 ADB 启动**：scrcpy 会发出 `adb start-server`（[上游实现](https://github.com/Genymobile/scrcpy/blob/master/app/src/adb/adb.c)）。它的启动工作目录也使用外部 MuMu ADB 所在目录；可执行文件、`ADB` 环境变量、server 资源及本地输出须使用确定的路径，并验证打包布局下的资源查找。仅修改 Python 直接执行 adb 的地方不足以满足目标。
3. **不修改全局目录，也不改变通用执行器默认行为**：禁止 `os.chdir()`；`executor.run_command` 已支持 `cwd`，由 ADB 业务调用端传参，不增加 `AdbExecutor` 或让所有外部命令默认进入 ADB 目录。
4. **先规范路径，再切换子进程目录**：在构造或配置边界把外部程序路径转换为绝对 `Path`，验证文件和父目录存在。`exists()` 本身不保证绝对路径。截图 `pull`、MVP 录像输出及其他受影响的本地文件参数须按调用前基准解析，不能在新的 CWD 下重新解释相对路径。
5. **只影响后续启动**：已有 MuMu/ADB 进程不会因为新调用带了 `cwd` 就更换其当前目录。不得用强杀 MuMu、`adb kill-server` 或重启共享服务的方式自动消除历史占用。
6. **有限承诺**：项目输出路径保持原有含义；第三方程序是否自行生成缓存或重新切换目录须实机观察，不承诺“绝对没有额外文件”或“任何情况下退出即可删除”。

## 3. 实施清单（历史记录）

> [!NOTE]
> 本清单所列核心改动已全部实施并完成双端自动化测试与实机验收。
> **关键边界说明**：
> 1. **旧常驻进程不会自动迁移 CWD**：Windows 系统内核为子进程分配的 `CurrentDirectory.Handle` 一旦在进程创建时继承确定，即无法被外部或调用端在运行时修改。实施前已在运行的或由外部拉起的旧常驻进程（如 `MuMuNxMain.exe`、旧 `adb.exe`）不会自动迁移其工作目录；必须在旧进程退出后，由本工具新拉起的进程才会生效隔离。
> 2. **禁止静默回退**：所有启动入口（包括 `StreamRecorder` 与 `ContinuousPipeline`）均强制使用绝对路径与明确工作目录；Windows 环境下若 ADB 路径缺失或无效，直接报错拒绝启动，严禁任何形式的静默回退（如退回到父进程默认 CWD）导致工作区再次被锁定。

## 4. 自动化验证

- 在 `subprocess.run/Popen` 或既有命令执行边界捕获参数；覆盖上述所有直接和间接启动入口，而非只测 `_run_manager`。
- 覆盖 ADB 初次调用、重连、重试、设备在线探测、截图拉取及收尾；scrcpy 正式管线与 MVP 入口都要覆盖。
- 使用含空格、中文的测试路径及相对路径输入，断言最终可执行文件、输出、环境变量路径和 `cwd` 的含义不变；验证父 Python 进程 CWD 未变。
- 验证缺失路径会明确失败；保持单设备 serial、停止、超时和异常传播语义，不修改通用执行器的默认目录。
- 执行相关测试和 Python 全量回归，实际数量和结果写入验证记录，不把固定的历史测试数量作为验收标准。
- 参数测试只能证明调用配置，不能据此关闭 K14。

## 5. 实机验收与环境恢复

1. 先通过 SSH 或 UU 只读核对实例、MuMu、ADB、控制台及其他录制进程的占用，记录 PID、命令行、父子关系和可获取的 CWD/目录句柄。台式机文件仅建于 `D:\mumu_test`；不影响 `D:\lb` 录制，不启动笔记本实例 3。
2. 在新的独立测试副本及仓外输出目录运行。仅在已确认空闲的实例 0/1 上验证按需开机、真实 Worker 录制、正常停止和收尾；抖音保持游客状态，核验 room_id + UID。确认切片、数据库、日志、截图仍在预期位置。
3. 覆盖“外部常驻进程本轮新启动”和“复用已有进程”两种条件。ADB 自动启动分支只在没有其他任务依赖服务的条件下测；若已有共享 ADB 正在使用，保留不动，将该分支标为待验，不能为造条件执行 `adb kill-server`。
4. 控制台、Worker 和采集进程退出后，保持本轮新启动的 MuMu/ADB 常驻进程存活，检查它们是否仍持有测试副本的目录句柄。从副本之外对该副本做一次可逆重命名并恢复；先验证两个绝对路径均在 `D:\mumu_test` 内且目标不存在。不删除原包、录像或证据，不把停止常驻进程后重命名成功算作隔离通过。
5. 若重命名失败，保留错误及句柄持有者证据，区分旧进程、终端 CWD、仍未退出的 Worker、加载的程序文件和新的继承缺口；不能统一归因于 ADB 或通过杀其他任务进程掩盖问题。
6. 完成观察后只关闭本次启动且确认未被其他任务接管的服务和实例，恢复测试前状态。共享进程保持不动；记录恢复结果及无法安全恢复的项目。

验收记录需包含受测代码版本、安装布局、启动方式、各分支的真实/合成/未验分类、前后句柄证据、重命名结果、媒体与数据位置检查及环境恢复情况。代码回归和可执行的实机分支通过后，仍有关键分支未验则保持“待验证”，K14 不关闭。

## 6. 非目标与风险

- 不更改录制算法、FFmpeg 固定版本、调度生命周期或文件存放约定，不迁移旧数据。
- 不修改已运行进程的 CWD，不注入、不强杀用户进程，不主动重启共享 ADB。
- 不保证解除所有 Windows 文件占用；本方案仅处理本项目启动路径的 CWD 继承问题。
- 外部程序可能自行改变目录或写入缓存、打包布局可能影响 scrcpy 资源查找，这些必须由实机结果确认。
