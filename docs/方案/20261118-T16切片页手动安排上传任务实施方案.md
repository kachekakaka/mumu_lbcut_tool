# T16 首轮实施方案：从切片页手动安排上传任务

- 创建及最后更新于 2026-11-18。首轮手动安排已实现，状态为待现场验证。用户于 2026-11-18 授权实施首轮手动安排及本方案的故障恢复验收。隔离环境从实际切片页安排任务并查回原单，现场真实 B 站投稿仍按第六节由用户确认。实施与查询证据见[验证记录](../证据/验证/20261118-T16切片页手动安排上传验证.md)。
- 用户已确认上传模块能向 B 站投稿。本轮验收对象是 mumu 能否把用户选中的一片交给指定部署，取得对应任务，并在重复点击、超时和重启后找回同一单。
- 首轮交付一个本机手动入口，一次确认对应一个切片、一个 Bilibili 账号、一份单 P 投稿。原 T16 的逐片自动投递、整场聚合和显式再投稿留作后续阶段，首轮验收后应分别记录，不能据此关闭整个 T16。[原交付约定](../adr/0010-orchestrator-architecture-and-delivery-contract.md) · [待办](../待办.md)

## 一、使用流程

1. 用户在录制机本机打开「切片」。可安排的行显示「安排上传」；已有投递的行优先显示当前进度和「查看任务」。保持原切片状态和质量标记可见，上传状态单列。
2. 点开弹窗只读取资料。展示主播、场次、切片序号、正式文件名、时长和质量提示；从绑定部署读取可用账号供选择。预填可编辑标题，填写标签、分区、版权及发布方式，可填简介。转载须填写来源，自制不填来源；发布方式只选实际部署支持的值。打开或关闭弹窗均不创建任务。
3. 用户核对部署、账号昵称/MID、文件、投稿信息和可见范围，点击「确认安排」。确认须携带后端在打开时签发的上下文，绑定部署、切片快照和本地单据版本。后端复核当前部署及账号，切换部署后旧弹窗失效，即使两边有同一个账号 ID 也不能下单。弹窗说明确认后 Worker 可能立即执行。页面先显示「已保存安排」；得到 Core 任务编号后才显示实际状态。
4. 关闭弹窗、刷新、换标签页或重启控制台后，从原切片行打开同一记录。详情展示目标账号、最近一次已确认的任务状态、查询时间、任务编号及 Core 已返回的稿件编号。服务暂不可达时保留上次结果并标明失联。首轮多账号按账号分别列单；有意选择另一账号时另行确认。

## 二、把一条切片变成一项任务

| 环节 | 实施规则 |
| --- | --- |
| 选文件 | 页面只传 job_id 和 segment_index。后端按复合主键读取已开始且状态为 finished 的切片，取正式 file_path，核对其位于配置的输出根内、是可读的非空普通文件。started、aborted、临时文件、越界路径、缺文件均不能安排。is_final 不是单片准入条件。按当前记录展示质量告警，有告警由用户明确确认；确认时若文件或告警已变化，要求重新核对。 |
| 定根目录 | 使用正式文件所在目录作为 directory，文件名作为视频相对路径。比如同目录有 000001、000002 两段，只列本次选择的那一段。Core 和 Worker 须在能读到该本机目录的部署中运行。250 的切片应交给能看到 250 原文件的服务。保留本地录像，无需搬运或扫描邻近文件。 |
| 组作品 | 为这单生成并保存一个 work UUID，清单固定一个视频逻辑 ID、一个上传单元逻辑 ID、independent 模式和一个启用目标。账号取 Core ID 或对应 reference，显示名仅供核对。提交前冻结目录、清单及执行参数，另记文件大小与修改时间供变化提示。首轮采用一次明确的立即提交。 |
| 登记 | mumu 后端用登记专用 Key 调用 POST /api/v1/works，正文为 directory 和 manifest，核对返回的 work_id。登记成功只进入「已登记，待取得任务」阶段。 |
| 提交 | 用另一个固定 Key 调用 POST /api/v1/works/{work_id}/submit，显式传入同一目录、清单和固定的执行参数。这样同目录多片无需轮流写 upload.yaml。首轮弹窗展示 mumu 冻结的清单；Core 的 preview 接口会重读磁盘 YAML，不作为此路径的前置。 |
| 关联 | 核对响应 work_id、唯一任务及其单元、视频、账号与原快照匹配。created 为真或假均可关联返回的当前 task_id。零条、多条或身份冲突进入「待核对」，保留原单，不任取第一条。 |

切片落库与迟到风险见[事件存储](../../src/orchestrator/storage.py)。Core 的字段以 [OpenAPI](../../../fileUploadPlatform/schemas/openapi.json) 和[投稿配置说明](../../../fileUploadPlatform/docs/operations/bilibili.md)为准，登记、去重与提交的实际行为见 [Core 服务](../../../fileUploadPlatform/src/upload_platform/application/service.py)。

## 三、调用边界与本地记录

- mumu 后端通过固定 loopback 地址和固定路由调用已核实归属的普通投稿部署。复用现有运行层的进程、端口和目录核验，确认录制输出可访问且账号属于该部署。API 就绪、扫码能力、投稿能力、上传 Worker 是否在线分别显示。Worker 离线时如 Core 已接单，显示「已排队，等待 Worker」，重新连接只查询原任务。
- 现有 gui-bridge-v1 被 Core 限定在扫码路由。投稿使用单独的受信任本机后端客户端，按现行契约构造 cli-v1、JSON 和幂等请求头；仅开放登记、提交、账号摘要、健康检查和限定的任务查询。浏览器只访问 mumu。若目标部署对接身份或能力与契约不同，显示具体缺口，交由上传项目确认；不改外部仓库、开启任意代理或借用 B18 专用名额。[Core 来源限制](../../../fileUploadPlatform/src/upload_platform/api/app.py)
- 投稿写操作及账号、稿件详情沿用本机账号页的真实对端、Host、来源和短期凭证检查。局域网用户仍能查看现有录制切片。公共切片列表不附账号或投稿详情，本机页面通过受保护接口按当前页切片批量取投递摘要。部署未核实时仍能查看本地历史，不允许向另一部署重放。
- 在 mumu 数据目录单独建立投递 SQLite，由 mumu 维护。首次启动不改已有调度库或 Core 库。保存安排编号、切片主键、部署身份、账号 ID、冻结的请求内容、两个 Core Key、工作阶段、task_id、最近可靠状态和时间。浏览器刷新后按切片找记录即可，不靠内存保存唯一凭据。只保存必要、安全的结果字段；不保存 Cookie、登录材料、原始异常或完整 Core 回包。

## 四、如何保证一次确认只安排一单

**先在本地事务中保存安排，再向 Core 发请求。** 同一 mumu 数据目录内，以「切片主键＋平台＋目标账号＋绑定部署」建立唯一约束。两个标签页即使用不同页面请求编号，也只能插入一条业务记录。并发事务中的另一方读取已存在的安排。完全相同的请求返回原记录；参数不同则展示原单与冲突，不覆盖第一次确认的内容。切换部署时保留旧单并在原行显示；已有单的切片不因配置切换自动产生新单。

页面每次确认带一个 UUID，后端绑定其提交参数；同号不同参数拒绝。工作编号、视频/单元编号、登记 Key、提交 Key 均在首次事务内固定。每次发送前持久标记当前步骤「可能已发送」，用短事务按步骤领取有到期时间的派发权并增加代次，再在事务外做有界网络请求。正常结束、超时和协程退出只释放自己持有的代次；进程退出或处理者失去响应后可在派发权到期时接手，即使原进程还活着。迟到回包按步骤、代次和派发权条件写回，不能覆盖已关联任务或更新的查询结果。

| 中断位置 | 恢复后的行为 |
| --- | --- |
| 用户点了确认，浏览器没收到 mumu 回包 | 按切片和账号查询原单。已经保存就展示该单；没有记录时用户可用原请求再确认，本地唯一约束处理迟到的首次请求。 |
| 本地已保存，登记未得可靠回包 | 显示「登记待确认」。用户点「继续原安排」才用原登记 Key 和清单重放。确认 work_id 后再进入提交。 |
| 登记已确认，提交未发或回包丢失 | 只继续提交步骤。已可能发送且没有 task_id 时先 GET 原 work_id 的所有任务分页，核对单元、视频和账号，唯一匹配才关联。分页失败、结果冲突或多条匹配时停在待核对。查完没有匹配，仅在用户点击继续且原文件仍符合快照时才能用原 Key 和正文重放；空列表不能证明原提交未生效。 |
| 已取得 task_id，之后网络、页面或 mumu 中断 | 只 GET 原 task_id。刷新页面、凭证续领和后台轮询都不重新 POST。若单任务查询 404、部署身份变化或记录冲突，保留关联，提示核对部署。 |
| 文件、参数或目标账号改变 | 首次发送前能明确证明未派发时可回到编辑。若已可能发送，先核对原步骤，不能以新文件、新 Key 或另一账号替代重放。若原文件已变，允许只读查回既有任务；一旦重放可能首次执行且文件已变，则阻止继续并提示核对。 |
| Core 拒绝或远端结果不确定 | 只有首次派发收到 Core 契约明确保证未生效的拒绝，或能证明写请求从未派发，才允许显式修订。修订保留旧快照和原单号，按事务提升版本，新的登记和提交各使用本次明确确认的正文及新 Key，旧弹窗失效。此前有超时、服务端异常、无法解析响应或进程中断时，后续重放被拒绝仍保留待确认。拿到原提交回执的 task_id 后立刻 GET 该任务的最新状态。UNCERTAIN 保留 task_id，交由上传模块核验。 |

后台启动只恢复本地索引和只读查询。对可能首次产生投稿的步骤，页面提供「继续原安排」。该动作始终针对原工作和原参数，首轮不提供 Core 的 resubmit、重新投稿、取消远端任务或删稿。保证范围是同一部署、完整的本地记录和 Core 幂等记录；丢库、换库或其他客户端另行投稿不在去重保证内。

## 五、状态查回与页面接口

拟在 mumu 增加受本机保护的切片投递路由，实际字段随实施写入现行契约。POST 创建只受理持久安排，可返回 202 和安排编号；重复确认返回同一编号。GET 按切片批量取本地摘要，GET 按安排编号取详情，POST 按安排编号继续未确认步骤。浏览器不能指定 Core 地址、素材绝对路径、work_id、Core Key 或任意 task_id。

已有任务通过 GET /api/v1/tasks/{task_id} 查当前状态；必要时按 work_id 分页查作品任务，用稳定身份核对关联，单次空列表不能作为新建依据。只查询当前页活跃记录，限并发、超时退避，关闭页面停止轮询。持久保存最新可信观察，迟到或旧部署响应丢弃。区分以下用户可见结果：

| Core 状态 | 切片页显示 |
| --- | --- |
| QUEUED、CLAIMED、VALIDATING | 已排队、已领取、准备上传 |
| RUNNING、RETRY_WAIT | 上传中、等待上传模块重试 |
| RECOVERY_PENDING、UNCERTAIN | 上传模块恢复中、投稿结果待核对；保留原单，可继续查询 |
| SUCCEEDED | 投稿成功，展示已返回的稿件信息；平台审核状态仅在有可靠查询结果时另行展示 |
| FAILED、CANCELLED、EXPIRED | 显示原任务的最终结果与可公开原因，继续保留历史 |

查询失败仅改变“最近一次查询是否成功”；未知枚举显示「未知状态」并保留安全状态值。普通页面轮询只读 Core 的任务状态，不反复触发主动平台查询。Core 状态定义见[任务状态机](../../../fileUploadPlatform/src/upload_platform/domain/core.py)。

## 六、实施顺序和验收

1. 先核对目标部署的归属、运行契约、普通投稿配置、Worker 和路径可见性。确认后端客户端被允许访问上述路由。现有账号页能扫码不自动打开投递开关。
2. 在 src/orchestrator 下实现独立的投递存储、固定路由客户端和本机 API，由 server.py 挂接。与录制调度分别处理，提交或轮询超时不能阻塞 Scheduler.tick、切片封口和停录。录制数据只读，切片资源复用现有查询与正式路径校验。
3. 在 [SegmentsView.vue](../../web/src/views/SegmentsView.vue) 和 [SegmentTable.vue](../../web/src/components/SegmentTable.vue) 接入确认弹窗、批量状态与详情，替换切片页模拟上传状态。功能已接入、当前能否下单、单个任务进度分别判断；后端暂停时原单仍可查看。
4. 用可控故障的测试服务和真实 SQLite 验证时间窗口，再用兼容 Core、测试目标及独立 Worker 从实际切片页完成一次下单。最终业务验收选明确允许投稿的样片、账号、参数和部署，由用户在确认页安排一次；记录 mumu 单号、脱敏 Core 任务关联和查询结论。既往 B 站投稿记录可佐证上传模块能力，但不能代替 mumu 下单证据。

| 验收场景 | 通过条件 |
| --- | --- |
| 同目录有两片，手动选择其中一片 | 确认页、冻结清单和 Core 任务快照对应同一片；没有提交邻片、改写公共 YAML 或删除原件。 |
| 临时片、中止片、越界路径、文件变更、账号停用、远端网页发请求 | 后端在相应边界拒绝，给出可操作原因；重新加载原录制切片页仍正常。 |
| 双击、两标签页并发、同 Key 不同参数、不同 Key 相同业务单 | 同一确认最多产生一条有效投递和一个当前任务；冲突不会改错文件或账号。 |
| 打开弹窗后切换部署，两个部署恰有同一账号 ID | 旧弹窗确认被拒绝，两个部署均未收到写请求。原安排仍显示在原切片行。 |
| 登记回包丢失、超时、协程退出、mumu 写回前硬退出 | 检查派发步骤、代次和请求序列。超时或协程退出后同一 mumu 进程可继续，硬退出后重启可接手；登记重放使用原 Key 和正文，旧回包不能覆盖新状态。 |
| Core 已建任务，提交回包丢失，随后移走录像 | 从原 work_id 开始 GET 并查完所有分页，唯一匹配时找回原 task_id，再 GET 最新状态。检查实际请求序列，恢复全程只有 GET；核对 Core 仍只有原任务。失败分页、冲突或多条匹配均保留待核对。 |
| 首次明确拒绝，或超时后重放收到同类拒绝 | 首次拒绝可显式修订，核对旧弹窗失效和新 Key；超时后的拒绝保留原单待确认，禁止修订。恢复若取得原回执编号，立即调用单任务 GET，界面使用最新状态。 |
| 任务排队时关闭页面、重启 mumu、Worker 离线后恢复、查询超时或迟到 | 页面找回原任务，展示最后确认时间，恢复后跟随原任务进展，无新增登记或提交。 |
| 发布结果不确定、明确失败、查回不到原任务、部署改变 | 保留对应状态及原编号；界面没有把结果未知变成失败再投，无跨部署重放。 |
| 用户可见的完整链路 | 从实际切片页安排一次，Core 可查到唯一匹配任务。再次进入详情看到该任务实际结果；测试目标、真实投稿和未验证的异常场景分别记录。 |
