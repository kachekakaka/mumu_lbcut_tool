## 1. 背景与可验证目标 (Background & Verifiable Goals)

在 2026-11-01 引入未登录弹窗治理与开录门禁后，针对代码基线 `d16aded` 的全面代码审查暴露了 17 项制约无人值守投产的核心缺陷。本方案不改变原有“外部调度器 + 独立 Recording Worker”的解耦架构，而是将原有的问题整改清单升级为**高内聚、可以直接执行、测试和验收的工程实施规格**。

### 可验证目标
1. **底层无卡死**：所有外部进程调用（ADB、scrcpy、MuMu）均受命令级严格超时保护，任何底层通信故障均在约定秒级内暴露，主控制循环绝不挂死；
2. **状态严密单写**：所有切片启停、状态流转与 NDJSON 事件严格由主控制线程单点执行，看门狗采用动作队列 + 代际 ID 交互，切片事件 100% 单调且一一对应；
3. **故障秒级感知**：scrcpy 进程异常退出在 1 秒内被感知，停止虚假录制心跳，并执行有界自愈或退出；
4. **房间绝对正确**：增加目标主播身份一致性校验，指定主播 A 时绝不错录为推荐流或相邻房间的主播 B；
5. **假死精准识别与容错**：视觉看门狗支持 PK 宽幅 ROI 与短间隔双帧差分，区分正常低动态画面与真卡死，分级恢复并闭环验收；
6. **产物状态真实**：每个切片必须通过封口完整性校验，未完成或损坏文件绝不上报为正常完成；切片空档作为已知限制进行物理度量。

## 3. 用户故事 (User Stories)

1. **作为外部调度器 (Orchestrator)**：
   - 当 Worker 遇到底层异常退出时，我希望通过退出码（15 登录强阻断、16 画面超时、17 导航失败、18 房间身份不匹配、30 录制崩溃、2 正常下播）精确获知原因，以便直接决策是否隔离实例或漂移重试，无需解析非结构化日志。
   - 当 Worker 处于自愈恢复状态时，我希望收到 `recovering` 状态而不是虚假的正常 `recording` 心跳。
2. **作为录播系统运维人员**：
   - 当启动指定端口（如 16448）录制主播 A 时，我希望 Worker 绝对不会绑定到其他端口的模拟器，且绝对不会录制被抖音自动切换到的主播 B。
   - 在主播进行连麦 PK 且自身短时静止时，我希望录像不会被看门狗频繁误杀切片。
3. **作为开发工程师**：
   - 我希望任何切片要么以 `segment_finished` 成功收尾，要么以 `segment_aborted` 明确中止，没有中间态丢失或并发错位。

## 4. 详细实施规格与技术设计 (Detailed Specifications)

### 4.1 录制管线状态机与单写者原则 (F-03, ADR 0008)

#### 4.1.1 Worker 生命周期状态模型
Worker 严格遵循以下有向状态迁移，禁止任意跨状态跃迁：

```text
       ┌──────────────┐
       │  PREFLIGHT   │ (准备环境、连接设备、拉起房间、门禁及身份核验)
       └──────┬───────┘
              │ 校验通过
              ▼
       ┌──────────────┐ 动作队列自愈 / scrcpy 异常
       │  RECORDING   │ ◄────────────────────────┐
       └──────┬───────┘                          │ 自愈成功
              │ 异常触发                          │
              ▼                                  │
       ┌──────────────┐ ─────────────────────────┘
       │  RECOVERING  │
       └──────┬───────┘ 超过重试上限 / 不可恢复
              │
              ▼
       ┌──────────────┐
       │   STOPPING   │ (封口切片、关闭子进程、释放资源、写出终态事件)
       └──────┬───────┘
              │ 清理完成
              ▼
       ┌──────────────┐
       │   STOPPED    │ (输出进程退出码)
       └──────────────┘
```

#### 4.1.2 五大核心架构原则
1. **单写者原则 (Single-writer)**：所有切片启停、`WorkerPipeline` 控制、状态迁移和 NDJSON 生命周期事件严格由主控制线程统一执行。看门狗等后台线程仅作为纯观察者，通过线程安全队列 `action_queue = queue.Queue()` 投递请求。
2. **代际 ID 丢弃规则 (Generation ID)**：
   - 主线程维护单调递增的整数 `generation_id: int`（从 1 开始，每次管线重启/切片切换时 +1）；
   - 主线程通过只读快照向看门狗发布当前的 `generation_id`；
   - 看门狗发出的动作请求必须显式携带其采样时的 `req.generation_id`；
   - 主线程消费队列时，若 `req.generation_id != self.generation_id`，判定为过期请求，**直接丢弃**并记录 trace 日志，彻底防止旧切片动作误杀新切片。
3. **有限自愈原则 (Bounded Recovery)**：
   - 任何故障恢复均有硬性重试上限（如单切片内就地重启最多 1 次，同房间 Intent 刷新最多 1 次）；
   - 切片计划切换不能无条件重置已发生的累计故障次数；恢复操作后必须执行健康验证，验证不通过直接推进到 `STOPPING`。
4. **事件完整性原则 (Event Completeness)**：
   - 每一个 `segment_started` 事件，在退出或切换时**必须且只能对应一个终态事件**：成功封口对应 `segment_finished`，异常中断或校验失败对应 `segment_aborted`；
   - 严禁将未产出有效视频的文件上报为 `segment_finished`。
5. **真实心跳原则 (Truthful Heartbeat)**：
   - 当系统处于 `RECOVERING` 状态时，心跳 `status` 必须标记为 `recovering`，严禁报 `recording`；
   - `fps` 字段若无法通过探针实测，必须填入 `null`，严禁硬编码伪造 `30.0`。
6. **统一退出收尾原则 (Unified Cleanup)**：
   - 无论是正常下播、达到总时长、外部中断信号（SIGINT/SIGTERM）、设备掉线还是未捕获的 Python 运行时异常，均必须进入统一的 `cleanup()` 收尾逻辑，执行子进程终止、未完成切片处置与退出码映射。

### 4.2 运行基础与子进程监控 (F-07, F-08, F-02, F-10, F-12)

#### 4.2.1 命令级超时规格与统一封装 (F-07)
在 `src/worker/` 封装统一的执行器 `run_cmd_with_timeout(cmd, timeout_sec, ...)`，杜绝直接裸调无超时的 `subprocess.run()`：

| 命令分类 | 涵盖操作 | 超时上限 | 超时处理策略 |
| :--- | :--- | :--- | :--- |
| **轻量状态查询** | `dumpsys window`、`dumpsys activity`、`adb devices` | **3.0 秒** | 强制终止子进程，抛出 `CommandTimeoutError`，重试 1 次失败则标记设备离线 |
| **内存截帧** | `exec-out screencap -p` | **5.0 秒** | 强制终止，返回 `None`，触发门禁/看门狗对应计数 |
| **应用唤起与交互** | `am start`、`input tap`、`input keyevent` | **8.0 秒** | 强制终止，抛出 `CommandTimeoutError` |
| **模拟器实例管理** | MuMu 启动实例、网络端口连接 | **15.0 秒** | 超时直接判定设备未就绪，抛出 `DeviceUnavailableError` |

#### 4.2.2 scrcpy 日志管道防背压 (F-08)
- 启动 `scrcpy` 子进程时，不再使用无限制累积的未读取 `subprocess.PIPE`；
- **实现方式**：将 `stdout` 和 `stderr` 重定向至滚动日志文件（如 `logs/scrcpy_{vmindex}.log`），或者在启动时创建专用后台 Daemon 线程实时 `readline()` 消费并转交 logger，彻底消除管道缓冲区满导致录制子进程死锁挂起的背压风险。

#### 4.2.3 scrcpy 子进程存活监控与就地自愈 (F-02)
- 主控制循环每个 tick（1.0 秒）严格调用 `pipeline.is_process_alive()`（底层检测 `process.poll()`）；
- 若检测到子进程非正常提前退出：
  1. 状态立即迁移至 `RECOVERING`；
  2. 针对当前切片发射 `segment_aborted` 事件；
  3. 执行**有限就地自愈 1 次**：在当前模拟器实例内重新拉起 `pipeline.start_segment()`；
  4. 若 3 秒内进程就绪且录制文件开始生成，状态恢复至 `RECORDING`，开启新切片并重置切片时长；
  5. 若拉起失败，或 5 分钟内再次发生异常退出，判定自愈超限，发射 `recording_failed` 事件，迁移至 `STOPPING`，以退出码 `30 (EXIT_RECORDING_FAILED)` 退出。

#### 4.2.4 依赖补全与 CLI 参数校验 (F-10, F-12)
- 在 `requirements.txt` 中显式声明：
  ```text
  numpy>=1.24.0
  Pillow>=9.5.0
  requests>=2.31.0
  ```
- CLI 入口对输入参数进行前置强校验：
  - `segment_duration_sec >= 60`（杜绝 0 秒或过短切片死循环）；
  - `heartbeat_interval_sec >= 1.0`；
  - `stall_timeout_sec >= 5.0`；
  - `total_duration_sec >= 0`；
  - 输出目录必须存在或可成功创建，且具有写入权限；
  - 校验失败直接输出错误并以退出码 `10 (EXIT_TARGET_INVALID)` 终止，不得进入任何模拟器操作。

### 4.3 视觉看门狗三环节恢复体系 (F-01)

看门狗状态机扩展为：`HEALTHY` -> `SUSPECTED_STALL` -> `RECOVERING` -> `HEALTHY` / `UNRECOVERABLE`。

```text
                     ┌───────────────┐
                     │    HEALTHY    │
                     └───────┬───────┘
                             │ 异常检测：短间隔双帧+跨周期差分低于阈值
                             ▼
                     ┌───────────────┐
                     │SUSPECTED_STALL│
                     └───────┬───────┘
                             │ 复检仍异常且无音频活动
                             ▼
                     ┌───────────────┐
                     │  RECOVERING   │ (分级恢复：Intent 刷新 -> 管线重启)
                     └───┬───────┬───┘
                         │       │
             恢复验收成功 │       │ 达到上限或仍无动态
                         ▼       ▼
              ┌───────────┐     ┌───────────────┐
              │  HEALTHY  │     │ UNRECOVERABLE │ (投递 FATAL_STALL，退场)
              └───────────┘     └───────────────┘
```

#### 第一环节：异常检测 (Detection)
- **PK 双画面全宽 ROI**：画面裁剪区域设定为高度 `[15% : 65%]`、宽度 `[5% : 95%]`，涵盖横向并列的双主播区域，避开顶栏（0~15%）与底部弹幕送礼区（65~100%）；
- **短间隔双帧采样**：每个 30 秒探针周期内，抓取相隔 **0.8 ~ 1.0 秒**的 Frame 1 与 Frame 2，计算瞬时灰度绝对差分率 $\text{diff}_{\text{instant}}$；
- **综合判决**：
  - 若命中登录遮罩特征（白底或卡片），直接触发弹窗消解动作；
  - 若 $\text{diff}_{\text{instant}} < \theta_{\text{dynamic}}$（初始标定参数暂设为 0.3%，需实机标定）：
    - 进一步对比 Frame 2 与上一探针周期（30 秒前）基准帧的跨周期差分 $\text{diff}_{\text{cross}}$；
    - 若两者均低且音频无动态输出，状态进入 `SUSPECTED_STALL`；否则保持 `HEALTHY`。

#### 第二环节：分级恢复 (Tiered Recovery)
- 当进入 `SUSPECTED_STALL`：
  1. **级别 1（轻量刷新）**：看门狗向主线程投递 `ACTION_REFRESH_INTENT`，主线程调用 `nav.refresh_current_room()` 执行同房间原地 Intent 唤起（严禁手势清屏），冷却等待 5 秒；
  2. **级别 2（切片重启）**：若刷新后复检仍处于卡死状态，看门狗向主线程投递携带当前代际 ID 的 `ACTION_RECYCLE_SEGMENT`，主线程关停旧切片并重启新切片；单次录制任务中此类重启设定冷却时间（如至少相隔 60 秒）且累计不得超过 3 次。

#### 第三环节：恢复验收 (Verification & Escalation)
- 重启或刷新操作执行后，必须等待 3~5 秒进行恢复验收；
- 重新检测前台 Activity、画面短间隔差分与切片文件写入；
- 若画面恢复动态，状态迁移回 `HEALTHY`；若连续自愈 2 次后画面仍未脱离静止或无法生成有效视频，看门狗投递 `ACTION_FATAL_STALL`，主线程终止录制并以退出码 `30` 退出，交由调度器处置。

### 4.4 ADB 精确绑定与端口就绪轮询 (F-04)

- **根除模糊回退**：修改 `src/mvp/mumu_client.py`，彻底删除 `len(lines) == 2` 以及任何在未找到匹配设备时盲目 `return parts[0]` 的逻辑；
- **严格匹配规则**：遍历 `adb devices` 输出，仅当设备 serial 字符串与请求的 serial（如 `127.0.0.1:16448`）完全一致，且状态为 `device` 时，才视为连接成功；
- **就绪轮询窗口**：
  - 封装 `wait_for_device(serial, timeout_sec=15.0)`；
  - 每隔 1.0 秒刷新一次 `adb devices`，在 15 秒内匹配成功即返回；
  - 若 15 秒超时仍未发现设备或设备处于 `offline` / `unauthorized`，立即抛出 `DeviceConnectionError`，绝不回退到其他在线设备。

### 4.5 目标房间身份核验、前置门禁与下播判定 (F-05, F-06)

#### 4.5.1 目标房间身份一致性校验 (Target Room Identity Verification)
为杜绝“指定主播 A，实际录制主播 B”的恶劣事故，在开录前门禁及运行期自愈后增加身份核验：
1. **输入解析**：通过 `WorkerRoomResolver` 解析目标输入，提取预期主播昵称、`room_id` 或 `web_rid`；
2. **多源探测**：
   - 方式一（UI 节点）：通过 ADB dump 快速检索当前直播间顶栏的主播昵称文本控件；
   - 方式二（局部 OCR 兜底）：若 UI 节点混淆无法读取，截取左上角主播信息卡片区域（高度 `[2%:10%]`, 宽度 `[3%:35%]`），执行轻量级 OCR 文本提取；
3. **决策分流**：
   - 匹配一致：标记 `IDENTITY_VERIFIED`，放行录制；
   - 明确不一致（发现属于其他主播）：坚决阻断，发射 `RoomIdentityMismatchEvent`，以退出码 `18 (EXIT_ROOM_MISMATCH)` 退出；
   - 无法确认身份：默认开启严格阻断模式，判定未通过门禁（退出码 18）；仅当 CLI 显式传入 `--allow-unconfirmed-identity` 逃逸参数时，允许在记录警告后继续录制。

#### 4.5.2 退出码与事件契约矩阵 (Escalation Contract)
统一退出码与 NDJSON 事件契约，使调度器无需猜测：

| 退出码 | 字符标识 | 触发场景 | 发射 NDJSON 事件 | 调度器标准处置建议 |
| :---: | :--- | :--- | :--- | :--- |
| **0** | `EXIT_SUCCESS` | 达到预设 `total_duration_sec` 或接收到正常停止信号 | `worker_stopped(reason="completed")` | 正常归档录像 |
| **2** | `EXIT_STREAM_ENDED` | 主播正常下播（API 下播 + 视觉画面静止双重确认） | `stream_ended(reason="anchor_offline")` | 任务正常结束，关闭实例 |
| **10** | `EXIT_TARGET_INVALID` | 输入直播间链接/口令无效，或 CLI 参数越界 | `worker_failed(reason="invalid_params")` | 标记任务配置错误，不重试 |
| **15** | `EXIT_LOGIN_BLOCKED` | 命中全屏/居中登录特征且白名单穿透失败 | `login_blocked(reason="auth_required")` | 隔离当前实例并告警，需人工登录 |
| **16** | `EXIT_PREFLIGHT_STALL` | 8 秒内未检测到有效视频动态渲染（黑屏或静止） | `preflight_failed(reason="render_timeout")` | 检查网络或实例渲染，调派备用机 |
| **17** | `EXIT_NAVIGATION_FAILED`| 拉起直播间 Intent 报错或前台非抖音包名 | `preflight_failed(reason="intent_failed")` | 重启 App 或检查模拟器环境 |
| **18** | `EXIT_ROOM_MISMATCH` | 前台主播身份与预期目标不匹配或无法核验 | `room_identity_mismatch(reason="id_mismatch")`| 阻断录制，排查跳转或链接 |
| **20** | `EXIT_DEVICE_UNAVAILABLE`| 目标 ADB 端口 15 秒未就绪或实例启动失败 | `worker_failed(reason="device_offline")` | 实例损坏告警，重启模拟器服务 |
| **30** | `EXIT_RECORDING_FAILED` | scrcpy 子进程二次崩溃或视觉卡顿自愈失败 | `recording_failed(reason="pipeline_crashed")`| 记录崩溃现场，调度备用实例接棒 |

#### 4.5.3 运行期下播双重核验 (F-05)
- 主线程每隔 30~60 秒通过 `WorkerRoomResolver` 查询一次房间在线状态；
- 若 HTTP API 明确返回“已下播”：
  - 不立即断流，触发看门狗对当前画面进行单次核验；
  - 若画面差分亦降为静止（主播已离开推流断开），确认下播，发射 `stream_ended` 事件，平稳封口退出（退出码 2）；
  - 若 HTTP 查询遭遇网络超时或抛出异常，**坚决不退场**，仅记录 warning 日志，防止网络瞬时波动造成录制中断。

---

### 4.6 切片产物校验与终态事件契约 (F-11)

- 当主线程调用 `pipeline.stop_segment()` 封口切片后，必须执行产物完整性校验函数 `verify_segment_output(file_path)`：
  1. 物理文件必须存在；
  2. 文件大小必须大于阈值（如 $\ge 1.0\text{ MB}$，防止仅有头部信息的空文件）；
  3. 通过 `ffprobe` 快速校验文件封装格式中包含有效的 `video` 轨且时长 $\ge 1\text{ s}$；
- **终态事件契约**：
  - 校验通过：发射 `SegmentFinishedEvent(segment_index, file_path, duration_sec, file_size_mb)`；
  - 校验未通过或子进程异常中止：发射 `SegmentAbortedEvent(segment_index, file_path, reason="file_corrupted_or_empty")`；
  - 任何切片生命周期严禁以未决状态静默结束。

---

### 4.7 切片空档策略与 F-09 工程取舍 (F-09)

- **现状取舍明确**：现阶段保留“每 30 分钟重启一次 scrcpy 重置 PTS 消除累积漂移”的设计，明确将重启过程中的秒级空档定义为**“已接受工程限制 (Accepted Limitation)”**，不承诺未经验证的零间隙；
- **量化度量实施**：
  - 在切片切换代码中精确记录：
    - 旧切片停止命令发起时间戳 $T_{\text{stop}}$ 与子进程实际退出时间戳；
    - 新切片启动命令发起时间戳 $T_{\text{start}}$ 与首帧有效写入时间戳；
    - 计算物理调用间隙：$\Delta t_{\text{call}} = T_{\text{start}} - T_{\text{stop}}$；
  - 在阶段 D 中，利用外部测试音视频源比对相邻切片末帧与首帧的真实媒体 PTS 差值，形成可复查的基准度量数据。

### 4.8 观测性与边界容错完善 (F-13 ~ F-17)

1. **短链解析回退 (F-13)**：重写 `resolver.py`，短链 HEAD 请求失败时回退使用 GET 请求；若正则提取未命中合法房间号，返回明确解析失败，严禁泛化正则匹配回退到 `"https"` 字符串。
2. **真实 FPS 心跳 (F-14)**：心跳中的 `fps` 字段由 scrcpy 实际统计或置为 `null`，配置的最大帧率使用 `configured_fps=30` 明确区分，不伪造固定测量值。
3. **scrcpy 就绪性探针 (F-15)**：启动前执行 `scrcpy --version`，检查实际版本号是否处于已验证区间（v2.0+），并记录到日志中。
4. **输出文件名防碰撞 (F-16)**：切片命名规范升级为包含任务 ID 与实例标识：
   `seg_{vmindex}_{web_rid}_{timestamp}_{segment_index:04d}.mp4`，创建前若检测到同名文件，追加微秒时间戳防覆盖。
5. **看门狗自愈动作与事件全映射 (F-17)**：看门狗触发的所有自愈尝试（`ACTION_REFRESH_INTENT`、`ACTION_RECYCLE_SEGMENT`）均通过 NDJSON 事件完整广播至外部调度器。

## 6. 风险、假设与已知物理限制 (Risks & Known Limitations)

1. **已接受的工程限制**：
   - **中断式切片物理空档 (F-09)**：当前版本接受约 1~1.5 秒的切片间隙作为消除长时累积漂移的工程折中。本方案要求完成精确度量，暂不引入复杂的内存抓流多路复用封装器。
2. **外部不可抗力风险与应对**：
   - **抖音极验滑块与短信强制登录**：Worker 不做暴力破解；一旦触发免登录风控死锁，由门禁严格阻断（退出码 15）并通知调度器隔离，生产环境以“人工预登录账号”为基线防线；
   - **抖音 UI 混淆导致主播昵称获取失败**：系统提供渐进式探测（UI 节点 -> 局部 OCR）；若完全无法识别，在严格模式下阻断，同时提供显式 `--allow-unconfirmed-identity` 逃逸开关由业务方承担风险。
