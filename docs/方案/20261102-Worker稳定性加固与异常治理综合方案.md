## 1. 背景与可验证目标 (Background & Verifiable Goals)

针对代码审查暴露的 17 项核心缺陷（F-01～F-17），本方案在保留“外部调度器 + 独立 Recording Worker”解耦模型与 F-09 已接受工程限制的前提下，将整体方案升级为**无内部阻塞矛盾、具有严密生命周期状态机、多信号独立研判、真实产物核验、身份闭环追踪与多维测试矩阵的实施规格**。

### 可验证工程目标
1. **主循环非阻塞与故障秒级感知**：主控制循环杜绝同步慢调用阻塞；在稳定录制状态下，`scrcpy` 进程异常退出在约 1～3 秒的检测预算内被感知并响应，心跳停止标记 `recording`；
2. **状态严密单写与队列去重**：主控制线程独占状态迁移、切片控制与事件发射；看门狗投递请求附带代际 ID（`generation_id`），旧代际丢弃且同代际重复请求合并，切片终态事件严格一一对应；
3. **房间身份闭环核验与风险追踪**：支持开录前与运行期主播身份一致性校验，区分 `VERIFIED`、`MISMATCH` 与 `UNCONFIRMED`；默认严格阻断；逃逸开关仅放行未确认，绝不放行明确错录；错房发生时关联并标记受影响切片范围；
4. **视觉看门狗四维独立健康信号**：视频动态、音频状态、进程存活与文件写入进度独立研判，消除“音频有声即判定视频正常”的误判逻辑；
5. **真实产物校验与短尾片容错**：切片封口校验区分容器完整性与业务质量，音视频双轨必需，短尾片正常标记，消除不切实际的文件大小硬门槛；
6. **科学量化度量与审慎验证**：对切片物理空档（F-09）定义基于外部统一时间码的精确度量方法，区分轨道时长差与真实音画同步偏移；周期重启定位为缓解长时音画漂移的候选措施，其效果通过实测验证；建立 8～24 小时长时间多实例长稳测试矩阵与故障注入用例。

## 3. 用户故事 (User Stories)

1. **作为外部调度器 (Orchestrator)**：
   - 当 Worker 遇到异常退出时，我希望通过确定退出码与结构化 reason（15 登录强阻断、16 画面超时、17 导航失败、18 房间身份异常、20 设备或采集能力缺失、30 录制崩溃/卡死/预算耗尽、2 正常下播）精确获知原因并调度，无需解析非结构化日志。
   - 当 Worker 处于自愈恢复状态时，我希望收到 `recovering` 状态而不是虚假的 `recording` 心跳；当主播身份未确认时，心跳与事件应明确标注风险。
2. **作为录播系统运维人员**：
   - 当启动指定端口录制主播 A 时，我希望 Worker 绝对不会绑定到其他端口的模拟器，且绝对不会录制被抖音推荐流自动切换到的主播 B。
   - 在主播进行连麦 PK 且自身短时静止时，我希望录像不会被看门狗频繁误切片；当运行期偶然错房时，我希望能精准获知受影响的历史切片清单。
3. **作为开发与测试工程师**：
   - 我希望任何切片生命周期要么以 `segment_finished` 成功收尾，要么以 `segment_aborted` 明确中止，没有中间态丢失或并发错位；音画同步与切片空档具备确定且可重复的度量测试方法。

## 4. 详细实施规格与技术设计 (Detailed Specifications)

### 4.1 录制管线状态机与六大核心架构原则 (F-03, ADR 0008)

#### 4.1.1 Worker 生命周期严格状态模型
Worker 严格遵循以下有向状态迁移，禁止任意跨状态跃迁：

```text
       ┌──────────────┐
       │  PREFLIGHT   │ (准备环境、连接设备、拉起房间、门禁及身份核验)
       └──────┬───────┘
              │ 校验通过                 校验失败 / 异常
              ├───────────────────────────────────────────┐
              ▼                                           │
       ┌──────────────┐ 动作队列自愈 / scrcpy 异常        │
       │  RECORDING   │ ◄────────────────────────┐        │
       └──────┬───────┘                          │ 自愈   │
              │ 异常触发                          │ 成功   │
              ▼                                  │        │
       ┌──────────────┐ ─────────────────────────┘        │
       │  RECOVERING  │                                   │
       └──────┬───────┘ 超过重试上限 / 不可恢复            │
              │                                           │
              ▼                                           │
       ┌──────────────┐ ◄─────────────────────────────────┘
       │   STOPPING   │ (封口当前切片、关闭子进程、释放资源、发射终态事件)
       └──────┬───────┘
              │ 清理完成（幂等保障）
              ▼
       ┌──────────────┐
       │   STOPPED    │ (输出进程退出码)
       └──────────────┘
```

**严格迁移矩阵**：
- `PREFLIGHT  → RECORDING | STOPPING`
- `RECORDING  → RECOVERING | STOPPING`
- `RECOVERING → RECORDING | STOPPING`
- `STOPPING   → STOPPED`

#### 4.1.2 六大核心架构原则
1. **单写者原则 (Single-writer)**：
   - `WorkerPipeline` 的所有生命周期操作（`start_segment`、`stop_segment`）、状态机迁移及外部 NDJSON 生命周期事件，严格由主控制线程独占执行；
   - 耗时外部操作（HTTP 房间查询、截帧差分、身份探测、ffprobe 文件校验等）必须通过受控后台只读任务或带剩余预算的可轮询过程执行，绝不得在主控制循环内同步长等待阻塞；
   - 后台任务仅具备只读探测权限，绝不得直接操作管线，探测结果仅通过线程安全队列投递给主线程消费。
2. **代际 ID 校验与动作去重原则 (Generation ID & Deduplication)**：
   - 主线程维护单调递增的整数 `generation_id: int`（从 1 开始，每次管线重启或切片切换时 +1），并发布只读快照 `PipelineSnapshot`；
   - 看门狗动作请求必须携带采样时的 `req.generation_id`；
   - 主线程消费队列时：
     - **旧代际丢弃**：若 `req.generation_id < self.generation_id`，直接丢弃并输出 trace 日志；
     - **同代际去重合并**：若队列中已存在相同类型的动作请求（如已有待处理的 `ACTION_RECYCLE_SEGMENT`），合并忽略后续重复请求，防止连续重启切片。
3. **有限自愈与全局预算原则 (Bounded Recovery & Global Budget)**：
   - 任何自愈均有硬性边界，分为三层约束：
     1. **单次故障恢复上限**：针对同一次疑似卡顿，最多执行 1 次 Intent 刷新 + 1 次切片重启；
     2. **滚动窗口恢复上限**：在 5 分钟时间窗口内，切片重启不得超过 2 次；
     3. **任务全局预算上限**：单个录制任务生命周期内，累计自愈重启不得超过 3 次；
   - 切换新切片时，重置当前切片大小与计时基线，但**绝不重置任务全局自愈次数与预算**；超限直接迁移至 `STOPPING` 并以退出码 `30`（reason=`recovery_budget_exhausted`）退出。
4. **事件成对与终态完整性原则 (Event Completeness)**：
   - 每一个 `SegmentStartedEvent` 在切片结束或任务退出时，**必须且只能对应一个终态事件**：成功封口且校验通过对应 `SegmentFinishedEvent`，异常中断或校验损坏对应 `SegmentAbortedEvent`；
   - 严禁将未产出有效媒体数据或结构损坏的文件上报为 `segment_finished`。
5. **真实心跳与非阻塞感知原则 (Truthful Non-blocking Heartbeat)**：
   - 心跳中的 `status` 严格反映状态机：处于 `RECOVERING` 时必须上报 `status="recovering"`，严禁虚报 `recording`；
   - 心跳中的 `fps` 仅在有可靠测量源时填写真实数值，无法实测时显式置为 `null`，严禁伪造固定 `30.0`；
   - 恢复冷却时间采用单调时钟截止时间（`cooldown_deadline = time.monotonic() + cooldown_sec`），在主循环心跳检测中按条件判断放行，严禁在主线程使用长时间 `time.sleep()`。
6. **幂等清理与安全收尾原则 (Idempotent Cleanup)**：
   - `STOPPING` 状态具备最高执行优先级：一旦进入 `STOPPING`，动作队列中任何恢复动作一律忽略，严禁启动任何新切片；
   - 收尾方法 `cleanup()` 具备重入锁与幂等标志（`_cleaned = True`），无论是正常结束、下播、外部信号还是未捕获异常均走统一收尾路径；
   - **强杀保证边界**：客观声明若进程遭遇操作系统级别强制终止（如 `SIGKILL`、Windows `TerminateProcess`）或物理断电，用户态 Python 代码无法捕获执行，此时调度器依据 Worker 退出码或进程消失作为判定依据，不承诺此时必然发射 NDJSON。

### 4.2 运行基础、子进程监控与工具版本策略 (F-07, F-08, F-02, F-10, F-12, F-15)

#### 4.2.1 命令级超时、流程总截止时间与单调时钟 (F-07)
在 `src/worker/` 封装统一执行器 `run_cmd_with_timeout(cmd, timeout_sec, deadline=None)`：
- 严格使用 `time.monotonic()` 进行计时与预算扣减：
  $$\text{remaining\_budget} = \text{deadline} - \text{time.monotonic()}$$
  实际执行超时为 $\min(\text{timeout\_sec}, \text{remaining\_budget})$；若剩余预算 $\le 0$ 则直接抛出 `TimeoutError`；
- 超时后强制调用 `proc.kill()` 并回收孤儿进程，严禁无超时裸调 `subprocess.run()`；
- 命令类型基准超时：
  - **轻量状态查询**（`dumpsys window`、`dumpsys activity`、`adb devices`）：**3.0 秒**；
  - **内存屏幕截帧**（`exec-out screencap -p`）：**5.0 秒**；
  - **应用唤起与按键**（`am start`、`input tap`、`input keyevent`）：**8.0 秒**；
  - **模拟器实例连接**（MuMu 端口连接、网络握手）：**15.0 秒**；
  - **外部分析工具**（`ffprobe` 产物校验）：**3.0 秒**。

#### 4.2.2 scrcpy 日志管道防背压 (F-08)
- 启动 `scrcpy` 时，杜绝使用无限制累积且未持续读取的 `subprocess.PIPE`；
- **实现方式**：
  - 启动后台 Daemon 线程实时消费 `stdout` 与 `stderr`，写入循环滚动日志文件（`logs/scrcpy_{vmindex}_{run_id}.log`，限制单文件最大 20MB，保留 2 个切片），并向 logger 投递关键报错；
  - 关停子进程时，安全关闭并回收管道读句柄，彻底消除管道缓冲区满造成的录制进程挂死。

#### 4.2.3 scrcpy 存活监控与就地自愈 (F-02)
- **进程超时边界澄清**：`scrcpy` 是长期录像进程，绝不给录像运行设置命令级超时；限制的是**启动就绪阶段**（3.0 秒内必须确认 `poll() is None` 且文件开始写入）和**关停封口阶段**（8.0 秒内完成 `CTRL_BREAK_EVENT` 优雅封口）；
- **故障感知与检测预算**：
  - 主循环每秒 tick 调用 `pipeline.is_process_alive()`（底层检查 `process.poll()`）；
  - 在 `RECORDING` 稳定状态下，进程异常退出在 **1～3 秒检测预算内** 被主循环感知；
- **故障处理流程**：
  1. 状态立即迁移至 `RECOVERING`，发射当前切片 `SegmentAbortedEvent(reason="process_crashed")`；
  2. 若未超过任务全局自愈预算与窗口上限，执行**有限就地自愈 1 次**：重新调用 `pipeline.start_segment()`；
  3. 若 3 秒内启动成功且产物生成，迁移回 `RECORDING`，开启新切片并重置切片时长；
  4. 若启动失败或短时间内再次崩溃，发射 `recording_failed(reason="process_crashed")`，进入 `STOPPING`，以退出码 `30 (EXIT_RECORDING_FAILED)` 退出。

#### 4.2.4 依赖补全与 CLI 参数校验 (F-10, F-12)
- 在 `requirements.txt` 中显式固定依赖：
  ```text
  numpy>=1.24.0
  Pillow>=9.5.0
  requests>=2.31.0
  ```
- CLI 参数强校验：
  - `segment_duration_sec >= 60`；
  - `heartbeat_interval_sec >= 1.0`；
  - `stall_timeout_sec >= 5.0`；
  - `total_duration_sec >= 0`；
  - 输出目录必须存在或可创建且具备写入权限；校验失败直接以退出码 `10 (EXIT_TARGET_INVALID)` 终止。

#### 4.2.5 scrcpy 版本管理、下载策略与能力验证 (F-15 修订规范)
针对现有下载器动态抓取 latest、版本宽松与降级不明确的问题，制定统一版本策略：
1. **候选版本 vs 已验证版本**：
   - 将 **`scrcpy v3.1`** 明确定义为当前架构的**“目标候选版本（Candidate Version，待实机验证）”**；在未完成目标 MuMu 模拟器和 Android 镜像环境实测闭环前，不得称为已验证基准；
2. **下载与缓存策略规约（后续重构 dep_manager.py 时执行）**：
   - 必须锁定目标候选版本下载 URL，**严禁默认请求 GitHub API 获取 latest**（防止不可预测的破坏性变更或参数弃用）；
   - 本地缓存目录命名绑定版本号（如 `tools/scrcpy-v3.1/`），启动前比对本地缓存完整性（包含 `scrcpy.exe` 与 `scrcpy-server`）；
3. **完整必需录制参数与能力检查**：
   - 启动前探测工具支持的完整参数组合，必须同时支持：
     - `--record`、`--no-playback`、`--audio-source=playback`、`--audio-codec=aac`、`--video-codec=h264`、`--display-id=0`、`--max-fps`、`--video-bit-rate`、`--max-size`；
     - 音频强制必需参数 `--require-audio`（scrcpy v2.1+ 原生选项）；
   - 启动前调用 `scrcpy --version` 解析语义化版本：要求主版本 $\ge 2$ 且必须支持 `--require-audio`（即版本 $\ge 2.1$）；
4. **严格能力门禁与拒绝静默降级**：
   - 缺少本任务必需的音频、视频或采集方式能力时（例如底层 Android 镜像不支持音频转发、或 scrcpy 缺少 AAC 编码器、或不支持 `--require-audio`），**在开录前明确阻断失败**（以退出码 `20 (EXIT_DEVICE_UNAVAILABLE)`，reason=`audio_capture_unsupported` 退出）；
   - **严禁通过删除音频选项、改变采集源（如退化为麦克风）等方式静默降级为无声录像**；
5. **已安装外部工具冲突处置**：
   - 若检测到系统已有安装的 scrcpy 但版本不符合策略，直接报错退出，**严禁擅自覆盖或替换正在被其他任务或进程使用的外部工具文件**。

### 4.3 视觉看门狗四维信号与三环节恢复体系 (F-01)

看门狗状态模型：`HEALTHY` → `SUSPECTED_STALL` → `RECOVERING` → `HEALTHY` / `UNRECOVERABLE`。

#### 4.3.1 四维独立健康信号研判
看门狗将以下四类信号作为独立维度研判，消除单信号绑架：
1. **视频动态 (Video Motion)**：核心视频 ROI 短间隔双帧差分率 $\text{diff}_{\text{instant}}$ 与跨周期差分率 $\text{diff}_{\text{cross}}$；
2. **音频活动 (Audio Activity)**：音频活动探测。**能力边界说明**：当前架构下录播音频直写 MP4，若未集成独立的实时音频分析器，该信号明确标记为 `UNKNOWN`，绝不得假设为静音或正常；当音频为 `UNKNOWN` 时，看门狗研判完全由视频动态与文件进度主导；音频正常绝不能否决持续视频异常；
3. **进程存活 (Process Liveness)**：底层 `scrcpy.poll() is None`；
4. **文件写入进度 (File Progress)**：切片物理文件在磁盘上的 byte 大小持续增长。**独立卡顿路径**：若进程存活但文件连续 15 秒无任何字节增长，直接触发文件流假死自愈，无需等待视觉差分；若自愈失败以退出码 `30`（reason=`file_progress_stalled`）退出。

#### 4.3.2 视觉看门狗三环节恢复体系
1. **第一环节：异常检测 (Detection)**：
   - **PK 双画面全宽 ROI**：裁剪区域设定为高度 `[15% : 65%]`、宽度 `[5% : 95%]`，覆盖 PK 直播横向双主播画面，排除顶栏（0~15%）与底部滚动弹幕送礼区（65~100%）；
   - **短间隔双帧采样**：每 30 秒探针周期，抓取相隔 **0.8 ～ 1.0 秒**的两帧计算瞬时灰度差分率 $\text{diff}_{\text{instant}}$；
   - **研判逻辑**：若命中登录页特征直接穿透；若 $\text{diff}_{\text{instant}} < \theta_{\text{dynamic}}$（初始标定基准暂设 0.3%，需实机标定），再对比 30 秒前基准帧；若瞬时与跨周期均低动态，状态进入 `SUSPECTED_STALL`；
   - **音频辅助边界**：若未来具备音频检测且检测到高音频活动，仅允许将复检周期延长 1 次（防 PK 听讲误判），若二次复检画面仍无动态，必须按卡死处理。
2. **第二环节：分级恢复 (Tiered Recovery)**：
   - 处于 `SUSPECTED_STALL` 时，看门狗向主线程投递带当前代际 ID 的动作：
     - **级别 1（原地刷新）**：投递 `ACTION_REFRESH_INTENT`，主线程调用 `nav.refresh_current_room()` 原地唤起直播间，记录冷却截止时间戳（5.0 秒）；
     - **级别 2（切片重启）**：若刷新后复检仍处于卡死状态，投递 `ACTION_RECYCLE_SEGMENT`，主线程关停旧切片并开启新切片。
3. **第三环节：恢复验收与退场 (Verification & Escalation)**：
   - 恢复动作执行后，等待 3～5 秒验收窗口，重新核验画面动态与文件增长；
   - 若恢复正常，迁移回 `HEALTHY`；若连续自愈失败，看门狗投递 `ACTION_FATAL_STALL`，主线程迁移至 `STOPPING`，以退出码 `30`（reason=`visual_stall_unrecoverable`）退出；若自愈重启次数超出全局预算，以退出码 `30`（reason=`recovery_budget_exhausted`）退出。

### 4.5 目标房间身份核验闭环、前置门禁与下播判定 (F-05, F-06)

#### 4.5.1 目标房间身份核验闭环与风险追踪 (Target Room Identity Verification)
为杜绝“指定录制主播 A，实际录制推荐流主播 B”的恶劣事故，建立开录前门禁与运行期持续闭环：

##### 1. 证据等级与状态三态定义
- **证据含义澄清**：
  1. 稳定的 UI 控件 $\ne$ 稳定且唯一的身份值；
  2. 仅凭昵称相等，不能证明是同一主播（同名号、高仿号、家族号普遍存在）；
  3. 仅凭昵称不同，也不能在可靠稳定标识（如数字 UID / room_id）仍匹配时直接判定错房（主播中途可能改名或顶栏轮播头衔）；
  4. UI 节点或 OCR 只能提供其读取到的证据文本，不得将昵称证据自动升级为强身份验证；
  5. 当证据不足、有歧义、昵称截断（如带省略号）或信号冲突未解决时，**必须进入 `UNCONFIRMED`**，绝不得伪装为 `VERIFIED` 或确诊的 `MISMATCH`！
- **三态定义**：
  - `VERIFIED`：获取到足够可靠的稳定身份依据（如直播间唯一数字 ID / web_rid / 验证过的精确 UI 节点文本）且与目标预期完全匹配；
  - `MISMATCH`：明确获取到前台为另一主播（如读取到不同房间 ID 或确诊的不同稳定标识）；
  - `UNCONFIRMED`：信息缺失、UI 节点被混淆屏蔽、昵称带截断省略号、OCR 置信度不足。

##### 2. 探测优先级与实机验证规约
- 优先通过 ADB dumpsys / UI 自动化检索前台顶栏主播信息控件；
- 局部 OCR 仅作为可选的最后辅助手段，不默认依赖重型库；
- **实机验证前置规约**：在正式投产前必须先在目标 MuMu/抖音版本上验证 UI 树可读取性；若当前版本无法可靠读取，系统诚实判定为 `UNCONFIRMED`。

##### 3. 运行期由 VERIFIED 变为 UNCONFIRMED 的闭环流转
在录制期间以低频周期（每 2～3 分钟）及自愈刷新后执行身份复核：
1. **状态上报**：运行期一旦从 `VERIFIED` 变为 `UNCONFIRMED`，立即更新状态，发射 `room_identity_unconfirmed` 事件，心跳标记 `room_identity_status="unconfirmed"`；
2. **带截止时间的复核窗口**：
   - 进入复核窗口，计算截止时间戳：
     $$\text{recheck\_deadline} = \text{time.monotonic()} + \text{recheck\_timeout\_sec}$$
     （默认 `recheck_timeout_sec=30.0` 秒，配置化管理，**严禁无限重试**）；
   - 复核窗口内允许继续录制当前切片，但标记当前录制存在身份未确认风险；
3. **超时与严格阻断**：
   - **严格模式下（默认）**：超过复核截止时间仍为 `UNCONFIRMED`，判定核验失败，主线程进入 `STOPPING`，发射当前切片 `SegmentAbortedEvent(reason="identity_unconfirmed")`，以退出码 `18 (EXIT_ROOM_MISMATCH)` 退出（reason=`identity_unconfirmed`）；
   - **逃逸模式下（显式 `--allow-unconfirmed-identity`）**：复核超时后允许持续录制，但心跳与所有切片事件必须持续携带 `room_identity_status: "unconfirmed"` 显式暴露风险；
   - **逃逸开关永远不得放行明确的 `MISMATCH`**！一旦确诊 `MISMATCH`，无论是否开启逃逸参数，坚决立即阻断并以退出码 18 退出（reason=`id_mismatch`）。

##### 4. 历史风险范围追踪与切片标记
- 主线程维护 `last_verified_monotonic`（最后一次确诊匹配的时间戳）与 `last_verified_segment_idx`（最后一次确诊匹配时的切片序号）；
- 运行期一旦确诊 `MISMATCH`：
  1. 关联可能受影响的历史切片范围：`[last_verified_segment_idx, current_segment_index]`；
  2. 终止当前正在写入的切片，发射 `SegmentAbortedEvent(segment_index, reason="room_identity_mismatch")`；
  3. **对已发出终态事件的历史切片**：**绝不重复发射终态事件**（保证终态唯一性），而是追加发射独立的质量/风险警告事件 `SegmentQualityWarningEvent(segment_index, flag="possible_identity_mismatch", suspected_start_time=...)`，并记录到切片元数据中；
  4. **严禁擅自删除或覆盖原始录像文件**，留存证据供人工审计。

#### 4.5.3 运行期下播多信号判定 (F-05)
- **核心判定依据**：
  1. 通过后台异步只读任务低频（30～60 秒）查询房间在线状态；
  2. 若 API 连续 2 次（间隔 10 秒）明确返回 `ENDED`，或前台识别到明确的下播遮罩/展板 Activity，判定为正常下播；
- **辅助信号与冲突处理**：
  - 画面差分仅作为辅助确认信号；**结束页面的旋转动效、轮播展板或残留特效绝不能阻止下播退场**；
  - 若 API 报下播但前台画面仍有大面积主播互动动态，进入最多 30 秒的复核窗口，复核期间继续录制，复核后仍判定已下播才退场；
  - 网络波动、HTTP 错误、解析异常或状态为 `UNKNOWN` 严禁作为下播依据，Worker 保持正常录制；
  - 若客户端跳转到其他直播间，由 4.5.1 身份核验的 `MISMATCH` 路径处理，严禁与正常下播混淆。

### 4.6 切片产物校验与终态事件契约 (F-11)

#### 4.6.1 完整性与质量分离校验
切片封口后调用 `verify_segment_output(file_path)`：
1. **容器与媒体完整性 (Integrity)**：
   - 物理文件存在且 byte 大小 $> 0$；
   - 通过 `ffprobe` 快速解析容器格式，确认 MP4 moov box 成功封口且容器元数据无致命损坏；
   - 核验必需轨道：有声录制任务必须同时包含有效的 `video` 轨和 `audio` 轨；缺少音频轨判定为完整性损坏；
2. **业务质量评估 (Quality)**：
   - 正常封口的短尾片（如录制数十秒因正常下播或用户停止而结束）：容器完整且音视频轨齐全，判定为成功切片，在事件中携带 `quality="short_tail"` 属性，**严禁判为文件损坏**；
   - 彻底删除将“文件必须达到约 1 MB”作为完整性硬门槛的错误逻辑。

#### 4.6.2 ffprobe 依赖与探测规约
- **来源与检测**：依赖打包在 `tools/bin/ffprobe.exe` 或从系统 `PATH` 探测，Worker 启动前执行 `ffprobe -version` 校验可用性；
- **执行超时**：单次切片核验设置 3.0 秒硬性超时，超时强制终止；
- **能力边界**：明确 `ffprobe` 读取头部元数据不等于逐帧完整解码验证，不虚构质量承诺。

#### 4.6.3 细化终态事件原因映射
每个切片必须对应且只对应一个终态事件：
- 校验通过：发射 `SegmentFinishedEvent(segment_index, file_path, duration_sec, file_size_mb, quality="normal"|"short_tail")`；
- 校验未通过：发射 `SegmentAbortedEvent(segment_index, file_path, reason=...)`，明确区分：
  - `process_crashed`：录制子进程提前异常退出；
  - `container_corrupted`：文件头部损坏或缺失 moov；
  - `missing_audio_stream`：缺少音频流；
  - `zero_byte_file`：产物为 0 字节空文件；
  - `room_identity_mismatch`：中途确诊错录主播；
  - `identity_unconfirmed`：严格模式下运行期身份未确认超时。

### 4.7 切片空档策略、音画同步指标与 F-09 工程取舍 (F-09)

#### 4.7.1 工程取舍定位明确
- **已接受工程限制 (Accepted Limitation)**：
  - 现阶段保留“每 30 分钟重启一次 scrcpy 重启录制”的架构设计，将重启过程中的秒级物理空档作为已接受工程限制，不承诺未经验证的零间隙；
  - **纠正确定性表述**：彻底删除“重置 PTS 必然消除或阻断音画累积漂移”的断言；统一界定为：**周期重启是缓解长时音画累积漂移的候选措施，其实际效果必须通过实测数据进行验证**。

#### 4.7.2 科学区分三大度量指标
严格区分以下三大独立指标，禁止混淆概念与公式：

1. **切片间隙耗时 (Slice Boundary Gap)**：
   - 进程切换耗时：$\Delta t_{\text{call}} = T_{\text{start}} - T_{\text{stop}}$（主机单调时钟 `time.monotonic()` 测量）；
   - **真实媒体内容缺口**：$\Delta t_{\text{gap}}$。**严禁将两段分别归零的本地 PTS 直接相减**！必须利用测试源携带的公共单调时间码（Timecode）或可识别音视频脉冲序列，比对切片 $N$ 末帧时间码与切片 $N+1$ 首帧时间码；
2. **轨道时长差 (Track Duration Delta)**：
   - 定义：$|\Delta T_{\text{track}}| = |T_{\text{video}} - T_{\text{audio}}|$；
   - 作用：仅反映切片封口时两轨物理时长差异，属于容器层面的辅助诊断指标，**绝对不等同于音画同步**；两条轨道时长完全相同的视频，画面与声音也可能存在固定或动态的严重延迟；
3. **音画同步偏移与累积漂移 (AV Sync Offset & Cumulative Drift)**：
   - **音画同步偏移**：$\Delta T_{\text{sync}} = T_{\text{audio\_event}} - T_{\text{video\_event}}$。在录制结果中，同一物理同步事件（如闪光帧与声音哔声脉冲）的呈现时间戳差；若测试源自身存在固有基线延迟，需扣除或标明该基线；在切片的开头、中间、末尾分别采样；
   - **累积漂移**：$\text{Drift}(t) = \Delta T_{\text{sync}}(t) - \Delta T_{\text{sync}}(t_0)$，反映音画同步偏离随录制时间的单调恶化趋势。

#### 5.2 长稳验收规约 (Long-term Stability Benchmarks)
- **试验环境与时长**：
  - 单实例基准长稳：连续录制至少 **8 小时**；
  - 多实例并发长稳：2 路与 4 路并发录制至少 **12～24 小时**；
- **监控指标与通过门槛**：
  - **不可见停录次数**：严格为 **0 次**；
  - **无效内容时长占比**：$\le 1.0\%$（除正常切片物理空档外）；
  - **切片终态事件一致性**：`segment_started` 与 `finished/aborted` 成对率严格为 **100%**；
  - **自愈恢复成功率**：偶发故障自愈成功率 $\ge 90\%$，超限时能准确以退出码 30 退场；
  - **资源稳定性**：内存泄漏速率斜率经线性回归拟合后趋近于 0（无句柄与缓冲区泄漏），CPU 占用稳定在单路基线浮动区间内；
- **指标状态标注**：
  - 目标值（Target）、待标定参数（如 $\theta_{\text{dynamic}}=0.3\%$、`recheck_timeout_sec=30s`）与实测数据在实机验证报告中分列，不作未经实测的虚假保证。

## 6. 风险、假设与已知物理限制 (Risks & Known Limitations)

1. **已接受的工程限制**：
   - **中断式切片物理空档 (F-09)**：当前架构接受切片重启过程中的物理空档作为消除长时音画累积漂移的候选措施；其实际效果要求通过时间码与同步偏移精确度量，暂不引入高复杂度的内存抓流解复用方案；
   - **身份核验覆盖窗口限制**：运行期周期身份复核只能将误录风险限制在检测周期内（2～3 分钟），无法实现严格“零帧级”误录杜绝；通过追加历史切片质量警告标记降低漏网风险。
2. **外部不可抗力风险与应对**：
   - **抖音极验滑块与短信强制登录**：Worker 不做对抗破解；触发后由门禁严格阻断（退出码 15）并通知调度器隔离，生产环境以人工预登录账号为基线防线；
   - **抖音 UI 深度混淆**：若无法获取稳定主播标识，系统诚实判定为 `UNCONFIRMED` 并默认严格阻断，仅在显式逃逸开关下由业务方承担风险录制。
