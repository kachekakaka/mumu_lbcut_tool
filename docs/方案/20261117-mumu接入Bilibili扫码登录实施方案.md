### 1.2 已核实的现状

- mumu 为 Windows/Python 3.11、FastAPI 后端和 Vue 3/TypeScript/Element Plus 前端。后端入口为 `src/orchestrator/server.py`，现有五页路由在 `web/src/router.ts`；没有账号页面、Core 客户端或 Core 托管功能。
- 后端在单台录制机运行，可显式开放局域网；现有启动机制负责服务就绪后可选打开浏览器。账号接入不能阻塞调度线程、开机录制或既有服务退出流程。
- 现有 `web/src/commands.ts` 的操作记录主要在内存中；部分中断操作提示重新生成请求编号。扫码不能直接套用这种恢复语义。
- Core 已有扫码会话、PNG、取消、恢复、账号摘要及能力查询；登录只需 Core API 进程，不需要额外启动上传 Worker。`gui-bridge-v1` 只是一类客户端标识，不是认证。
- Core health 当前报告 API/数据库就绪及 Worker 状态，不提供数据目录身份；capabilities 报告图形登录能力，也不提供服务实例与目录的绑定证明。
- 前次只读访问本机默认 `127.0.0.1:8765` 的 health/capabilities 均连接拒绝，未发现匹配的 Core Server 进程。这不是对所有端口或机器的扫描结论。
- 新机器扫码构建为 `bue-0.2.0-dev1`，已有运行配置未自动升级。服务端记录的合成测试不等于 mumu 真实界面或真实扫码通过。

### 1.3 本次包括与不包括

包括账号页面、同机后端桥接、单个明确部署的 Core 启动/复用管理、非敏感请求恢复、二维码内存呈现、账号摘要、必要测试和文档同步。

不包括投稿、T16 Webhook、上传 Worker、自动上传或删稿、Cookie 导入导出、凭据复制、读取 Core 数据库/私有凭据目录、修改对接项目/引擎、任意远程 Core、用户体系或反向代理接入。`upload_enabled` 继续为 false，不因登录可用而开放现有上传占位功能；Core 的 `upload_ready=false` 也不应被误用为禁用扫码的条件。

本方案首版只管理一个明确配置的 Core 部署。已有库不迁移、清空或重建，不把版本错误转成“自动使用新空目录”。

## 二、页面和后端结构

### 2.1 使用流程

1. 在侧栏及移动布局导航中新增“账号”，路由 `/accounts`，使用现有 Element Plus 的表格、提示及弹窗样式。
2. 本机打开账号页时，先展示接入服务状态；没有部署配置时显示一次性配置入口，服务未启动时提供“启动登录服务”，不要求用户打开终端。点击“添加 Bilibili 账号”也可触发同一受控启动流程，启动完成后再创建会话。
3. 账号列表显示昵称、MID、登录账号状态和阻塞原因，操作为“重新登录”“查看登录进度/恢复”。首版不新增账号启停接口，保留 Core 返回的手动停用状态。
4. 新建/重新登录弹窗展示二维码、当前可证实阶段、当前操作错误和服务连接状态；取消、恢复、重新申请按钮按服务端允许动作显示。
5. 关闭弹窗只释放页面中的图片与观察资源；重新进入通过已保存关联和 Core 查询找回原会话。成功后刷新账号摘要，无需再次登录。
6. 账号服务状态与录制调度状态分开呈现。Core 不可用只禁用账号相关操作，不让五个录制页面误报调度断开。

### 2.2 职责与数据流

页面只请求 mumu 自己的账号接口；mumu 后端用固定客户端标识和自身构造的 HTTP 请求访问同机 Core。浏览器不直连 Core，不修改 Core 的 CORS、Host 或浏览器头限制。

新增模块拟置于 `src/orchestrator/`：

| 模块 | 拟负责内容 |
| --- | --- |
| `bilibili_api.py` | 账号路由、来源检查、严格 DTO、二进制 PNG 响应与安全错误映射 |
| `upload_core_client.py` | 固定 Core URL/路由白名单、超时、响应大小与类型检查、契约校验；不提供任意 URL 代理 |
| `upload_core_runtime.py` | 配置校验、进程与端口归属核验、互斥启动、就绪检查、复用及失联状态 |
| `upload_core_host.py` | 无窗口的长期宿主，只运行固定 Core Server 入口并保存启动身份，不导入其数据库或直接执行引擎 |
| `account_login_store.py` | mumu 自己的非敏感请求日志、Core 部署关联和会话索引；不存 Core 凭据或二维码 |

`server.py` 只挂接模块生命周期和路由，`cli.py` 增加可选部署配置路径；不将登录轮询放进 `Scheduler.tick()`。后台启动/网络操作使用独立有界任务，所有磁盘事务均短时执行，不持有调度器锁等待 Core。

前端新增 `views/AccountsView.vue`、`components/BilibiliLoginDialog.vue`、`components/CoreConnectionSettings.vue`、`api/bilibili.ts` 和 `bilibiliLogin.ts`。账号会话状态单独管理；公共 JSON 客户端可复用基础错误类型，但 PNG 使用专用二进制读取，不送入 JSON/文字错误解析器。

## 三、边界一：Core 归属、版本与无终端启动

### 3.1 明确配置，不猜目录

部署配置拟保存于 mumu `data_dir` 下的 `upload-core/profile.json`，由本机账号页配置；可由 CLI 显式指定另一配置文件，但不以终端操作作为日常使用前置。配置仅包括部署 UUID、Core 虚拟环境 Python 绝对路径、明确的 `http://127.0.0.1:<端口>`、Core 数据目录和 Bilibili 配置文件路径等非凭据字段。

- 禁止页面提交任意命令、启动参数、引擎命令或请求地址；启动命令固定为所选已安装 Python 的 `-I -m upload_platform server`，通过专用环境传递 Core 配置，关闭 shell 展开。
- 校验 Python/配置文件存在、目录绝对化与 Windows 路径别名；检查 Bilibili 部署配置的结构和能力文件，不读取私有状态目录内的文件。引擎最终可用性以 Core capabilities 为准，mumu 不直接运行引擎。
- 已有数据目录必须由明确配置选择，不能从目录名、默认端口或示例路径猜测。首次需要新部署时，在页面明确显示新目录并由用户选择“新建独立部署”；不得在连接/版本错误时暗中另建。
- 不自动安装、更新 Core/引擎或覆盖其配置。若只有旧部署，显示所缺能力与需要的新版本配置；有活动维护/执行时不切换部署。缺少运行环境或部署路径属于必要输入，应在实施现场发现后集中说明。
- 尚未生效的错误配置可在页面修正；已有 Core 运行期间配置只读，首版不提供在线切换部署。GUI 白名单不能完整查询所有上传活动，不能仅因扫码列表为空就认定可安全切换；既有部署升级/更换先由其运维流程完成，再核对本接入层关联。
- 接入状态、配置校验结果和错误帮助均在页面呈现。错误版本只报确定事实；Core 在提供 health 前退出且没有可靠原因时，报告“启动失败/配置或运行环境待核对”，不猜成数据库损坏。

### 3.2 可复用的证据

先用以下三项证据核实部署归属，再决定可以开放哪些操作。

1. 有本接入层此前形成的受控启动记录，绑定部署 UUID、规范化目录、配置修订、宿主与 Core 的 PID/创建时间、Python 路径、固定启动参数及机器启动身份。
2. 操作系统查询证明当前监听者就是受控创建记录中的 Core 或已明确登记的子进程。宿主仍运行时一并核验其身份，宿主退出后的处理见第 3.3 节。不能只比较 PID 或进程名称。
3. 当前配置与启动快照相符，未在活动会话下切换目录、端口或引擎配置；匹配值直接比较，不引入内容指纹算法。

| 核验结果 | 页面与后端允许的操作 |
| --- | --- |
| 归属未证实 | 只显示本机启动诊断，阻止所有账号、会话及图片读写。 |
| 已证实归属，但 health 未就绪或扫码协议版本、平台无法确认兼容 | 保留原操作关联，显示服务状态或协议错误。允许重新检查原服务，暂停扫码业务调用。 |
| health 就绪、协议兼容，`gui_login.available=false` | 复用原 Core，显示能力不可用原因。允许读取摘要、原会话及其仍有效的 challenge。用户可按最新会话的 can_cancel / can_resume 对原会话操作，以 Core 回执为准。禁止添加、重登、重新申请二维码及重放未知结果的创建请求。 |
| 同上且 `gui_login.available=true` | 开放新建与重登，仍执行第五节的占用和原请求重放规则。能力恢复本身不发起创建。 |

启动记录只是本机受信任接入层的运行证据，不是防恶意本机进程的认证。其文件只由当前用户/服务账户维护；不接受浏览器上送 PID 或“我确认这是正确目录”替代 OS 核验。

端口已有服务但缺少可靠归属记录，即便 health/capabilities 相符，也显示“端口被未纳管服务占用，未连接账号数据”；不杀进程、不改端口试探另一份库、不读取 Core 数据库核验身份。任意手工启动的历史 Core 暂不能自动纳管，这是现有外部契约的限制。若必须无条件接管这种服务，应交由 fileUploadPlatform 增加可验证的部署身份契约，不能在 mumu 伪造证明。

### 3.3 启动、竞争与退出

- 启动只由本机用户点击账号功能触发；mumu 启动时可只读探测，不能因为后台轮询就创建新服务或新扫码会话。
- 对同一 Windows 用户的单部署启动使用跨会话的 OS 互斥和持久启动意图；多标签页、两个 mumu 进程和重复点击加入同一次启动，不生成多个 Core。规范化目录和端口登记为唯一绑定，拒绝用同一目录创建另一份托管配置。
- 宿主先可靠记录启动意图，创建无窗口 Core 子进程后记录身份；未完成身份记录的启动窗口进入待核对状态，不根据等待超时断言旧进程已退出。实现前针对“进程已建、记录未写”窗口做专门验证。
- 初始预算：每次 health/capabilities 请求最多 3 秒，启动等待最多 30 秒，单次按钮请求快速返回启动状态；超时只表示未就绪，不作为终止进程或开启第二份服务的依据。页面提供重新检查原启动。
- TCP 端口预检查与真正绑定之间仍可能竞争。最终必须再次核对监听进程归属；未知进程抢占时阻断。没有记录的进程不能因可执行文件名相同就被停止。
- Core 是可复用的长期本机服务。关闭弹窗、关闭浏览器、停止 mumu 调度均不自动停止 Core 或取消登录；宿主不使用“mumu 父进程退出即杀 Core”的策略。已有上传/维护可能由其他客户端使用，首版不提供停止 Core 按钮。
- mumu 重启后先恢复绑定记录和 OS 身份核验，再连接原服务。确认进程退出且端口空闲后，才允许用户重新启动同一部署；不删除或迁移旧库。身份不可确认时保留待核对，不能循环重启。
- 本单例约束覆盖使用同一受控宿主的本用户部署，不声称能阻止其他用户或外部手工命令绕过管理启动相同数据目录；所选目录不得同时交给其他独立启动器管理。

同一 Windows 用户的启动登记统一放在 `%LOCALAPPDATA%/mumu_lbcut_tool/upload-core/registry.sqlite3`。各 mumu 数据目录里的 profile 仅引用部署。持有该用户跨会话启动锁的一方，在共享登记事务中校验部署 UUID、规范化 Core 目录和监听地址的唯一绑定。不同 mumu 目录引用同一绑定时读取同一启动记录，目录或端口与另一绑定冲突时显示冲突。登记不可读或写入失败时暂停启动。

| 登记阶段与重新检查所得证据 | 在原部署上的恢复动作 |
| --- | --- |
| 已写意图，尚未写入“可能创建子进程” | 宿主必须先持久提交下一阶段才能调用进程创建。接手方取得锁、确认原启动者已退出且端口空闲后，可结束本次意图并允许用户重启。 |
| 已标记可能创建，尚无可靠子进程身份 | 原宿主仍在时等待其提交身份。宿主已退出时，即使暂时没有监听者也保持待核对。页面展示部署、端口、启动时间和待查原因，交由本机运维确认原启动器与可能的子进程均已退出。无法辨认进程时，可在安排好录制及其他任务的维护窗口后重启 Windows。 |
| 已记录子进程身份 | 重新核对进程创建时间、机器启动身份、配置与监听归属。已登记 Core 仍存活且监听匹配时可复用，原宿主已退出也以完整的受控创建记录核验 Core。仍在启动则等待，确认相关进程均已退出且端口空闲才允许重新启动。 |

“重新检查原启动”只读现场并在锁内更新登记。对缺少子进程身份证据的记录，机器启动身份已改变可证明上一轮进程均已退出，还须核对绑定与当前端口空闲，方可结束旧意图并允许显式启动。仅有人工确认、等待超时或端口空闲均不能解除此状态。新出现的未知监听者按第 3.2 节处理。

## 四、边界二：账号接口只允许本机受信任页面

首版选择 **账号相关页面能力仅限运行 mumu 后端的本机浏览器**。局域网访问原五页不变；远端进入账号页只显示“请在服务所在电脑打开本机控制台”，不返回账号摘要、二维码、会话信息或部署路径。若希望笔记本远程操作 250 的账号登录，需要另行明确受保护的远程授权方案，不能把现有录制访问权限直接当成账号权限。

账号接口统一执行以下约束，而非只在前端隐藏按钮：

1. 校验真实 TCP 对端为 loopback，不信任代理转发头；相关服务配置禁用代理头对 client 的解释。Host 必须为配置对应的明确 loopback 主机和端口，拒绝重绑定域名、错误 Host 和转发头。
2. 浏览器 Origin/Fetch Metadata 必须与本机控制台同源；拒绝跨站、嵌入式第三方页面和跨源访问，不新增通配 CORS。缺少浏览器头的本机测试客户端也不能绕过下一项访问凭证。
3. 受保护的本机 bootstrap 返回短期随机页面访问凭证，仅存前后端内存。账号 GET、PNG 和修改请求均要求专用请求头携带该凭证；凭证不进入 URL、持久存储或普通日志。bootstrap 本身受对端、Host、来源限制，不能由远端取到。刷新重新获取凭证，服务重启使旧凭证失效。
4. 修改请求还要求 JSON 和 UUID 幂等编号；账号页面使用防嵌入策略。开发联调优先用构建后由 FastAPI 托管的同源页面，不为 Vite 代理放宽生产检查。
5. 凭证只隔离意外网页请求，不声称能隔离恶意本机用户/进程；本项目没有引入多用户账号权限系统。

凭证到期或 mumu 重启时，账号接口在转发前返回专用的凭证失效错误。仅此错误触发页面重新 bootstrap，每个页面同一时间只续领一次，共享结果给并发请求。旧凭证的迟到响应不能使新凭证失效。来源、Host 或权限检查失败直接提示原因。续领失败或补发后再次失效，暂停轮询、清图、保留操作关联，提供“重新连接”。

续领成功先查询原操作及已知会话。仍在观察的只读请求可重取一次，图片须重新核对当前 challenge。创建、取消、恢复都先检查对应操作记录，已受理则展示最新会话，结果未知则走第 5.2 节显式重试。确知凭证检查拦截、原请求未转发且用户操作仍有效时才可补发一次，沿用原动作、正文和 Key。关闭弹窗或已改变观察对象时丢弃旧的页面工作。

mumu → Core 使用独立 HTTP 客户端：固定 `127.0.0.1` 地址、不使用环境代理、不跟随重定向、只允许本功能的会话/摘要/健康/能力路由。请求头由 mumu 自己构造，不转发浏览器 Origin、Cookie、授权头或转发头；这是受控后端调用，不是向浏览器开放 Core 任意代理。

普通 Core 请求初始连接上限 2 秒、整体上限 10 秒，健康/能力探测按第三节收紧为整体 3 秒；读响应、重试和错误处理都不能突破本次截止。修改请求超过截止归为结果待确认，不能当成未执行。配置、状态和图片请求的并发数量有界，不把 Core 慢响应转化为 mumu 调度阻塞。

## 五、边界三：幂等、刷新和服务恢复

### 5.1 非敏感持久记录

新增 mumu 自己的 `data_dir/upload-core/account-login-bridge.sqlite3`，只记录桥接请求和关联；不改现有调度库格式，不读取或复制 Core 的 SQLite。新库按当前 schema 创建，已有不匹配文件拒绝打开，不自动迁移。

允许保存：部署 UUID/配置修订、mumu 操作 UUID、Core 幂等 Key、固定动作与规范化请求正文、目标账号/会话 ID、创建时间、是否已经可靠取得响应及安全错误码。请求正文只来自登录、取消、恢复的字段白名单。可保存非敏感会话索引以便按 ID 查询，账号摘要与当前会话状态始终向 Core 重读。

禁止保存：完整 Core 原始响应、二维码 PNG/base64/扫码 URL、challenge 对象、Cookie/token/凭据路径、页面访问凭证。请求日志不是第二套 Core 状态库，也不把 mumu 本地的“已发送”当作登录成功。

### 5.2 发送与重复点击

- 页面在发送前生成 UUID，并将该 UUID 和动作/目标的非敏感恢复标记写入 sessionStorage；不能保存会话原始响应或图片。浏览器存储不可用时明确提示恢复能力受限，不默默换号。
- 后端先事务保存原请求和固定 Core Key，再发送 HTTP。保存失败不向 Core 发请求。同一 Key/同一正文回到原操作；同 Key/不同正文拒绝。不得因请求超时或取消页面 fetch 就生成新 Key。
- 每个账号只允许一个本接入层未解决的登录操作；“新增未知账号”首版也只允许一个未解决操作。后端事务门禁处理多标签页使用不同 Key 的重复点击，返回已有操作关联，不只靠按钮 disabled。Core 自身互斥继续作为最终裁决。
- 创建/取消/恢复分别使用独立操作 Key；同一次取消或恢复的重试复用自己的 Key。创建结果不明时，先找回 session_id，不能凭账号 ID 猜测要取消哪次操作。
- 对响应丢失保持“提交结果待确认”。前端刷新后先查 mumu 原操作记录；已知 session_id 则 GET 原会话，未知则允许用户“重试原请求”，后端使用持久记录的原 Key/正文重放。后端不在无人页面的启动阶段自动重发可能首次生效的创建 POST。
- mumu 在发往 Core 后、保存回包前崩溃时，靠原请求日志重放恢复；不能使用现有录制命令的“中断后重新操作/新编号”逻辑。

创建请求占用目标账号或“新增未知账号”的唯一位置。后端将下表中的证据和占用变化写入同一事务。取消、恢复有各自的请求记录，它们的受理或拒绝不能单独解除原会话占用。

| 创建请求的证据 | 占用与下一步 |
| --- | --- |
| 已登记，确定尚未发送 | 占用目标。发送方先持久标记“可能已发送”再调用 Core，同时只允许一个发送方处理此操作。确认尚未进入发送阶段且已阻止后续派发时，可撤回并释放。 |
| 首次尝试收到契约可确认没有创建会话的拒绝，且没有更早的结果未知尝试 | 记录确定拒绝并释放本地占用。若 Core 提示已有维护，只报告该冲突，仍由 Core 决定何时能再创建。 |
| 可能已发送，超时、回包丢失、写回前崩溃或响应无法判定 | 保留占用和原 Key。即使后续重放被拒绝，也保留此前结果未知的事实。页面列出待确认操作供重新打开后的用户找回。 |
| 取得原请求对应的 session_id | 记录关联并查询该 ID。原会话仍在进行、查询暂时失败或取消仅被受理时继续占用。 |
| 原会话给出可靠终态 | 事务记录终结并释放占用，保留关联供查询。摘要刷新失败不阻止释放。重新申请依照原会话 can_retry，下一次独立的登录动作使用新 Key。 |

Core 创建入口先检查引擎能力，再进入幂等处理。原创建回包丢失后，若重放返回能力不可用，页面显示“原登录结果待确认，扫码能力恢复后可重试”。保留原 Key 和正文，等能力恢复后由用户重试以取回同一 session_id。长期无法找回则保持占用并报告缺少关联证据，不能按相同账号、时间或活跃列表猜测会话，也不提供强制解锁。

### 5.3 找回、乱序与切换

- 页面打开时合并本地已知会话 ID 与 Core 活跃列表；已知会话逐个 GET，以找回关闭页面期间已完成的会话。活跃列表最多 100 项且不代表全部历史，不能因列表未包含某 ID 就认为它不存在或允许重建。
- 查询频率初始 1 秒，网络异常退避至 2、5 秒；一次只保持一个会话查询在途。重复进入页面不叠加轮询。暂停显示不发送 cancel。
- 前端每次打开/切换会话设置观察代次，并同时核对部署绑定、session_id、revision、challenge_id。旧代次、较低 revision、旧 challenge 的图片或状态迟到后直接丢弃。
- revision 约束会话演进，不是整个响应的版本号：当前 Core 会按时间/内存状态动态隐藏 challenge，终态 account_summary 也可能独立变化。相同 revision 时允许较新查询更新这些动态字段；按本地请求序号丢弃旧查询回包。已撤销或超时的 challenge 不被迟到响应重新显示；phase/outcome 在同 revision 下矛盾才按协议异常重新核对。进入终态后不允许迟到的非终态重新显示二维码。
- 切换部署配置前必须确认本桥接不存在未解决请求、Core 原会话无未完成操作。失联时无法证明结束，拒绝切换；旧记录不能自动改绑到新目录或另一 Core。
- Core 服务中断立即清除图片，保留非敏感关联并显示失联。重连完成归属核验后 GET 原会话，不重建旧二维码、不自动再次扫码。仅在 `can_resume` 允许且用户点击时 POST 恢复；未知原进程或凭据发布状态交给 Core，不能从 PID 消失、deadline 或图片消失推断已结束。
- “重新申请二维码”必须等原会话可安全重试，再以新 Key 创建；`recovering`、取消已受理但未终结、结果待确认均不能提前开新会话。

## 六、边界四：登录成功不等于账号可用

Core 的阶段、结果和账号摘要各自按其 Schema 校验，不在前端重新推导账号启停。

| 观察 | 页面含义和动作 |
| --- | --- |
| 创建请求被受理 | 正在准备登录；不能显示登录成功 |
| 等待确认且有有效 challenge | 展示当前二维码；只说明等待手机确认，不虚构已扫码或平台已授权 |
| 核验身份、等待原账号、提交中 | 显示对应等待原因，不重复创建会话；扫码确认仍不算最终成功 |
| 取消请求返回受理 | 显示取消处理中，立即清除图片；继续查询原会话，成功竞争时允许显示最终实际成功 |
| `outcome=succeeded` | 才显示登录成功，随后读取账号摘要；以摘要中的 id/reference 供后续功能引用 |
| 摘要 `ready` | 显示当前账号可用；不据此开放尚未接入的投稿功能 |
| 摘要 `disabled` | 显示登录成功但账号已手动停用，不自动 enable |
| 摘要 `blocked` | 显示登录成功但仍有阻塞，保留全部 block_reasons，不擅自清除其他维护/限制 |
| 成功后摘要刷新失败 | 保留已确认的登录成功，账号可用性显示待刷新，不回退成登录失败或默认 ready |
| `cancelled/expired/failed` 或可恢复状态 | 展示 Core 的可靠结果和稳定错误码，按钮依据 can_cancel/can_resume/can_retry，不根据文案猜动作 |

本地倒计时对应 `deadline_at`，不是平台二维码到期证明。到时先清图并重新查询，不擅自把 outcome 设为 expired。当前协议未知的平台状态或网络错误不冒充“已扫码”“扫码过期”。账号昵称/MID/错误文字作为普通文本呈现，不作为 HTML 执行。

## 七、二维码与 mumu API 适配

### 7.1 图片和数据处理

- 只通过已查询会话的 challenge 读取 Core PNG；验证 image_path 对应固定会话路由及当前 challenge，不能按返回任意 URL 取图。mumu 对浏览器返回本域图片接口，不暴露 Core 地址或扫码 URL。
- 图片仅在有界内存中转发和渲染。按当前 Core 上限限制 PNG 为 128 KiB，核对 Content-Type、PNG 标识及声明大小；分块读取过程中也执行上限。其他 JSON 响应限制为 1 MiB；超限或契约不符报错，不把原文显示出来。
- 图片、会话和账号敏感响应均设置 no-store，并禁止代理缓存；前端 fetch 使用 no-store、Blob/object URL，图片加载/切换/关闭/取消/失联/终态时撤销 URL 和清空引用，不写 localStorage、IndexedDB、Service Worker 或磁盘。
- 图片 409 表示尚未就绪，410 表示当前图片不可继续提供；两者都重新查会话，不自动换 Key。图片获取过程中发生取消或 challenge 改变时，旧回包不能再显示。
- 普通应用日志只写动作、非敏感操作关联和稳定错误码；不写请求/响应体、PNG、完整 challenge URL、访问凭证或 Core 原始异常。Core 子进程标准输出不落普通日志；启动监控仅留有界的安全状态信息，不能为了调试把原始流全量保存。
- 界面截图和验收录屏不得包含真实二维码；使用合成 QR 做视觉证据，真实扫码证据仅保留脱敏后的结果摘要和必要状态。

### 7.2 mumu 路由组织（拟定，非现有接口）

在现有 `/api/v1` 下新增 `/bilibili` 子路由，全部由第四节保护：

| 路由组 | mumu 职责 |
| --- | --- |
| 本机 bootstrap | 发放短期页面访问凭证；不触发 Core 启动 |
| Core 配置、状态、ensure | 本机配置、查询状态、幂等地发起同一受控启动；不接收命令字符串 |
| accounts | 只读 Core summary，限定 Bilibili，不暴露凭据或完整账号内部对象 |
| login-operations | 创建/找回 mumu 持久请求关联、原请求重试；与现有录制命令队列分开 |
| login-sessions、单会话详情、cancel、resume | 受控调用外部约定接口，校验状态和修改请求 Key |
| 单会话 PNG | 校验当前 session/challenge，二进制 no-store 响应，无通用代理能力 |

具体 mumu 响应模型在实施时写入 `docs/控制台接口契约.md`；仅编写本方案阶段不提前将其写成现行契约。修改接口统一保留现有 mumu 错误形状；请求是否受理、Core 会话是否成功、账号是否可用为三个独立结论。

## 八、实施顺序和文件范围

1. **核对现场配置与契约**：读取明确的非敏感部署配置，查询 health/capabilities，核对新引擎配置是否已部署。证据只读不足时不猜；缺 Python/部署路径/目标机器等必要输入再集中询问。
2. **接入层与日志**：增加上述后端模块、独立请求库、DTO、超时和来源保护。先用合成 Core 验证原请求重放、非敏感持久边界及图片迟到丢弃。
3. **托管启动**：接入 `server.py`/`cli.py`，实现跨会话互斥、启动记录、端口/PID/目录归属核验和无窗口宿主；真实子进程验证后才用于实际部署。
4. **页面**：修改 `web/src/router.ts`、`App.vue`，新增账号页面、配置和扫码弹窗、专用 API 与会话状态模块。录制 `commands.ts` 保持原语义，账号不复用其重新发号路径。
5. **联调**：构建后用 mumu 实际页面连接合成 Core，再连接实际兼容 Core，由用户手机扫码；真实扫码时只给用户界面入口，不要求传 Cookie 或运行命令。
6. **文档和收尾**：实施阶段更新运行说明、设计说明、mumu 接口契约、tests/README、必要待办及独立验证记录；当前方案同步状态。全部必要验证完成后归档，否则明确待验证项。保留失败材料，不自动提交或推送。

现有录制库、Core 库和凭据目录不改；前端上传占位组件不接投稿。若新增依赖，按实际需要更新 requirements 或 web/package.json/锁文件，不预先引入 SDK、桌面壳或另一套服务框架。

| B16 | 回归与结束状态 | 相关后端测试、前端组件/状态测试、类型构建；录制五页及启动就绪行为按影响回归，无上传、无误停现有 Core |
| B17 | Windows 上同一用户、不同 mumu 数据目录引用同一部署，分阶段中断宿主 | 两个入口只生成一次受控启动。分别在写意图后、标记可能创建后、创建后写身份前及写身份后中断。验证可安全重启、证据不足继续阻断、已登记存活 Core 可复用三条路径。在隔离环境验证跨系统重启后重新检查，端口空闲允许显式启动，未知监听者仍阻断。 |
| B18 | 已有会话时扫码能力从可用降为不可用，再恢复 | 用兼容协议驱动实际账号页。摘要与原会话仍能读取，取消及恢复依据各自会话的允许标志和实际回执，创建调用数不增加。恢复能力后须由用户发起创建。换成未知归属或不兼容协议时不能沿用上述业务权限。 |
| B19 | 确定拒绝与历史结果未知分别到达同一错误分支 | 用桥接库和可控制回包的 Core 分别验证首次明确拒绝释放占用、原创建已生效但丢包后重放被能力检查拒绝仍占用。重开页面及换标签页均找回原操作，能力恢复后用原 Key 重放仅得到原会话。持续失联仍保留占用，可靠终态后允许新的独立登录。 |
| B20 | 页面长开使凭证过期，轮询、图片与修改请求交叠，或 mumu 重启 | 实际页面验证并发失败只触发一次续领，旧图及旧凭证的迟到响应被丢弃。已受理操作先查原记录，未转发的有效动作至多补发一次且 Key 不变。结果未知不自动重发。续领失败后停止轮询、可手动重连，跨站或错误 Host 不触发续领。 |

合成协议、真实 Windows 进程、mumu 实际浏览器、真实平台扫码分开记录。无窗口须验证进程实际没有控制台窗口，不以创建参数存在代替；二维码展示须验证真实页面能呈现，不能只看 PNG 接口 200。真实扫码必须由用户手机完成，没有该结果时不得把整个接入标为完成。

## 十、风险、完成条件和当前交付

- 当前 Core 不暴露部署身份，首版只能复用可验证的受控实例；未知手工实例是明确阻断条件，不是假装已解决的接口缺口。
- 账号入口本机限定是本方案拟采纳的安全边界。远端账号操作需求若出现，先修订访问方案和验收，不能临时放宽来源检查。
- 外部源码/能力和实际部署可能不同；`bue-0.2.0-dev1` 是本轮已知支持构建，不等于已安装。实施以能力协议和现场配置双重核验，不只匹配版本名字。
- 保留 Core 进程会使已创建登录在关闭 mumu 后继续至终态，这是关闭页面不取消的预期；UI 必须说明，下一次按原关联恢复。
- 必要验证通过、真实扫码完成、文档已承接、未验边界明确后才能完成归档。其他机器或未授权远程部署不自动算入已验范围。
- 发现必须改 Core 契约时，提供路由/模型差异、脱敏复现步骤、实际响应与最小所需字段，交由对应项目处理；不擅改对接仓库，也不为绕过缺口读取数据库或凭据。
