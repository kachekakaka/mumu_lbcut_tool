## 问题陈述 (Problem Statement)

在多模拟器多路直播录播与视频发布运营中，运维人员面临以下核心挑战：
1. **多模拟器缺乏自动化纳管与并发编排**：本地运行的多台 MuMu 模拟器实例需要人工逐个匹配 ADB 端口、分配直播间并手动启动录制，极易发生实例冲突或漏录；
2. **主播开播时间离散导致人工蹲守成本极高**：关注的数十个抖音主播开播时间随机，人工刷新监控耗时费力且容易错过黄金直播片段；
3. **本地物理算力受限引发资源争抢**：受宿主机 GPU/内存限制，模拟器多开路数存在上限（通常 3~4 开）；当多个重点主播同时开播时，缺乏平稳的先进先出排队机制，容易导致系统满载卡死；
4. **抖音免登录风控导致录播中断与单点故障**：某台模拟器偶发免登录弹窗或登录强阻断（退出码 15）时，若单机原地死磕会导致整场直播漏录，缺乏“自动秒级切机漂移 + 后台平滑复位备用”的容灾韧性；
5. **切片大文件缺乏自动化下游交付链路**：Worker 每 30 分钟落盘的高清切片视频缺乏与外部上传服务（如 biliup 服务）的标准化投递通道，人工拷贝与手动投稿费时易错，且切片投递状态缺乏可视化跟踪。

## 解决方案 (Solution)

构建基于 **FastAPI 的一体化单进程录播调度平台（Orchestrator Host）**：
1. **免构建单进程交付**：集成 RESTful HTTP API 与内嵌轻量现代化单页 Web 控制台（Single-page WebUI），一个命令直接启动运行，无额外 Node.js/Nginx 运维与部署负担；
2. **四大可视化核心控制区**：
   - **模拟器槽位墙**：卡片化直观展示每台 MuMu 实例状态（空闲/录制中/维护中/阻断中），提供一键唤醒、后台 ADB 强杀重置与解除阻断；
   - **主播监控大厅**：统一维护监控主播列表，实时展示开播状态指示灯，支持 YAML 批量导入、开关自动录制与即时开录；
   - **录播任务监控**：实时掌控正在录制任务的时长、心跳与渲染帧率，支持平滑封口停止；
   - **切片与上传记录**：全量罗列 MP4 切片产物，展示外部投递状态，支持一键重新推送上传；
3. **双模任务摄入与 FIFO 先进先出排队**：底层高并发定时轮询监控列表，结合外部 HTTP API 即时派单；当实例满载时，新开播任务进入 Pending 队列等待，绝不粗暴掐断在播录制；
4. **动态切机漂移与后台 ADB 复位机制**：遇到登录强阻断时，若有空闲健康实例则秒级漂移任务继续录制，原故障实例在后台执行 ADB 强杀抖音应用（`am force-stop`）复位备用；若无空闲实例则原地重启自愈；
5. **标准 Webhook 切片交付对接外部上传服务**：本地严禁主动物理删除切片，通过标准 HTTP POST Webhook 将切片绝对路径与元数据传给外部上传服务（如 biliup 服务），支持“切片即刻投递”与“整场下播聚合投递”双模配置与失败重试。

## 用户故事 (User Stories)

1. 作为录播运营人员，我希望在 Web 控制台直观看到所有 MuMu 模拟器实例的卡片状态（运行中、空闲、录制中、维护中、阻断中），以便于一目了然掌握本地算力水位并进行单机运维。
2. 作为录播运营人员，我希望能够通过编辑本地 YAML 配置文件或在 Web 界面批量粘贴抖音房间号/口令/链接导入监控列表，以便于快速纳管几十个重点主播。
3. 作为调度系统，我希望每隔 15~30 秒以高并发线程池快速批量探测所有监控主播的开播状态，并在发现新开播时自动调配空闲实例拉起录播 Worker，以便于实现开播秒级全自动开录。
4. 作为录播运营人员，我希望在临时有突发录制需求时，能在 Web 界面或通过 HTTP API 直接下发单次即时录制任务，以便于灵活应对计划外的突发直播。
5. 作为调度系统，我希望在同时开播的主播数超过当前可用模拟器数量时，以先进先出（FIFO）规则将多出的任务放入等待队列，以便于平稳有序地等待空闲实例而不打碎正在进行的录制。
6. 作为调度系统，我希望当某个实例上的 Worker 上报登录强阻断（退出码 15）时，若有空闲健康实例则立即将录制任务漂移到该备用实例，以便于最大程度抢救正在直播中的宝贵素材。
7. 作为调度系统，我希望将发生阻断的故障实例置为维护态，并在后台自动执行 ADB 强杀抖音进程复位，以便于在几秒内恢复其备用能力并重新入池。
8. 作为录播运营人员，我希望在 Web 界面实时查看正在录制房间的视频切片进度、渲染帧率与心跳，并在需要时点击“平滑封口停止”，以便于保证视频文件完好封装落盘后安全退场。
9. 作为录播运营人员，我希望录制生成的 MP4 切片能通过 HTTP Webhook 自动推送给外部 biliup 上传服务，以便于无需人工干预即可将视频自动化投稿到 B 站。
10. 作为录播运营人员，我希望在 Web 控制台查看所有切片的投递状态，并在网络抖动导致投递失败时提供“一键重新推送”，以便于保障数据链路 100% 闭环。

## 实现决策 (Implementation Decisions)

### 1. 模块组织架构

```text
src/orchestrator/
├── __init__.py           # 核心 SDK 与数据模型统一导出
├── models.py             # 领域实体定义 (InstanceStatus, JobStatus, DeliveryStatus, TargetSpec)
├── storage.py            # SQLite 单文件存储引擎与 YAML 导入器
├── instance_pool.py      # 线程安全模拟器实例池与后台 ADB 强杀复位
├── room_scanner.py       # 高并发批量开播检测与差量事件触发器
├── worker_process.py     # Worker 独立子进程控制句柄与 NDJSON 异步流监听
├── delivery.py           # 外部上传服务 HTTP Webhook 投递客户端
├── scheduler.py          # 核心调度引擎 (FIFO 排队、切机漂移、生命周期编排)
├── server.py             # FastAPI 服务主入口与 RESTful API 路由定义
├── cli.py                # 调度平台 CLI 启动入口 (支持 --port, --host, --config)
└── static/               # 内嵌轻量单页 Web 控制台 (HTML/CSS/JS 静态单页)
    └── index.html
```

### 2. 数据库设计 (SQLite Schema)

采用轻量 SQLite 单文件数据库（默认 `orchestrator.db`），规避外部数据库依赖：

```sql
-- 1. 监控主播表
CREATE TABLE IF NOT EXISTS monitored_targets (
    id TEXT PRIMARY KEY,
    target_raw TEXT NOT NULL,         -- 原始链接/口令/房间号
    resolved_room_id TEXT,            -- 解析后的标准房间号
    nickname TEXT,                    -- 主播昵称
    avatar_url TEXT,                  -- 头像链接
    is_live INTEGER DEFAULT 0,        -- 当前是否在播
    auto_record INTEGER DEFAULT 1,    -- 是否开启自动录制 (1: 是, 0: 否)
    upload_mode TEXT DEFAULT 'segment',-- 上传模式: 'segment'(切片即刻投递) | 'job'(下播整场投递)
    created_at REAL NOT NULL,
    updated_at REAL NOT NULL
);

-- 2. 录播任务表
CREATE TABLE IF NOT EXISTS record_jobs (
    id TEXT PRIMARY KEY,
    target_id TEXT NOT NULL,
    room_id TEXT NOT NULL,
    nickname TEXT,
    vmindex INTEGER NOT NULL,
    status TEXT NOT NULL,             -- pending, running, stopping, finished, failed
    failover_count INTEGER DEFAULT 0, -- 发生切机漂移的次数
    started_at REAL,
    ended_at REAL,
    error_reason TEXT
);

-- 3. 切片产物与投递记录表
CREATE TABLE IF NOT EXISTS video_segments (
    id TEXT PRIMARY KEY,
    job_id TEXT NOT NULL,
    room_id TEXT NOT NULL,
    segment_index INTEGER NOT NULL,
    file_path TEXT NOT NULL,
    duration_sec REAL NOT NULL,
    file_size_bytes INTEGER NOT NULL,
    delivery_status TEXT DEFAULT 'pending', -- pending, delivered, failed
    delivery_attempts INTEGER DEFAULT 0,
    delivered_at REAL,
    delivery_error TEXT,
    created_at REAL NOT NULL
);
```

### 3. API 接口契约 (RESTful API)

- **模拟器与实例管理**：
  - `GET /api/instances`：获取所有模拟器槽位快照（vmindex, name, status, current_job_id, is_running）；
  - `POST /api/instances/{vmindex}/reset`：触发后台 ADB 强杀抖音（`am force-stop`）复位并解除维护；
  - `POST /api/instances/{vmindex}/unblock`：手动解除阻断态；
- **主播监控池管理**：
  - `GET /api/targets`：获取监控主播列表、在播状态与自动录播开关；
  - `POST /api/targets`：新增或批量导入监控目标（支持文本批量粘贴或 JSON 数组）；
  - `DELETE /api/targets/{id}`：移除监控主播；
  - `POST /api/targets/{id}/toggle-auto`：切换开启/暂停自动录播；
  - `POST /api/targets/{id}/record-now`：跳过排队即时触发手动开录；
- **录播任务控制**：
  - `GET /api/jobs`：获取正在运行的任务与历史任务清单（含实时 FPS、录制时长、切片数）；
  - `POST /api/jobs/{id}/stop`：向指定任务发送平滑封口停止请求（Graceful Stop）；
- **切片管理与上传投递**：
  - `GET /api/segments`：按主播或任务查询已生成切片列表与投递状态；
  - `POST /api/segments/{id}/redeliver`：手动触发重新推送到外部上传服务。

### 4. 外部上传服务 Webhook 契约

当 Worker 产出切片（分段模式）或整场录播结束（整场模式）时，调度平台通过 HTTP POST 请求投递至配置的外部上传服务 URL（如 `http://127.0.0.1:8080/webhook/upload`）：

```json
{
  "event": "segment_ready",
  "job_id": "job_20261105_74400659583",
  "room_id": "74400659583",
  "nickname": "林思琪",
  "title": "晚间PK日常",
  "segment_index": 1,
  "segment_path": "D:/recordings/74400659583/20261105_seg001.mp4",
  "duration_sec": 1800.0,
  "file_size_bytes": 1048576000,
  "timestamp": 1793867800.0,
  "is_final": false,
  "total_segments": 1
}
```

## 测试决策 (Testing Decisions)

### 1. Seams（高层测试接缝）

优先复用高层 Seam，避免侵入内部私有实现：
- **Seam 1: FastAPI TestClient 端点级接缝**：通过官方 `TestClient` 发送真实 HTTP 请求，测试实例槽位查询、主播导入、任务启停与切片列表接口，确保 API 契约和数据持久化符合预期；
- **Seam 2: Scheduler 引擎与 Mock Worker/Webhook 接缝**：使用隔离的内存 SQLite 与 Mock 进程桩验证：
  - FIFO 排队进出机制（满载入队、释放出队）；
  - 动态切机漂移（收到退出码 15 后原机进入后台复位、新机拉起任务）；
  - 切片落盘触发 Webhook 投递与重试计数更新。

### 2. 良好测试的标准
- 严格黑盒测试公开行为，断言 HTTP 响应状态码、JSON 结构体与数据库持久化终态，不依赖内部临时变量；
- 遵循已有测试先例（参考 `tests/test_instance_pool.py`, `tests/test_room_scanner.py`, `tests/test_worker_process_handle.py`）。

## 范围外说明 (Out of Scope)

- **外部 Biliup 服务自身实现**：本平台仅作为上游数据生产者可靠投递切片路径与元数据，B 站账号 Cookie 维护、视频分 P 上传及投稿标签生成由外部上传服务独立负责；
- **多机分布式集群协调**：当前系统专注于单台录播服务器内的多开实例管理与并发调度，不引入分布式锁与多机协调中间件；
- **本地视频离线重编码**：不引入额外的视频转码、水印压制或离线渲染，保持原汁原味数字流切片；
- **本地视频强制物理删除**：遵循业务决策，本地切片严禁自动静默删除。
