## 1. 背景与目标

现有 `src/orchestrator/` 已实现 SQLite 调度、实例分配、Worker 管理、事件保存与人工控制，尚无 HTTP 服务。当前 CLI 的 `add` 直接写库，`record`、`stop`、`remove`、`reconcile` 写命令队列；`status` 读取整库，`run` 驱动调度循环。

现有代码还不能完整承接控制台：没有自动录制开关命令；长期开关与本场持续录制意图尚未分开；重新添加停用目标不会恢复监控；命令结果仅有简单文本；切片缺少用于筛选、排序和统计的独立时间字段。`models.py` 的任务枚举也未覆盖存储层实际使用的所有状态。

目标是在保留现有 Worker 录制职责的前提下，让网页和调度 CLI 共用可查询、可追踪的后端接口，完成总览、实例、主播、任务、切片五个页面所需的读取与操作。

## 2. 范围与主要取舍

### 2.1 本轮范围

- 单进程 FastAPI 服务、调度循环与 `web/dist/` 同端口托管。
- 本文第 6 节的查询、命令提交与命令结果接口，包括 CLI 使用的对账操作。
- 本场录制意图、命令结果、切片时间等持久化调整，以及新的独立运行数据目录。
- 调度 CLI 通过 HTTP 查询和控制，统一校验、命令处理与结果。
- 针对接口、调度语义、进程生命周期与实际录制结果的分阶段验收。

### 2.2 非目标

- 前端页面实现与构建；由配套前端方案负责。
- 上传/Webhook、旧库迁移或兼容、历史库浏览、YAML 导入、实例人工解封或开关机。
- Worker HTTP 服务、录制管线重构、视频播放或下载、任意文件读取。
- 登录验证、公网发布、多主控或跨主机协调、后台系统服务安装、自动重启服务进程。
- 数据清理、自动提交 Git、打包对外分发。

业务选择及原因集中见 ADR 0017，不在这里复制问答。工程上采用 HTTP 薄接口与现有调度器分工，使用 SQLite 持久命令；页面采用定时查询，首版不引入推送、消息中间件或额外通用框架。

### 3.2 进程与线程

```text
网页 / 调度 CLI
        │ HTTP
        ▼
FastAPI 接口 ── 只读查询 / 日志尾部
        │ 保存命令
        ▼
SQLite commands ── 单一调度循环 ── Worker 子进程
                         ▲              │
                         └── 事件队列 ──┘
```

- Uvicorn 只运行一个服务进程；不开放多 worker 启动配置，实际录制时不用热重载。
- 调度器在独立线程中初始化、运行 `tick()` 和收尾；设备查询与封口继续使用现有后台任务，外网开播查询改为第 4.5 节的受控辅助进程。HTTP 事件循环不执行阻塞的 MuMu、网络查询或封口操作。
- 调度循环独占业务状态转换。HTTP 仅允许写入命令表，不能直接改任务、目标或实例状态；所有后台查询只返回结果，由调度线程应用。
- “单进程主控”指只有一个 FastAPI/调度服务进程；外网查询辅助进程只负责解析，不运行调度器、不写数据库、不访问模拟器或录像，不属于录制 Worker。
- HTTP 读操作使用独立只读连接和短读事务；同一次列表的 `items` 与 `total` 来自同一数据库快照。写事务保持短小，不在持锁期间访问设备、网络或大日志。
- 继续使用数据库 WAL、现有主控锁和实例锁；新数据目录不意味着可以绕过旧进程仍占用的实例锁。

服务启停通过 FastAPI 的 `lifespan` 管理资源，这是官方推荐的启动与关闭入口。[FastAPI 生命周期文档](https://fastapi.tiangolo.com/advanced/events/)。单进程限制是本项目防止重复调度的设计选择；Uvicorn 的多 worker 会创建多个进程。[FastAPI 服务进程文档](https://fastapi.tiangolo.com/deployment/server-workers/)。

### 3.3 启动、关闭与失败

1. 校验参数、数据格式和监听地址，确认端口可绑定后才允许派发任务。
2. 获得主控独占锁后，把上次遗留的未应用命令标为 `interrupted`，再执行既有重启对账。未拿到锁的第二个进程不得修改这些状态。
3. 调度初始化成功后才接受控制请求。`/api/system` 的健康信息取自本次实际调度循环，不根据数据库里残留的 `running` 推测服务仍在运行。
4. 正常关闭先拒绝新命令、停止新任务和外网查询派发，作废尚未应用的异步命令；并行执行查询进程回收与现有录制平滑停止、事件收尾，最后释放数据库连接、锁和监听资源。
5. 调度线程致命异常时，HTTP 不继续作为健康控制台运行；停止接收控制操作，记录错误、尽力收尾后整个服务非零退出。端口占用、启动中途失败也必须清理已取得的资源。
6. 强制结束进程仍可能留下未封口切片；重启沿用既有对账流程，不把正常关闭路径的保证扩大到强杀或断电。

正常关闭仍沿用既有约 70 秒的录制调度收尾上限；外网查询回收使用第 4.5 节的独立 5 秒总预算，与媒体收尾并行，不能为每个查询再串行等待 30 秒。HTTP 框架的退出配置和线程等待不能先于录制收尾直接杀掉 Worker。Windows Ctrl+C、Ctrl+Break、主控异常退出和查询辅助进程退出分别验收。

### 3.4 配置、静态文件与访问

- `run` 保留明确指定 `--instances`、`--output-dir`，以及扫描、切片、导航时限等已有运行参数；新增 `--host`（默认 `127.0.0.1`）、`--port`（默认 `8000`）。
- 默认新数据目录为仓库同级 `mumu_lbcut_tool_dev/runtime-console/`；允许 `--data-dir` 指定其他独立目录。路径按仓库位置解析，不写机器固定盘符。
- 组网访问时显式绑定组网地址；不增加登录验证。开发环境由 Vite 代理 `/api`，不启用任意来源的跨域访问。
- 静态根目录为仓库根下 `web/dist/`，只托管其中的文件和前端路由。未知 `/api/...` 必须返回 JSON 404，不能落到 SPA 的 `index.html`。
- 前端尚未构建时 API 和调度仍可运行，网页入口明确返回“前端尚未构建”（503）；这是同一服务缺少静态产物的提示，不是新增只读运行模式。
- 静态路由不暴露运行目录或录像目录；文件路径仅作为切片元数据返回。

## 4. 持久化与命令执行

### 4.1 新版数据库

数据库文件仍名为 `orchestrator.sqlite3`，结构版本从当前 1 更新为 2。只初始化空库或打开相同结构版本的库；检测到旧格式时明确报错并退出，不执行 ALTER 迁移、不覆盖、不自动切换到另一个空库掩盖问题。

| 数据 | 结构调整与用途 |
| --- | --- |
| `targets` | 用可空的 `record_session_key` 记录本场录制意图，替代启动后清零的 `manual_requested`；增加 `updated_at`、`control_revision`、`latest_observation_seq`、`applied_observation_seq`，分别用于显示、控制变更检查及统一观测排序；保留长期开关、本场抑制、修正标记与退避信息 |
| `commands` | `id`、唯一 `request_id`、`kind`、`subject`、`payload_json`、`status`、`result_json`、`error_code`、`message`、`created_at`、`started_at`、`finished_at`；替代简单文本结果 |
| `jobs` | 保留现有任务、进程、心跳与事件关联；补 `reconcile_requested`，持久记录已经受理、待执行的对账意图 |
| `segments` | 补 `created_at`、`started_at`、`ended_at`、`updated_at`；时间取对应事件的 `timestamp`，保留实际接收时间作为缺失时的回退，不用文件修改时间冒充事件时间 |
| 查询索引 | 按实际查询增加任务状态/目标/时间、切片时间与任务、事件任务/类型/接收时间、待处理命令的索引；保留目标活跃任务与实例占用的唯一约束 |

`record_session_key` 只在非空且等于目标当前 `session_key` 时有效；同样，不能把两个空值相等解释成本场已抑制。跨场次、确认下播、移除或人工停止按既有边界清除对应意图，进程异常或主控关闭不清除已生效的本场意图。

新库不带入旧主播、任务或切片；部署前先平滑停旧主控及其 Worker，确认不再占用目标实例，再启用新版本。旧目录与录像全部原样保留，新控制台不提供旧库查看入口。

### 4.2 命令生命周期与原子提交

```text
pending → running → succeeded / failed
    └────────────→ interrupted
             running → interrupted（尚未应用时关停或重启）
```

- `pending`：请求已保存；`running`：正在处理或等待后台查询；两者都不代表业务状态已生效。
- `succeeded`：操作要求的调度状态与命令结果已经在同一事务内保存。开录结果是“已安排任务”，停止结果是“停止意图已生效”，均不代表媒体动作完成。
- `failed`：校验、业务条件或查询失败，返回可显示的原因；不能先修改业务状态，再单独写失败结果。
- `interrupted`：关闭或重启时发现尚未应用的请求；不自动补执行。用户重新操作使用新的请求编号。
- 修改业务状态和写入 `succeeded` 必须共享事务；异常回滚后再保存失败原因。发生数据库故障而不能确定提交结果时，不对客户端宣称成功，交由恢复后读取持久状态判断。
- 物理启动、停止、对账等动作在提交后由调度循环根据持久状态推进。`reconcile` 先保存待对账意图和命令成功结果，再进行进程核查与日志补账；最终结果查看任务状态，不把“已安排对账”当作“已恢复空闲”。
- 批量新增在单次提交中保存各条合法变更及完整逐条结果；格式有效但个别地址为空或不支持时返回逐条错误，其余项可成功。整批事务失败则不保留一部分变更而遗漏结果。

### 4.3 重复请求与查询迟到

- 所有变更请求必须携带 `Idempotency-Key`，值为客户端为本次操作生成的 UUID；`commands.request_id` 加唯一约束。
- 同编号、同操作对象及同一规范化参数返回原命令，不能再次执行；同编号携带不同参数返回 409。直接比较已保存的结构化参数，不引入内容摘要算法。
- 去重查询先于可变业务状态检查；这样重试已完成的删除或停止请求时仍能取回原结果。未知命令或请求结果不明时，客户端不能自行换编号重做。
- “立即开录”的网络查询按第 4.5 节执行，命令保持 `running`，不阻塞其他目标的事件收集、停止和移除。命令超时与底层查询进程回收都必须完成，不能只丢弃结果。
- 手动查询除第 4.4 节的统一观测检查外，还核对命令仍为 `running`、目标控制版本、请求前场次和活跃任务。目标被移除、恢复、停止、修改开关，或录制意图/抑制/修正状态发生改变时，增加 `control_revision`。若已存在可复用的当前场次任务，可只返回 `existing`，但不得再应用旧观测；其余失配返回冲突或中断。
- FIFO 仍指录制任务分配顺序；不能为了等待一条网络查询而阻塞所有后续控制命令。

### 4.4 所有开播观测共用时序

1. 周期扫描、手动开录查询、任务启动前复核都通过同一派发入口。调度线程真正派发某个目标的查询时，原子递增该目标的 `latest_observation_seq`，随请求保存序号、`control_revision`、请求前 `session_key`、查询发起的 Unix 时间和单调时钟截止时间；不在 HTTP 收到命令时提前分配序号。
2. 每个目标的结果单独返回、单独应用，不等待整批最慢目标；已删除旧 `ScanResult` 批次应用入口，派发与收取统一由 `ObservationDispatcher` 负责，不以批次完成时间记录观测。
3. 应用结果的事务内要求：目标仍启用，控制版本未失效，序号等于该目标最新已派发序号且大于 `applied_observation_seq`；解析器返回必须在截止时间前由父进程接收，超时后只允许执行器生成的超时 UNKNOWN 参与上述校验，不能接受迟到的解析结果。启动复核还必须对应当前启动中的任务及场次。旧序号、重复结果和失效控制版本一律丢弃，不能更新可信状态、结束确认次数、场次、抑制、退避或录制意图。
4. 接受有效结果时，同一事务保存 `applied_observation_seq` 和观测变更；`observed_at`、可信结果的 `confirmed_at` 使用该次查询发起时间。排序靠序号，不靠墙上时钟或批次完成时间。下播仍要求两次独立、有效且间隔达标的明确观测；同一序号不能重复计数。
5. 较新的 UNKNOWN 只更新观测状态并保留最后可信状态，但仍推进已应用序号；不能随后用更早的 LIVE 把它覆盖。无查询槽位而延期的目标不增加序号，也不凭空产生 UNKNOWN。
6. 已确认的控制操作与正在应用的观测都由调度线程串行提交；各来源不得绕过此入口直接调用旧的 `observe(now=整批完成时间)` 路径。重启保留序号，先回收旧查询执行器，防止旧结果混入新运行期。
7. 同一目标的同类查询未结束时不重复派发；不同来源产生的较新查询可以使旧结果失效。启动复核失效后，若任务仍满足启动条件，保留待复核状态并重新安排查询，不能将丢弃结果当作已通过，也不能永久卡在等待已丢弃结果的状态。

必须验证：旧批次已查到场次 A、被另一个目标拖慢时，手动查询先确认 B 并建立录制意图；A 的迟到结果不得把目标改回 A、清除 B 意图或停止 B 的任务。

### 4.5 外网查询截止时间、容量与回收

**执行边界**：周期扫描、手动查询和启动复核全部使用受控只读辅助进程，不再把阻塞的 `RoomResolver.resolve()` 放入主控 `ThreadPoolExecutor`。每个辅助进程顺序执行一个查询，正常完成后可复用自己的解析器和游客会话；不每次查询都重新注册游客标识。现有解析及签名逻辑复用，不为本轮接口改写一套网络协议。

**容量**：首版最多 8 个查询槽位，按需无窗口启动：周期扫描最多 5 个、启动复核 1 个、手动查询最多 2 个。三类分别保留容量，不因一类持续占满而挤掉其他来源；不再在辅助进程内建立批量线程池或无界执行队列。周期扫描按目标轮转，未获得槽位的目标留待后续派发；启动复核留在有界的实例任务集合中，分配查询槽位后再派发。手动命令没有空闲槽位时及时返回 `query_busy`，不在底层无限排队。

**总截止时间**：父进程以单调时钟从查询派发起计时，30 秒覆盖进程准备、IPC、游客会话/锁等待、DNS、连接、重定向、内部重试、响应读取和解析。解析器原有单次网络超时仅作为提前失败手段，不能替代该总截止。独立的执行器监控循环检查期限，不依赖阻塞的网络调用自行返回，也不依赖业务调度线程一直空闲。

**超时处理**：到期先撤销该次结果的有效性，停止接收它的成功返回，并终止准确对应的自有查询进程；等待确认退出、关闭其 IPC 与读取线程后，才归还槽位并允许按需新建。资源回收最多再用 5 秒，超限则报告服务故障并进入收尾，不用“再起一个进程”绕过并发上限。手动命令返回 `live_query_timeout`；周期扫描与复核的超时按带本次序号的 UNKNOWN 处理，不伪造已下播，不应用任何迟到结果。

**IPC 与进程归属**：每个辅助进程使用独立通道，只传目标查询参数、观测元数据和有大小上限的结果；主调度循环不能在通道读写上无限阻塞。强制结束后整条通道废弃重建，不复用可能只写了一半的共享队列。辅助进程不持有数据库连接、实例锁、录像文件或跨进程共享业务锁，不能派生其他业务进程；仅通过本次创建并持有的进程句柄终止它，不按进程名称批量清理。

**服务关闭**：停止新查询后并行回收全部辅助进程，共用 5 秒总预算；请求已标为中断还不算回收完成。Windows 下仅把查询辅助进程放入专用的 `KILL_ON_JOB_CLOSE` Job Object，句柄由主控独占且不继承；辅助进程接收首个查询前必须完成关联，关联失败则退出并明确报错。该 Job 不包含主控、录制 Worker、scrcpy 或 MuMu，以便主控异常消失时清理查询进程而不破坏录像封口路径。

选择进程隔离是为了落实可终止的资源边界：运行中的线程任务不能依靠 `Future.cancel()` 回收，Requests 的单次超时也不是总下载期限。[Python 线程池说明](https://docs.python.org/3.11/library/concurrent.futures.html#concurrent.futures.Executor.shutdown)、[Requests 超时说明](https://requests.readthedocs.io/en/latest/user/quickstart/#timeouts)。强制终止会跳过子进程清理并可能破坏 IPC，所以只用于无业务写入的查询进程，终止后丢弃其独立通道。[Python 进程终止说明](https://docs.python.org/3.11/library/multiprocessing.html#multiprocessing.Process.terminate)。Job Object 关闭时清理所属进程的行为依据 [Windows Job Objects 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。

## 5. 操作语义的实施规则

以下是 ADR 0017 决定在调度中的具体落点。

| 操作或事件 | 实施规则 |
| --- | --- |
| 自动承接直播 | 确认在播且满足既有新鲜度、抑制、修正和退避条件时，原子建立当前场次意图与唯一排队任务；无可用实例也要保留本场意图 |
| 关闭自动录制 | 只改长期开关，不清除已建立的本场意图；失败等待重试期间同样保留，不能只检查是否恰有运行中的 Worker |
| 开启自动录制 | 当前在播且满足准入条件即可承接，不绕过本场抑制和修正标记；开关写入成功不代表已经录制 |
| 手动开录 | 无活跃任务时查最新状态，仅 LIVE 成功后建立本场意图、解除本场抑制/修正标记并重置退避；ENDED、UNKNOWN 或查询失败不留预约，也不提前清除原标记 |
| 重复开录 | 排队、启动中、录制中返回已有任务；停止中或待对账返回明确冲突；不撤销停止，不创建延迟重开请求 |
| 按任务平滑停止 | 清除该任务场次的意图并写本场抑制；排队任务取消，其余可控任务进入停止中。停止中的重复请求返回已有停止状态；终态任务仍返回无须停止，不把旧任务 ID 当作停止新场次的入口 |
| 按主播停止本场 | 请求必须携带页面看到的非空 `session_key`，执行时与目标当前场次核对。匹配后原子清除本场意图、写抑制、失效正在等待的旧控制查询，并取消或停止同场次可控任务；即使退避期间没有活跃任务也能成功。场次变化则报 `session_changed`，不得转而停止新场；待对账任务仅取消后续录制意图，仍保留对账，不向未知进程发信号 |
| 首次添加 | 严格身份核验为默认；记录地址和本次自动录制设置，开播解析由正常扫描负责。新增成功不代表地址已经通过直播身份核验 |
| 重复添加启用目标 | 返回 `existing`，不改开关、身份策略、抑制或修正标记 |
| 恢复停用目标 | 返回 `restored`，沿用 ID 和历史关联，更新本次自动录制设置；保留身份策略及已有人工抑制/修正标记，自动录制仍需通过正常准入条件 |
| 移除目标 | 停用监控、清除本场意图并停止可控活跃任务；不物理删除目标、任务、日志或录像。待对账任务保留对账状态，不对未知进程发信号 |
| Worker 失败或重启 | 本场意图仍有效时按既有退避、身份核验与对账规则续录；关闭长期开关不能让这段恢复失效 |
| 目标配置错误 | 退出码 9 等已确认的目标配置错误写入修正标记并结束对应本场意图；不按普通录制失败无限重试，需显式修正或重新开录 |
| 场次结束/更换 | 失效旧意图与旧场次排队任务；新场只由长期开关或新手动请求建立意图，不将旧请求沿用到新场 |
| 对账 | 复用现有归属检查与事件补账边界，不新增人工解封、不接管未知进程；网页首版没有对账按钮 |

地址匹配沿用已有规范化与解析去重能力，不宣称任意不同分享链接都能在提交瞬间识别为同一主播。解析后确认的重复目标继续按既有去重规则停用，保留历史关联。

## 6. HTTP 接口契约

### 6.1 通用约定

- 路径统一 `/api`；请求和响应为 JSON，时间为 Unix 秒，布尔值使用 JSON 布尔，缺失值返回 `null`。不直接返回数据库原始行或内部 JSON 字符串。
- 请求字段、筛选值及范围严格校验；未知请求字段不静默忽略。错误格式为 `{"code":"稳定英文代码","message":"中文说明","details":null}`，不暴露异常堆栈。
- HTTP 400 用于无法解析的请求，422 用于字段/范围错误，404 用于对象或路由不存在，409 用于请求编号冲突或已知状态冲突，503 用于服务未就绪或关闭中；内部错误返回 500 并记录日志。
- HTTP 层能发现的错误立即返回；排队后才发现的业务变化写入命令的 `failed` 结果，由命令查询接口以 HTTP 200 返回。不能用一个 202 表示执行已成功。
- 列表返回 `{items, total, limit, offset, generated_at}`；默认 `limit=50`，范围 1～200，`offset` 为非负整数。筛选条件取交集，先筛选再计数和分页；固定排序且用唯一 ID 补齐同时间排序。
- 时间区间参数统一 `from_time`（含）与 `to_time`（不含），要求前者小于后者；客户端把所选本地时间转换为 Unix 秒再发送。
- 业务原因统一为可空对象 `{code,detail}`：`code` 是稳定英文代码，`detail` 是可空附加文本。适用于实例 `reason`、目标 `needs_fix_reason/last_failure_reason`、任务 `stop_reason/error_reason`、详情事件及切片 `reason`、告警 `reason`。后端统一解释 Worker 的“代码: 详情”，未知代码保留；无法识别为代码的文本使用 `unspecified` 并保留为 detail。修正标记的自由文本使用 `target_invalid` 加详情。前端只映射代码，不拆冒号。命令的 `error_code/message`、日志不可用的中文 `reason` 保持原契约。
- 状态值：实例 `idle/busy/resetting/offline/reconcile`；任务 `pending/starting/running/stopping/needs_reconcile/finished/finished_with_warnings/failed/cancelled`；切片 `started/finished/aborted`；可信开播状态 `live/ended/unknown`。命令状态见第 4.2 节，前端对未知返回值保留原文。
- 页面每 2 秒刷新当前页与系统信息，前一轮未完成时不叠加请求；操作提交后查询命令，命令到终态后立即刷新相关数据。日志仅手动刷新。隐藏页可降低频率，回前台立即刷新。

### 6.2 读取接口及筛选

| 接口 | 参数、排序或边界 | 返回内容 |
| --- | --- | --- |
| `GET /api/system` | 无分页 | `scheduler_running`、`service_state`（`running/closing/failed`）、`last_tick_at`、`server_time`、`upload_enabled=false`、`service_version`、`api_version=1`、`statistics_timezone="Asia/Shanghai"`、`frontend_available` |
| `GET /api/overview` | `limit/offset` 只分页告警 | `instance_counts`、`job_counts`（按各状态计数）、`recording_count`、`pending_count`、`today_finished_segments`、`statistics_timezone`、`generated_at`、`alerts` 列表分页对象 |
| `GET /api/instances` | `status`；按 `vmindex` 升序 | 第 6.3 节实例对象 |
| `GET /api/targets` | `q`（昵称或原始地址子串）、`trusted_status`、`auto_record`、`has_notice`；只列启用目标，按 `created_at,id` 倒序 | 第 6.3 节目标对象 |
| `GET /api/jobs` | `active` 默认 true（false 为历史）；`target_id`、`status`、`from_time/to_time`；时间筛选及排序按 `created_at,id` 倒序 | 第 6.3 节任务对象 |
| `GET /api/jobs/{id}` | 按 ID 查询，包括历史与已移除目标的任务 | 任务对象及 `recent_events`，最多最近 50 条相关事件；切片通过 segments 的 `job_id` 分页读取 |
| `GET /api/jobs/{id}/log` | `lines` 默认 200，范围 1～2000 | 第 6.5 节日志对象 |
| `GET /api/segments` | `target_id`、`job_id`、`status`、`has_quality_flags`、`from_time/to_time`；按 `COALESCE(started_at,created_at),job_id,segment_index` 倒序 | 第 6.3 节切片对象；时间筛选同排序时刻 |
| `GET /api/commands/{id}` | ID 不存在返回 404 | 第 6.6 节命令对象 |

`active` 对应现有活跃状态集合（包括 `needs_reconcile`），不能仅凭 `ended_at` 是否为空判断。其他各列表同样接受通用分页参数。服务版本使用源码中的版本标识，不在每次请求时运行 Git。

`has_notice` 指本场抑制、需要修正或失败重试中任一成立；false 表示三者均不成立。总览的计数与告警同样在单个读快照内产生，避免一份响应中的数量和条目取自不同状态。

### 6.3 读取对象字段

| 对象 | 字段 |
| --- | --- |
| 实例 | `vmindex,name,status,job_id,reason,updated_at,target_id,nickname` |
| 目标 | `id,raw,nickname,created_at,updated_at,trusted_status,observed_status,observed_at,confirmed_at,auto_record,room_id,anchor_uid,session_key,recording_intent,suppressed,needs_fix_reason,note,attempts,retry_at,is_retrying,last_failure_reason,active_job_id,active_job_status` |
| 任务 | `id,target_id,nickname,target_raw,vmindex,status,created_at,started_at,recording_started_at,ended_at,exit_code,stop_reason,error_reason,elapsed_sec,fps,room_identity_status,heartbeat_at,finished_segment_count,aborted_segment_count,reconcile_requested` |
| 切片 | `job_id,target_id,nickname,target_raw,segment_index,status,file_path,duration_sec,file_size_mb,is_final,reason,created_at,started_at,ended_at,updated_at,quality_flags` |
| 质量标记 | `flag,suspected_start_time`；每片保留全部已记录标记，未知值不丢弃 |
| 详情事件 | `event_id,event,timestamp,received_at,action,reason,phase,attempt`，缺失项为 null；范围包括导航、卡顿发现/恢复、登录阻断、流结束和 Worker 失败/结束，不返回全量心跳 |

- `recording_intent` 与 `suppressed` 由后端按当前场次计算；`needs_fix_reason` 去除内部 `needs_fix: ` 前缀后输出结构化原因，前端不自行解析存储状态。
- `is_retrying` 表示本场意图仍有效、已有失败尝试且尚未恢复到运行中，且没有抑制、修正或待对账阻挡；`last_failure_reason` 来自对应本场最近失败任务。
- 心跳字段取最新有效心跳，没有心跳则为 null；同时提供 `heartbeat_at`，前端不得把旧值显示成刚采集的实时值，不按本地计时虚增录制时长。`started_at` 表示 Worker 拉起时间；`recording_started_at` 是该任务切片中最早的 `started_at`，没有切片开始事件则为 null，不能用 Worker 拉起时间补值；恢复采集不重置此时间。
- 录制中切片的路径可回退到 `raw_path`，完成或中止的时长/大小缺失时保持 null，不伪造 0 或扫描整个录像目录补值。
- 已移除主播的任务、切片仍可读取，关联名称缺失时显示 `target_raw`；不因目标从监控列表隐藏而丢失历史列表项。

### 6.4 总览与告警

今日完成数以北京时间（当前统计使用 UTC+08:00）的当日零点至次日零点为界，统计 `status=finished` 且 `ended_at` 在范围内的切片；中止切片不计入完成数。

告警项含 `type,object_type,target_id,nickname,target_raw,job_id,segment_index,reason,attempts,retry_at,timestamp`，按时间倒序分页。`reason` 使用结构化原因对象，不混入中文默认消息；重试告警直接提供 `attempts/retry_at`，其他类型这两项为 null。对象名称来自当前快照中的关联记录，前端不再额外查询主播列表补齐。类型覆盖 `retrying`、`needs_fix`、`needs_reconcile`，以及最近 24 小时内新出现的 `segment_quality`、`segment_aborted`；同一切片可分别有质量与中止告警。前端通过对象 ID 跳转，不接收任意跳转 URL。

当前状态告警使用最近对应失败/对账事件的时间，缺失时回退到对象记录时间；质量与中止告警使用对应事件时间。不能每次查询都把告警时间改成当前时间，也不能只截取一个列表却声称返回全部告警。

本轮无上传告警、上传字段或上传筛选；`upload_enabled` 始终为 false。未来上传状态及分类需由独立方案定义，首版不编造枚举占位。

### 6.5 日志读取

返回 `{job_id,available,text,returned_lines,truncated,reason}`。任务存在但尚未启动或日志不存在时返回 200、`available=false` 和明确原因；任务不存在为 404，实际读取失败则返回对应错误，不伪装为空日志。

只允许读取当前数据目录 `events/<job_id>.log`，先核对任务并校验解析后的路径仍在该目录内；不接受请求传入任意路径。采用文件尾部有界读取，最多 1 MiB；行数或字节上限截断时 `truncated=true`。允许末行仍在追加，对不完整编码使用替换字符显示，既不改日志也不把一条未写完的行当成后端失败。

### 6.6 控制与结果

| 接口 | 请求体 | 命令成功结果的关键内容 |
| --- | --- | --- |
| `POST /api/targets` | `{targets:[地址...],manual_only:false,allow_unconfirmed_identity:false}`；1～100 条，每条至多 2048 字符 | `items:[{input,target_id,outcome,message,code}]`；`outcome` 为 `created/existing/restored/error` |
| `DELETE /api/targets/{id}` | 无 | `target_id,changed,affected_job_ids`；表示停用与停止意图生效，录像保留 |
| `PATCH /api/targets/{id}` | `{auto_record:bool}`，指定目标值而非盲目 toggle | `target_id,auto_record` |
| `POST /api/targets/{id}/record` | 无或 `{}` | `target_id,job_id,outcome`，`outcome=queued/existing` |
| `POST /api/targets/{id}/stop` | `{session_key:"页面当前场次"}`，必填非空 | `target_id,session_key,outcome,affected_job_ids,reconcile_job_ids`；`outcome=intent_cancelled/stop_requested/already_stopped`；无活跃任务时也可取消本场重试 |
| `POST /api/jobs/{id}/stop` | 无或 `{}` | `job_id,outcome`，`outcome=cancelled/stop_requested/already_stopping/already_terminal` |
| `POST /api/reconcile` | `{job_id:null}` 为全部待对账对象，或指定任务 ID | `job_ids,outcome`，`outcome=reconcile_requested/not_required`；CLI 使用，前端首版不提供按钮 |

`allow_unconfirmed_identity` 保留 CLI 现有显式选择；网页首版不提供该开关，创建时使用 false。重复或恢复已有目标不得借默认值或重复提交悄悄改变其身份策略。

目标级停止与任务级停止共用场次抑制和封口处理逻辑，目标级停止不要求存在活跃任务，不移除监控，也不改变长期自动录制开关。目标级命令处理时若本场已被抑制且无新增作用，返回 `already_stopped`；有待对账任务时通过 `reconcile_job_ids` 告知“后续重试已取消，遗留进程仍需对账”。同一请求编号重试仍优先返回原命令结果，新请求编号必须重新校验场次。

首次受理返回 HTTP 202：

```json
{"command_id":"命令ID","status":"pending"}
```

相同请求编号再次提交时，返回同一个 `command_id` 和当前 `status`；非终态返回 202，终态返回 200。查命令返回：

```json
{
  "id":"命令ID",
  "request_id":"客户端UUID",
  "kind":"record",
  "subject":"目标ID",
  "status":"succeeded",
  "result":{"target_id":"目标ID","job_id":"任务ID","outcome":"queued"},
  "error_code":null,
  "message":"已安排录制，实际状态请查看任务",
  "created_at":0.0,
  "started_at":0.0,
  "finished_at":0.0
}
```

示例时间仅说明类型，不是实际运行记录。失败/中断通过 `error_code,message` 解释；错误码包括 `target_not_live`、`live_status_unknown`、`live_query_timeout`、`query_busy`、`target_changed`、`session_changed`、`job_stopping`、`reconcile_required`、`service_interrupted` 等，不能靠前端解析中文判断状态。批量部分失败通过逐项结果表示，不把整个批次显示成“全部新增成功”。

## 7. 调度 CLI 调整

现有 7 个子命令保留；这是调度平台 CLI，Worker CLI 不变。

| 命令 | 新行为 |
| --- | --- |
| `run` | 本机启动统一服务；运行参数与数据目录只在此入口生效 |
| `add` | 调用新增接口，保留 `--manual-only` 和显式身份放宽选项；输出命令编号 |
| `record/remove/stop` | 调用对应接口，输出命令编号；不离线排队 |
| `stop --target-id ID --session-key KEY` | 停止指定主播的这一场，包括没有活跃任务的退避期；与 `stop JOB_ID` 互斥，仍属于同一个子命令 |
| `reconcile [job_id]` | 调用对账接口，省略 ID 表示全部待对账对象 |
| `status` | 从 system、overview 和列表接口组装 JSON；列表保留分页信息，默认展示活跃任务，不再宣称是整库转储 |
| `status --command-id ID` | 查询单条命令结果，提供 CLI 跟进已提交操作的入口；不是新增子命令 |

客户端入口增加 `--server`（默认 `http://127.0.0.1:8000`），`status` 支持 `--limit/--offset` 和 `--history`。变更请求自动生成 UUID，可显式传 `--request-id` 重查/重试同一次请求；网络超时不自动换编号重发，输出原编号并提示结果尚未确认。`status` 不带命令 ID 时无需从命令表读取全量历史。

不为旧 CLI 的离线写库行为保留兼容路径。实施时同步运行说明中的“先 add 后 run”示例，改成先启动服务、再通过 CLI 或网页添加目标。

## 9. 验收标准

以下为本专项验收要求。2026-11-11 实际测试和未测范围统一见[验证记录](../证据/验证/20261111-调度控制台后端接口验证.md)，本表不将未测项计为通过。

| 层次 | 必须通过的行为 |
| --- | --- |
| HTTP 与数据查询 | 各读取接口的字段、空值、筛选交集、总数、稳定排序与分页符合契约；非法参数、未知路由、静态资源缺失返回正确错误；跨北京时间零点的完成数正确，中止片不混入完成数 |
| 控制规则 | 首次新增/重复/恢复逐项结果正确；关闭自动录制后本场排队和失败恢复仍有效；开启开关不解除人工抑制；手动开录下播或未知不留预约；停止中拒绝重新开录；任务唯一与 FIFO 保持 |
| 本场停止 | 在失败退避且没有活跃任务时，通过主播停止接口清除意图；保持监控和开关不变，推进到原 retry_at 之后也不得续录。停止请求等待执行时若已换场，必须报冲突且不影响新场；存在待对账进程时只取消后续意图 |
| 原子性与重复请求 | 同请求编号只产生一次逻辑作用，不同内容复用编号为 409；在提交前/提交后注入故障，均不会出现状态已生效却标中断，或结果成功但状态未保存 |
| 异步竞争 | 开播查询期间停止、移除再恢复、改变开关或换场，迟到结果不得重新开录；旧批次 A 晚于手动确认 B 返回时，B 的意图和录制保持；周期扫描、手动查询、启动复核均验证序号比较；重复 ENDED 不重复计数，较新 UNKNOWN 不被旧 LIVE 覆盖 |
| 查询资源 | 分别注入 DNS、游客会话等待、重试、缓慢持续响应和不返回的解析：查询在总期限到达后失效，对应进程/IPC/读取线程在回收预算内退出；槽位确认释放后才能接新请求。反复超时不增加总进程数，手动容量满不挤占扫描和启动复核；辅助进程的游客会话在正常复用时不逐次重建 |
| 重启与对账 | 未应用命令标中断；已生效本场意图继续按既有规则恢复；旧 Worker 与未知归属沿用既有对账约束；对账命令成功仅表示已安排，最终状态另行核对 |
| CLI 一致性 | 7 个子命令按新职责工作；控制/查询只经 HTTP，服务关闭时不写库；`status --command-id` 能取回结果，错误码与网页使用同一契约 |
| 生命周期 | 隔离 Windows 子进程验证端口冲突、双主控、Ctrl+C/Ctrl+Break、初始化失败与调度异常；所有查询槽位阻塞时仍在共用预算内回收。强制结束测试主控时只清除其查询辅助进程，验证录制 Worker 未被查询 Job Object 连带终止；平滑关闭仍等待媒体和事件收尾 |
| 日志与静态托管 | UTF-8 尾行、空文件、缺失日志、超过行数/字节限制、大日志与目录越界均符合约定；不开放任意文件或录像下载；未知 API 不返回前端 HTML |
| 实际录制 | 新目录下完成添加、开关、开录、停止与移除；核对真实任务、切片终态、文件保留与 ffprobe 可读性，不以 202 或命令 succeeded 代替开录/封口验收 |
| 前端联调 | 五页与相同筛选下的 API/CLI 数据一致；在后端取得状态后 5 秒内显示变化；断线保留数据、恢复刷新；组网设备可访问；上传隐藏；手机宽度验收按前端方案 |

自动化优先复用现有调度注入点和隔离数据库；API 用 FastAPI 测试客户端，真实 Windows 子进程与真实 MuMu 分开记录。测试产物使用根 README 规定的仓外任务临时目录，正式运行数据使用独立长期目录，不以测试清理名义动旧数据。

## 10. 风险、限制与交付状态

- 无登录验证只适用于已确认的本机/组网访问边界；公网发布不在本次授权内。
- 数据库写入、长网络查询和封口若进入 HTTP 事件循环或长事务，会拖慢页面与停止操作，必须以并发和慢查询场景验证分工。
- 查询隔离增加有限的辅助进程与 IPC 成本；须验证 Windows Job Object 关联、异常回收、游客会话复用和实际扫描吞吐，不能用命令已超时替代资源回收成功。
- 数据库结构变化后旧历史不会显示在新控制台，这是已接受边界；切换版本时要避免旧进程仍占用相同实例。
- 5 秒是健康连接下后端取得数据至前端显示的目标，不是承诺从实际开下播起 5 秒发现；现有状态扫描周期和可信下播确认保持。
- 事件、命令和历史数据仍会增长，本轮只限制单次查询范围，不增加自动清理；更长期容量问题另行评估。
- 后端及 CLI 已实施并完成接口、Windows 隔离进程和实例 2 短录验证；后续台式机实例 0 真实录制与前端联调已验，边界及异常合成结果见[收尾记录](../证据/验证/20261111-调度控制台前端联调验证.md#收尾阶段接口修正与远程验收)。第二设备和真实手机访问未完成，方案保留待验证，不归档为完成。前端总体样式与其独立实施授权不由本方案代替。
