# 台式机单路录制至 B 站自动私密投稿实机验收方案

创建及最后更新于 2026-11-20。方案已定稿，状态为**待实施**。**今晚的开录时间由用户通知。**

## 验收目标

在台式机选一名真实在播的主播，录制一场。录制正常收尾后，MuMu 自动准备成片和投稿信息，交给 dev6 上传服务，由已登录的 B 站账号自动提交一份「仅自己可见」的稿件。用户无需在切片页填表、核对或点击「确认安排」。本地音画、平台回放、可见范围和唯一稿件都核对通过后，结论为**单路录制到自动私密投稿初步可用**。

台式机已有真实录制和尾片封口记录，开发机已用 dev6 验过真实扫码和私密选项。本轮要验证的是台式机当晚新录成片的完整去向。多路录制、整场多片聚合和账号页内嵌各有独立范围。[台式机实录记录](../证据/验证/20261120-T22双路四小时实机复验.md) · [dev6 接入复验](../证据/验证/20261118-T16切片页手动安排上传验证.md#2026-11-20-dev6-成品包接入复验) · [项目待办](../待办.md#待做)

## 开录前的准备

| 准备项 | 到什么状态能开测 |
| --- | --- |
| 保留本场直播间标题（待补齐） | 直播间查询已能返回标题。MuMu 需在确认开录时，将当时的主播名、直播间标题和实际开录时间与本场录制关联。下播后仍能用这些值组稿，避免取到下一场的标题或只剩文件名。[直播间查询](../../src/mvp/room_resolver.py) · [现有投稿标题预填](../../src/orchestrator/segment_uploads.py) |
| 正常收尾后自动建单并提交（待补齐） | 现有入口由人选择切片并确认。待验版本需在本次录制正常结束、正式 MP4 封口可读后，自动使用本场资料及下表规则登记作品、提交任务，并把原任务关联回切片。一次收尾只生成一单，重复收到收尾事件或响应丢失时查回原单。[现有手动安排与恢复机制](20261118-T16切片页手动安排上传任务实施方案.md) |
| 台式机部署（待现场核对） | 在台式机 `DESKTOP-VPIBHSS` 记录待验 MuMu 版本及 dev6 包版本。确认控制台连到本次选定的上传服务，已登录账号显示「可用」，发布范围支持「仅自己可见」，上传 Worker 在线且能读取本次录像输出目录。如登录已失效，通知用户扫码。选一个可用的录播实例，保留原有录像和运行数据。[部署与账号操作](../最小调度运行说明.md#在账号页扫码登录-bilibili) |

本轮按单片组织，可沿用程序默认的 30 分钟切片时长，让约 20 分钟的正常录制在收尾时形成一个 MP4。上传只关联本次选中的场次、成片和账号。[录制参数](../../src/orchestrator/cli.py)

## 自动投稿规则

| 字段 | 本轮取值 |
| --- | --- |
| 标题 | `{主播名}｜{本场直播间标题}｜{日期和开录时间}｜直播回放`。日期和时间取本场实际开录的北京时间。开录未取得直播间标题时，在收尾补查同一场。仍取不到就省略这一段，按其余字段照常验收。[MuMu 标题记录与缺失处理](20261120-MuMu开录标题记录与按场次交付dev6实施方案.md#开录时保存本场标题) |
| 标签与分区 | 标签为「直播回放」和主播名。按实际直播内容选用该投稿账号可用的 B 站分区。 |
| 版权与来源 | 版权选「转载」，来源栏只填纯文字「转载」。标题、简介和来源等投稿字段均省略直播间链接。 |
| 账号、范围与数量 | 使用台式机所连 dev6 部署中的已登录账号，发布范围固定为「仅自己可见」（`self_only`）。本次录制自动提交一份稿件。 |

## 台式机现场步骤

1. **等用户通知后开录。** 从已有候选中选一名当时在播的主播。确认房间、主播身份和实际画面，记下本场直播间标题。看到正确画面开始采集时记开录时间，环境准备、等待开播、上传和平台处理分别计时。
2. **按现场情况结束本次录制。** 20 分钟是体验时长的参考。按下表执行，只记录本次实际走到的分支。[下播判定](../最小调度运行说明.md#unknown-与下播) · [按本场停止录制](../最小调度运行说明.md#人工停止)

   | 现场情况 | 处理及验收口径 |
   | --- | --- |
   | 主播提前自然下播 | 让 MuMu 自己复核下播、停止录制并封好尾片，随即走自动投稿。即使只录了 12 分钟，只要有有效成片且后续验收通过，这轮也通过，并记为「自然下播」。 |
   | 约 20 分钟时仍明确在播 | 正常停止本次录制，待尾片封好后走同一自动投稿流程，记为「主动停录」。若当时已出现下播信号，先等调度器复核，再按实际结果收尾。 |
   | 设备掉线、断流或录错房间 | 记录故障、受影响的录像和实际恢复结果。以调度器的直播状态判断主播是否下播。中止片、未封口文件或身份不符的录像不能作为本轮投稿成片。 |

3. **观察自动交片和实际投稿。** 从切片详情核对本次正式文件、目标账号、投稿字段和任务进度，记录 MuMu 安排编号、Core 作品编号和任务编号。若还需要人点击「确认安排」才能产生任务，自动投递项未通过。遇到超时或结果不明，沿原安排和任务编号核对，避免重复投稿。
4. **核对本地和 B 站。** 播放本地 MP4 的开头、中间和结尾，确认三处均有声音和画面。用投稿账号在 B 站创作中心找到稿件，对照上表核对标题、标签、分区、转载信息和「仅自己可见」，并打开回放。确认平台 BV 号与 MuMu 返回的一致。刷新或重开切片详情后仍应是原任务，创作中心中本轮也只有这一份稿件。

## 结果怎么记

| 结论 | 判定 |
| --- | --- |
| 通过 | 本轮真实录制正常收尾，系统自动提交一份符合约定的私密稿件。本地三处音画正常，MuMu 与创作中心的 BV 号一致，投稿账号能回放，刷新后仍是同一单。两种正常收尾方式中实际走通一种即可，另一种记为本轮未覆盖。 |
| 已收稿，回放待验 | 平台已有对应稿件，但仍在转码或审核。保留原 BV 号，待能播放后补核可见范围和回放，再给最终结论。 |
| 待核对 | 服务失联或提交响应丢失，暂时无法确认是否收稿。使用原安排和任务编号查回结果。 |
| 未通过 | 需要人工点击投稿、投错内容、可见范围错误、重复建稿、音画异常或平台拒绝等情况已有明确证据。记录失败环节与原因。 |
| 未开测 | 自动提交或台式机环境尚未就绪，或仍在等用户通知。方案定稿本身不计作实机验证。 |

现场记录写明受测版本和部署、本场主播及直播间标题、实际开录和收尾时间、收尾原因、正式文件及实测时长。用 MuMu 安排编号、Core 作品编号、任务编号和 BV 号关联同一份稿件，附上播放抽查及刷新后的结果。实录结束后按项目约定保存仓外材料，在验证记录中写明结论、证据位置和仍待核对的事项。[文件存放约定](../../README.md#项目目录与文件存放) · [验证记录约定](../README.md#文档职责与入口)
