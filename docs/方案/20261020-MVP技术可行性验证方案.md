## 一、背景与目标

依据《抖音 PK 直播双路自动录播系统 PRD V1.2》，系统的最终目标是实现两路抖音娱乐/PK直播间的全自动、长时间稳定录播（保留手机端完整UI与独立音频）。

在启动包含 Web 控制台、多任务调度及 6–8 小时持久运行的全面工程开发前，首要任务是**通过 MVP（最小可行性验证）穿透最核心的技术链路与风险点**。

### MVP 核心目标
1. 验证通过命令行/ADB 自动纳管本机 MuMu 模拟器（`lb1`、`lb2`）的可行性；
2. 验证结合抖音网络接口查询开播状态与通过 Scheme URL / Intent 直达直播间的可靠性；
3. 验证基于 ADB 数字流（scrcpy 核心）在 Android 系统层直接捕获独立音画并生成 MP4 切片的可行性；
4. 验证双实例同时录制时的**音频彻底物理隔离（绝对无串音）**；
5. 为后续完整系统（Web 控制台与持久化调度）确立坚实的技术底座与实测参数。

---

## 二、范围与非目标

### 1. MVP 包含范围
- **外部依赖自动化部署**：自动下载 scrcpy 免安装 Release 并部署至仓外开发工具目录；
- **单路全流程贯通**：从启动 `lb1` 模拟器、检测开播状态、Intent 唤起抖音直达直播间、启动数字流录制 3 分钟并平稳保存切片 MP4；
- **双路并发音画隔离验证**：同时启动 `lb1` 与 `lb2` 录制两个不同直播间各 3 分钟，交叉比对音轨，实测验证无任何系统混音与跨路串音；
- **基础容错与优雅清理**：支持进程异常或用户中断时的自动清理（Teardown），确保录制进程平稳封口、ADB 端口释放；
- **验证证据沉淀**：按规范产出验证报告文档至 `docs/证据/验证/20261020-MVP技术可行性验证.md`。

### 2. MVP 非目标（本阶段不实施）
- FastAPI + Web 前端仪表盘（待 MVP 验证通过后进入下一阶段实施）；
- 6–8 小时长时间压力测试与磁盘安全阈值自动化轮转；
- 复杂的录像历史检索与多条件切片归档；
- 模拟器的自动化全新安装与环境初始化（直接复用本机已有的 `lb1` 和 `lb2`）。

## 三、实施路径与关键取舍

1. **录制管线选型（ADR 0001）**：
   - 放弃 Windows 宿主机桌面/声卡窗口抓取（存在多路串音和窗口遮挡风险），采用 scrcpy 架构的 ADB 数字流抽取（AudioPlaybackCapture + 屏幕投屏编码流）；
   - scrcpy 二进制包（含 `scrcpy.exe`、`scrcpy-server.jar`）由脚本自动下载至仓外工具目录 `../mumu_lbcut_tool_dev/tools/scrcpy/`，不污染 Git 仓库；
   - 默认复用 MuMu 自带的 `D:\soft\MuMuPlayer\nx_main\adb.exe` 保证与模拟器内核版本完全匹配。
2. **直播间定位与唤起**：
   - 采用轻量 Web 接口（`/webcast/room/web/enter/`）解析出 `room_id`，再通过 `am start -a android.intent.action.VIEW -d "snssdk1128://live?room_id=..."` 唤起抖音客户端；
   - 若主播未开播，流程立即拦截提示，不空转启动模拟器。
3. **切片存储与封装（ADR 0002）**：
   - MVP 录制时长设定为 3 分钟，验证录制中断或主动停止时，MP4 文件尾部 moov atom 的封装完整性与可播性；
   - 输出路径固定存放于仓外临时目录 `../mumu_lbcut_tool_dev/mumu_lbcut_tool_tmp/20261020-mvp/`。

## 五、实施步骤与依赖

### 步骤 1：声明依赖与准备 scrcpy 组件 (`dep_manager.py`)
- 创建 `requirements.txt` 引入 `requests>=2.31.0`；
- 检查仓外工具目录 `../mumu_lbcut_tool_dev/tools/scrcpy/`：若缺失 `scrcpy.exe`，自动从官方源下载 Windows 64 位发布包并解压就绪；
- 校验 MuMu 自带 ADB 可用性。

### 步骤 2：实现 MuMu 实例管理 (`mumu_client.py`)
- 封装 `MuMuManager.exe control --vmindex <N> launch/shutdown`；
- 获取实例运行状态与 ADB 连接地址（如 `127.0.0.1:16384` 等），建立连接并进行超时等待。

### 步骤 3：实现直播间解析与开播检测 (`room_resolver.py`)
- 复用 `douyin_live_lab` 中的 `/webcast/room/web/enter/` 接口；
- 输入短链或链接，解析提取 `web_rid`，请求返回当前 `status`（2=直播中，4=未开播）。

### 步骤 4：实现抖音 Intent 唤起 (`app_launcher.py`)
- 组装 `snssdk1128://live?room_id=...` Intent 广播；
- 通过 ADB 唤起并跳转到抖音直播界面，校验当前前台 Activity；
- 监控可能出现的系统音频捕获授权弹窗，必要时通过 ADB 自动化点击确认。

### 步骤 5：实现数字音视频录制管线 (`stream_recorder.py`)
- 封装 scrcpy 子进程管道（设置 `--record <file.mp4> --no-playback --audio-source=playback --video-bit-rate=4M --max-fps=30`）；
- 录制输出指向 `../mumu_lbcut_tool_dev/mumu_lbcut_tool_tmp/20261020-mvp/`；
- 实现 `stop()` 方法向子进程发送停止信号（SIGINT 或控制台 CTRL_C_EVENT），等待其完整写入 MP4 索引；
- 增加上下文清理机制（`teardown`），确保任何异常退出时终止录制并释放 ADB 资源。

### 步骤 6：执行单路验证 (`verify_single_stream.py`)
- 启动 `lb1` 实例，测试指定在播直播间录制 3 分钟；
- 验证 MP4 生成、播放正常且画面含弹幕/PK区域。

### 步骤 7：执行双路音频隔离验证 (`verify_dual_isolation.py`)
- 同时启动 `lb1` 与 `lb2` 录制两个不同直播间各 3 分钟；
- 对两段生成的 MP4 音频进行对比，确认无跨路串音；
- 沉淀验证证据至 `docs/证据/验证/20261020-MVP技术可行性验证.md`。

## 六、验收标准（AC）

| 验收项 | 验收条件 | 判定依据 |
| --- | --- | --- |
| **AC-1 依赖就绪** | scrcpy 成功部署于仓外工具目录，ADB 正常建立通信 | 依赖自检通过，`adb devices` 列出实例状态正常 |
| **AC-2 状态准确** | 给定正在直播的主播链接，正确识别状态为“直播中”；已下播链接识别为“未开播” | 接口返回字段校验一致 |
| **AC-3 直达直播间** | 模拟器内无需人工操作，直接拉起抖音并停留在此主播的直播间界面 | 屏幕截图中可见主播画面、弹幕及比分区域 |
| **AC-4 单路音画完整** | 生成时长约 3 分钟的 MP4 录像，画面清晰（720P）、动作流畅，包含弹幕和礼物动效，声音清晰同步 | 视频播放器正常回放，音画无脱节 |
| **AC-5 双路彻底隔离** | `lb1` 录制直播间 A，`lb2` 录制直播间 B，两段录像各自仅含自己直播间的声音，**完全没有对方的声音混入** | 两份视频音频波形独立，无串音 |
| **AC-6 优雅退出与封口** | 录制主动停止或异常退出时，MP4 文件正常结束并具备完整索引，无僵尸进程残留 | ffprobe / 播放器解析无损坏报错 |
| **AC-7 证据沉淀** | 形成规范的验证报告 | `docs/证据/验证/20261020-MVP技术可行性验证.md` 包含完整测试结论与文件位置引用 |

## 七、风险、异常处理与回滚

1. **Android 15 内部录音权限弹窗**：
   - *风险*：MuMu 15.0 内部首次被请求音频投屏时，系统可能弹出“是否允许录制/投屏”提示。
   - *应对*：在 `stream_recorder.py` 启动后 2 秒内检测并自动触发 ADB 回车/点击“立即开始”；
2. **下载或网络受限风险**：
   - *应对*：`dep_manager.py` 支持配置镜像源或在下载失败时输出友好的手动放置提示；
3. **异常清理与回滚（Teardown）**：
   - 脚本注册退出钩子（`atexit` 及 `signal` 处理），发生异常时立即平稳关闭 scrcpy 录制子进程，杀掉残留 ADB 端口映射，关闭模拟器实例（可选），确保系统恢复到初始状态。
