# MuMu 开录标题记录与按场次交付 dev6 实施方案

创建及最后更新于 2026-11-20。用户于同日授权 MuMu 侧实现及本地验证。状态为**待台式机实机验证**。本机已通过单片、三片和丢回包后的原任务查回验证，现场开录仍等用户通知。[本地验证记录](../证据/验证/20261120-MuMu按场次交付dev6本地验证.md)

**MuMu 的交付目标是让 dev6 接到一份完整的场次任务，并把平台任务号记回这场录像。** 用户按主播设置账号、分区和自动投稿开关。开启后，手动开录和自动开录都走同一条交付流程，录完无需在切片页点「确认安排」。dev6 负责读文件、上传视频、执行 B 站投稿并回传结果。[已确认的分工](../adr/0022-per-streamer-session-submission.md)

现有直播间查询已返回可空的标题，录制台账也能区分主播、场次、录制任务和切片。现有上传入口按一条切片建单，默认用文件名预填投稿标题，查回任务时也只核对一个视频。本次改动集中在 MuMu 的开录记录、整场清单和自动交付入口。[直播间查询](../../src/mvp/room_resolver.py) · [录制台账](../../src/orchestrator/storage.py) · [现有单片交付](../../src/orchestrator/segment_uploads.py)

## 开录时保存本场标题

1. **先把房间和录制任务关联。** 调度器通过启动复核后，从返回的 `ResolvedRoom` 取房间 ID、主播 ID 和昵称，连同观测时间写入该 `job_id` 的启动记录，供首片开录时核对。用 `target_id + session_key` 标识本场直播。同一主播下一场使用自己的记录，标题相同也能区分。[启动复核与 Worker 启动](../../src/orchestrator/scheduler.py)
2. **首片真正开始采集时才记开录。** 在本场首条 `segment_started` 入账的同一事务中创建场次记录，取事件的 `timestamp` 为实际开录时间，写入已核实的主播昵称。由这个事件触发一次异步的开录标题查询，使用现有房间查询器和原房间、主播标识。这样，即使主播在准备录制期间改过题，也能取得首片开录时的观测。匹配成功后把非空标题和观测时间写回原场次，失败或空白就留空，录制继续。后续切片、同场换实例和主播改题都沿用首次记录。重放事件只恢复当时保存的结果，已经记下的标题和开录时间不会被覆盖。[切片开始事件](../../src/worker/events.py) · [事件入账](../../src/orchestrator/storage.py)
3. **开录没拿到标题，只在收尾补查。** 正常收尾时，等开录查询返回或超时，对标题仍为空的场次补查一次。返回的房间 ID 和主播 ID 能对应原场次时才接受非空标题。已下播只返回状态、超时、空标题或已换场，都直接省略直播间标题这一段，继续交单。补查只补本场资料，不更新调度器的在播状态。查询放在录制线程和数据库事务之外，迟到回包不能改写已交付的清单。[房间查询通道](../../src/orchestrator/room_query_process.py)

取得直播间标题时，投稿标题用「主播名｜本场直播间标题｜日期和开录时间｜直播回放」。未取得时用「主播名｜日期和开录时间｜直播回放」。两种格式都取首次实际开录的北京时间。标签为「直播回放」和主播名，版权选「转载」，来源只填「转载」，投稿字段省略直播间链接。[本轮投稿字段](20261120-台式机单路录制至B站自动私密投稿实机验收方案.md#自动投稿规则)

## 正常收尾后收集本场切片

**正常收尾要同时满足两个条件。** 一是调度器已确认主播自然下播，或本场已执行主动停录。二是本场录制已停止、相关 Worker 的事件已收齐、已开始的切片都有明确终态，成片已封好。两个条件谁先到都先记账，条件齐了再交付。正常轮转得到一个 MP4、某条切片带 `is_final`、设备掉线或主控退出，都不能单独触发交单。同场故障恢复产生新 `job_id` 时，先继续按原场次记片。[录制收尾判定](../../src/orchestrator/storage.py) · [切片终态说明](../最小调度运行说明.md#持续采集与切片终态)

- 按本场的 `target_id + session_key` 找到各次录制任务，再按 `job_id + segment_index` 取切片。同一主播同一时间只有一个活跃任务，各任务按首片实际开始时间排，同刻按台账中的任务创建次序排。任务内按数字片号排列，并用各段的 `started_at` 核对。清单定下后保存顺序，事件重放和重试都读取原清单。
- 从台账中取有开始记录、状态为 `finished` 的正式 `file_path`，复用文件检查，逐片核对位于配置的录像输出根内、为可读非空 MP4。用本场身份及切片风险记录核对归属。已核实身份的完整成片遇短暂面板遮挡照常交付，并保留提示。缺片、文件损坏、身份未核实、录错房或终态冲突时，保留本地录像，在场次记录中标出待核对的片号和原因。[文件检查](../../src/orchestrator/segment_uploads.py) · [切片质量标记](../../CONTEXT.md#language)

## 多个切片组成一份 dev6 任务

例如，同一场第一次录制产生两段，换实例续录产生第三段。两次录制都可能从 `000001.mp4` 开始。登记时 `directory` 取配置项 `output_dir` 的本机规范绝对路径，dev6 的服务和上传 Worker 均须能读取该目录。清单中的路径相对于这个根目录，只列本场选中的文件。

| 实际顺序 | MuMu 切片来源 | 清单视频 ID | 交给 dev6 的相对路径 |
| --- | --- | --- | --- |
| 第 1 段 | 任务 A，片号 1 | `p1` | `job-a/000001.mp4` |
| 第 2 段 | 任务 A，片号 2 | `p2` | `job-a/000002.mp4` |
| 第 3 段 | 任务 B，片号 1 | `p3` | `job-b/000001.mp4` |

1. **一个作品。** 预先生成并保存一个 UUID 作为 `work.id`。清单使用 `version: 1`，在 `work` 中放入 `ready=true`、整场投稿标题和标签，在 `assets.videos` 中逐一列出视频 ID 及相对路径。按路径引用原片即可，无需拼接视频、搬文件或扫描相邻目录。
2. **一个上传单元。** 三段的例子只生成一个 `upload_units` 元素，`mode=multipart`，`videos=["p1","p2","p3"]`。这个数组决定分 P 顺序。单片沿用 `mode=independent` 且 `videos=["p1"]`。两条路径都只有一个启用的 B 站目标，因此本场只对应一个平台任务。
3. **一个目标账号。** 生成安排时取该主播保存的原部署、Core 账号 ID、对应 MID 和分区，固定本单参数。向 dev6 传 `platform=bilibili`、选定账号，以及 `category_id`、`copyright=2`、`source="转载"`、`publish_mode=self_only`。发送前复核原部署、账号可用性、私密能力和实际字段及分 P 数量上限。条件不符就显示具体原因并保留原片，避免改投其他账号、改为公开或拆成多份稿件。[MuMu 的部署与能力核对](../../src/orchestrator/segment_upload_core.py) · [上传平台清单契约](../../../fileUploadPlatform/docs/operations/core-mvp.md)

## 自动交单、停止交付与查回原单

| 时点 | MuMu 的动作和可核对的结果 |
| --- | --- |
| 整场可交付 | 在调度库的收尾事务中记下本场结果。开关关闭记「只录」，素材归属或完整性有疑点记「待核对」，已开启且能按上述规则组单就记「待交付」。服务侧后台只读取待交付场次，在现有 MuMu 投递库中按 `target_id + session_key` 唯一创建自动安排。保存有序明细、原部署和账号、文件大小与修改时间、清单、作品编号及登记和提交各自的固定请求编号。重启可从待交付记录补办，重复通知仍命中同一单。网络交单与录制分开执行，关闭网页也不影响交单。 |
| 登记并提交 | 复用 `PostingCore`。先用登记编号调用 `POST /api/v1/works`，携带 `directory + manifest` 并核对原 `work_id`。提交前按保存的清单复核每片的路径、大小、修改时间及风险记录。匹配后用提交编号调用 `POST /api/v1/works/{work_id}/submit`，带同一目录、清单和 `execution_type=immediate`。两次写请求各自使用持久保存的 `Idempotency-Key`。仅登记作品时显示「已登记，待接单」。 |
| 投稿开关关闭 | 录制继续。对尚未发起提交的场次持久记录「只录」，即使原安排尚未创建或已登记作品也能停住。对同一场，把关闭开关与开始提交这两个动作串行判定。关闭先发生就停止派发，提交已在途就只查原单，页面显示已受理的原任务或「待核对」。 |
| 平台接单 | 核对原 `work_id`、唯一任务、账号、上传单元、模式，以及快照里的 `parts[].video_id` 顺序和 `assets[].relative_path`。dev6 多 P 的 `item_key` 是 `group`，单片独立模式取视频 ID。回执匹配和按作品查回都按对应模式核对。匹配后保存 `task_id`，关联到本场和每一片，显示「已交付」。排队中的任务也已接单。 |
| 超时、重启或重复收尾 | 沿原部署、原安排和固定请求编号恢复。登记回包丢失可用原编号和原正文恢复登记。提交结果不明先分页查询原 `work_id` 的任务。唯一匹配就关联，查询不全、冲突或多条匹配时保留「待核对」。完整查询仍未找到时，只有本场仍允许交付、文件及参数仍与原单一致才可按原提交编号和原正文重放。取得 `task_id` 后按该编号读取平台状态及其返回的 BV 号。 |

在同一投递库事务里核对手动安排和自动安排的切片归属。切片已关联到同账号、同部署的同一任务时展示原单。已有安排内容与整场清单冲突时保留原单和原因，避免两个入口并发交出重复任务。自动入口直接使用后端登记与提交流程。现有切片页继续提供手动安排和结果查看。[现有登记、提交与查回](20261118-T16切片页手动安排上传任务实施方案.md) · [MuMu 的 dev6 客户端](../../src/orchestrator/segment_upload_core.py)

## 实施顺序与验收

| 顺序 | 修改位置及验收办法 |
| --- | --- |
| 1. 本场资料 | 在调度存储和启动复核处保存录制任务的候选资料、首次开录时间、场次标题及收尾状态。用改题、同主播换场、标题一直为空和日志重放验证。已有标题保持开录时的值，空标题只在收尾补查，同场可补得，异场标题不得带入。[调度存储](../../src/orchestrator/storage.py) · [调度器](../../src/orchestrator/scheduler.py) |
| 2. 主播设置与有序清单 | 主播页通过本机受保护接口，把开关、绑定部署、账号和分区按 `target_id` 存入调度库。账号信息只经现有本机接口读写。把投递库的单片文件引用扩为有序明细，保留手动单片入口。用上表的跨目录同名片测试，断言清单顺序为 A1、A2、B1，邻场文件未入单。另测短暂遮挡、未封口和错房。[主播页](../../web/src/views/TargetsView.vue) · [本机接口](../../src/orchestrator/bilibili_api.py) · [投递存储](../../src/orchestrator/segment_upload_store.py) |
| 3. 后台交单与状态 | 后台交单随服务启动和关闭，沿用现有的请求编号、派发互斥与任务查询。用隔离的 dev6 Core、测试账号资料和合成切片验证实际接口，上传 Worker 保持离线。单片和三片两个正例各取得恰好一个可查的任务号，三片快照的顺序与清单相同。在可控回包测试中覆盖登记后关闭开关（零任务）、丢回包、重启、重复收尾及与手动入口并发（查回同一任务）。[服务生命周期](../../src/orchestrator/server.py) · [交单逻辑](../../src/orchestrator/segment_uploads.py) · [定向测试](../../tests/test_segment_uploads.py) |
| 4. 台式机单片实测 | 依照正式验收方案核对 dev6 部署、账号、目录可读和 Worker 在线。**今晚开录等用户通知**，以约 20 分钟为参考，提前自然下播即可收尾。分别记录 MuMu 取得任务号、平台返回稿件及账号实际可回放的结果。单片实测与多 P 清单测试分别记结论，真实多 P 投稿另行验证。[台式机验收方案](20261120-台式机单路录制至B站自动私密投稿实机验收方案.md) |

实施若调整数据库结构，按项目约定使用独立数据目录验证，保留已有库和录像。自动恢复只处理本功能已经记录的场次和安排。MuMu 交付验收以平台接单为准，实际上传、投稿重试和稿件管理由 dev6 承担。
