# 最小自动调度运行说明

## 当前交付边界

已实现 HTTP + CLI + SQLite 的单机流程：可信开下播观测、目标去重、FIFO 排队、指定实例分配、Worker 子进程控制、切片事件保存、本场录制意图与人工停止抑制、在播退避重试、实例同步与按需开机、重启对账。CLI 查询和控制必须连接运行中的服务，不再离线打开数据库。

调度层独占公网状态查询；Worker 负责本地导航、准入、录制、守护及退出时关闭抖音的尝试。SQLite 是运行中调度状态的唯一事实来源。`InstancePool` 只负责查询实例是否开机与按需自动开机，实例占用记录在数据库。

网页控制台见[控制台网页](#控制台网页)，台式机真实录制与页面联调已验，第二设备与真实手机访问仍待验。本轮不包含上传/Webhook、跨主机运行或自动接管旧主控遗留的活跃 Worker。Worker 只有持续采集一条录制路径，独立分装 MP4；计划切片不重启 scrcpy。旧的停止重启模式和交叠双管线已删除（[ADR 0014](adr/0014-remove-restart-mode-and-dual-pipeline.md)）。

## 环境与目录

升级部署前应先平滑停止旧版本主控及其 Worker，避免新旧锁作用域并存；不能把新锁当作旧进程已经退出的证明。

要求 Windows、Python 3.11、`requirements.txt` 中的依赖，以及 MuMu、可用的 scrcpy、ffmpeg 和 ffprobe；自动化测试使用 `requirements-test.txt`。不要把单次测试成功当作工具版本和设备能力均已完成长期验证。

### 固定媒体工具部署

媒体工具固定为 **Gyan `9.0.2-full_build-www.gyan.dev`**，ffmpeg 与 ffprobe 必须来自同一个发行包。使用 [Gyan 9.0.2 固定发行包](https://github.com/GyanD/codexffmpeg/releases/download/9.0.2/ffmpeg-9.0.2-full_build.7z)，不要使用会随时间变化的 latest 下载地址。解压后按仓库位置放置：

```text
仓库父目录/mumu_lbcut_tool_dev/tools/ffmpeg-9.0.2-full_build/
├─ bin/ffmpeg.exe
├─ bin/ffprobe.exe
├─ LICENSE
└─ README.txt
```

源码运行与部署副本采用同一布局；程序内置依赖的含义是随部署目录携带这套工具，无需用户另装 FFmpeg 或修改系统 PATH。二进制保留在仓外，不写入 Git；本轮未生成安装包。运行时不下载、不自动升级，也不回退到 PATH 中的工具。已有目录或旧版本文件不能直接覆盖；升级先平滑停机，在独立部署目录核验后再切换。

Worker 在操作模拟器前核对两只工具的完整版本标识、编译器与构建配置是否匹配，并在日志记录绝对路径与构建信息。缺文件、版本不符、无法执行或配套配置不一致会明确失败。分装和画面分析共用已校验的 ffmpeg，所有切片封口使用配套 ffprobe。

Gyan full build 的许可证为 GPLv3，保留包内 LICENSE、README 及[构建来源](https://www.gyan.dev/ffmpeg/builds/)；对应上游源码版本为 [946fcce07b](https://github.com/FFmpeg/FFmpeg/commit/946fcce07b)。本次是内部部署，正式对外分发仍按项目授权边界另行处理。

音轨修复在 stream copy 输出端增加 `-copyinkf:a`，允许复制 scrcpy 未标为关键包的 AAC-LC 音频；视频仍按关键帧开始和分段，不重编码。原因、对照实验与真实 Worker 结果见[固定 FFmpeg 9 与 AAC 音轨修复验证](证据/验证/20261112-固定FFmpeg9与AAC音轨修复验证.md)。

### 设备与运行目录

Worker 每次启动会把所用实例的渲染模式设为“稳定”（MuMuManager 中 `renderer_mode=dx`，MuMu 记为 OpenGL），在实例下次开机时生效；Vulkan 模式下曾多次出现显卡驱动崩溃，见[待办](待办.md) K9。MuMu 主程序未运行时 Worker 会先拉起它；启动实例的命令若返回错误（如主程序刚启动时的 `-503 mainnx connect failed`），45 秒内每 3 秒重发一次，实例开机等待从命令被受理时起算。

默认长期数据位置为仓库同级的 `mumu_lbcut_tool_dev/runtime-console/`。仅 `run --data-dir` 可以指定独立目录。数据库结构为 v3（含实例启用与开机冷却字段）；旧版本（含 v2）或未知格式一律拒绝打开，并提示使用新的独立数据目录，不执行迁移或覆盖。旧 `runtime/` 与录像保持原样。共享实例锁仍使用旧位置，不能通过新数据目录绕过旧 Worker 的占用。

- `orchestrator.sqlite3`：目标、任务、槽位、事件、切片及控制命令。
- `orchestrator.host.lock`：主控操作系统互斥锁；文件留存不等于仍被占用。
- `events/<job_id>.ndjson`：用于对账的事件日志。回调失败、收集不完整必须报告，不能当成功。
- `events/<job_id>.log`：该任务 Worker 的运行日志（含 scrcpy 输出，采集失败时附 ffmpeg 报错末尾；ffmpeg 完整输出在录像目录的 `segmenter.stderr.log`），由 Worker 自己追加写入，主控退出后仍继续记录；单独运行 Worker 时用 `--log-file` 指定。设置了总录制时长时，切片 ffmpeg 到点先结束，scrcpy 随后写不进收尾数据会报 `Failed to write trailer`，这类行会带“(已录满总时长，预期收尾)”标注，不是故障。正常录制期间日志很少，主要在开录前和故障恢复时写入，60 分钟录制约 5 KB。
- 默认共享实例锁：`mumu_lbcut_tool_dev/runtime/instance-locks/`，不跟随录像目录变化。
- 录像：用户指定输出目录下的 `<job_id>/<run_id>/`。没有自动删除、覆盖和保留期清理。

## CLI 使用

在仓库根目录打开已经具备依赖的 Python 环境。下面 PowerShell 示例把输出定位到仓库之外；实例编号必须先核实并明确允许使用，不应照抄其他机器的编号。

```powershell
$Repo = (Get-Location).Path
$Dev = Join-Path (Split-Path $Repo -Parent) 'mumu_lbcut_tool_dev'
$Data = Join-Path $Dev 'runtime-console'
$Records = Join-Path $Dev 'recordings'

python -m src.orchestrator.cli --help
# 默认无需指定 --instances，启动后可在控制台“实例”页动态启用/停用本机探测到的实例（选择持久化于数据库）；
# 如需批处理或测试预设初始启用编号，可附加可选参数 --instances 2,3。
python -m src.orchestrator.cli run --data-dir $Data --output-dir $Records
```

先保持服务运行，再在另一终端执行 `python -m src.orchestrator.cli add 'https://live.douyin.com/实际房间号'`。`add` 支持多个地址，返回命令编号；用 `status --command-id 编号` 查询逐项结果和 `target_id`。默认自动监控并采用严格身份核验；`--manual-only` 仅监控状态，不自动承接新场。

默认监听 `127.0.0.1:8000`；`run --host 组网地址 --port 8000` 显式绑定本机或组网 IP，客户端用 `--server http://组网地址:8000`。不提供认证或公网发布，不接受监听所有网卡的地址。服务同端口托管 `web/dist/`；未构建时网页入口返回 503“前端尚未构建”，API 正常可用。未知 `/api/...` 始终返回 JSON 错误，不返回前端 HTML。

### 控制台网页

网页源码在 `web/`，构建需要 Node.js（已用 Node 24、npm 11 验证）；运行服务的机器只需要构建结果 `web/dist/`，可从构建机拷贝，不必安装 Node。

```powershell
cd web
npm ci              # 首次或依赖变化时
npm run build       # 类型检查并输出 web/dist/
npm test            # 单元测试
```

构建后启动调度服务，浏览器打开 `http://127.0.0.1:8000/`，组网设备打开 `http://组网地址:端口/`（服务需按上文绑定组网地址）。页面每 2 秒刷新当前页，隐藏标签页时降为 10 秒；与服务断开时保留最后数据并禁用操作，恢复后自动刷新。日志抽屉只手动刷新。

开发时 `npm run dev` 启动 Vite 开发服务器，并把 `/api` 代理到 `CONSOLE_API_TARGET`（默认 `http://127.0.0.1:8000`）；`npm run dev:mock` 改用 `web/src/mock/` 的样例数据，不需要后端。带模拟开关执行构建会直接报错。页面与交互规则见[前端方案](../archive/docs/方案/20261111-调度控制台前端方案.md)，联调结果见[前端联调验证](证据/验证/20261111-调度控制台前端联调验证.md)。

### 主动定位而非只做 UID 门禁

调度层在启动前查询本场 `room_id` 和主播 UID。Worker 使用目标直达、页面观察、替代入口和重新进入组成有界定位流程；命令被系统接受不等于已经到达目标。

初次进入先确认直播 Activity，再同页等待主播入口并取得独立证据；返回后才执行最终画面确认，不重复前后两轮动态画面检查。入口暂不可用先同页复检，再换路线。优先按当前 UI 节点的实际坐标进入资料卡，不把固定点击位置当成已完成操作。

当前 MuMu / 抖音版本不在直播 UI 树直接显示 UID，Worker 会点开**当前直播主播**的资料卡，并从客户端新生成的资料页跳转中独立取得 `uid` 和 `room_id`，然后退出资料页/登录提示、恢复直播画面。仅接受同一直播任务中新出现、来源为 live 的资料 Activity，拒绝旧历史条目、昵称代替标识、以及回填待导航目标。

与调度目标匹配且画面就绪后才开录。遇到首页、错误房间或取证失败，先尝试切换入口/重新进入，最多三次、整体有截止时间；确实无法完成时才报告原因。整个过程不要求 Worker 访问外网 API，不执行账号登录、关注、送礼或对外分享。

导航就绪到正式开录之间仍会出现延迟弹窗。采集前、采集启动等待期间（每次检查完成后至少间隔 0.5 秒）、正式登记首片前均执行新的窗口状态检查，单次探针预算 1 秒。登录页、离开直播页、遮挡或读不到可靠窗口状态均不能放行；先收尾临时采集，再重新导航并严格核验身份。每次启动最多三轮准备，每次重新导航仍使用既有导航时限；不额外消耗“5 分钟最多两次”的运行期恢复次数。耗尽以 `startup_gate_exhausted` 失败交给调度器退避，设备离线仍以 20 退出。

被拒绝的准备阶段媒体保留在独立采集目录中，用 `capture_startup` 的 `discarded` 事件记录目录，不登记为正式切片、不计入已录时长，也不伪造完成片或中止片。这里的 discarded 表示不纳入正式录像，**不删除文件**。正式录制后发现登录页的片段仍按既有规则中止；窗口复核不能保证未来不会再弹窗。看门狗在启动后立即首采，随后继续按原间隔检查，不进行高频截图。

这是实际客户端能力适配：目前已验证竖屏 LivePlayActivity 的主播资料入口；其他 App 版本、横屏布局仍需实测。网页 Intent 在当前版本可能不被接受，程序据返回结果改用下一路线，不宣称网页回退一定可用。

严格模式保持默认，不必因为 UI 没有数字 UID 就打开逃逸开关。显式接受无法取得任何可靠房间证据的风险时，原有 `--allow-unconfirmed-identity` 才允许未确认录制；它不放行明确错房，也不把状态伪造为 verified。

重复 `add` 启用目标返回 `existing`，保留自动开关、身份策略、抑制和修正标记；恢复停用目标返回 `restored`，沿用 ID 与历史，采用本次自动录制设置，保留其余人工标记和身份策略。确诊身份不同始终阻断。

在另一个终端通过 HTTP 操作（默认连接本机服务）：

```powershell
python -m src.orchestrator.cli record 'target_id'
python -m src.orchestrator.cli stop 'job_id'
python -m src.orchestrator.cli stop --target-id 'target_id' --session-key '页面当前场次'
python -m src.orchestrator.cli remove 'target_id'
python -m src.orchestrator.cli reconcile 'job_id'
python -m src.orchestrator.cli status --limit 50 --offset 0
python -m src.orchestrator.cli status --command-id 'command_id'
```

控制命令写入持久队列；`pending/running` 仅表示请求已保存或仍在处理，`succeeded` 表示调度意图与命令结果已经原子提交，不代表录像已开始或封口。查看任务 `running`、切片终态及文件才能判断媒体结果。`status` 默认活跃任务，`--history` 查看历史，列表保留分页信息。

变更请求自动生成 UUID 并输出 `request_id`，可用 `--request-id 原编号` 重试同一操作。连接超时后保留原编号及原参数，不自行换编号重复操作；同编号异参数返回 409。主控关闭或重启将尚未应用的命令标为 `interrupted`，不会自动补执行。HTTP 契约见[控制台接口契约](控制台接口契约.md)。

Ctrl+C / Windows Ctrl+Break 会停止本主控拥有的任务并等待切片和事件收尾。强制 kill 仍可能导致媒体损坏，不能用它代替平滑停机。启动即停止时，SDK 先有界等待 Worker 在注册信号处理器后发出的 `worker_started`，再发送中断；创建进程不等于已开始录制，任务收到首个 `segment_started` 后才转为 `running`。

## 任务规则

### 开播状态查询（2026-11-11 起）

调度器通过签名接口 `live.douyin.com/webcast/room/web/enter/` 查询状态，只带游客 `ttwid`（向 `ttwid.bytedance.com` 注册取得），不使用登录 Cookie。请求签名 `a_bogus` 由 F2 的算法生成，来源与许可证见 [vendor/NOTICE.md](../src/mvp/vendor/NOTICE.md)。接口返回空正文时换一个新的 `ttwid` 重试一次。房间 `status` 为 2 表示在播，为 0、4 或业务码 30003 表示已结束，其余情况（包括 3 暂停）记为 UNKNOWN。主播 UID 优先取 `room.owner`，缺失时取外层 `data.user`。

不再抓取直播间网页。2026-11-11 台式机网页返回“验证码中间页”时，签名接口在同一网络下仍正常返回。

### UNKNOWN 与下播
查询失败、HTTP 错误或无法读取可信房间结构时记录 UNKNOWN，保留最后可信状态。默认至少两次明确 ENDED 且时间间隔达到 10 秒才确认下播；结束画面有动画不影响确认。后续调度每轮核对数据库状态，不仅依赖一次性回调。

周期扫描、手动查询和启动复核共用每目标观测序号，以查询发起时间记录观测；较旧、重复、控制版本已变化的结果不更新状态。查询在只读辅助进程中执行，保留 5 个扫描、1 个复核、2 个手动槽位，30 秒总截止，超时后确认对应进程与 IPC 回收才释放槽位；关闭时所有查询共用 5 秒回收预算，与录制收尾并行。

### 排队与启动复核

目标活跃任务唯一，实例活跃分配唯一。没有空闲实例就 FIFO 排队，不抢占已有任务。真正启动前再次查询当前直播场次；已下播或无法确认不启动，使用过期 room_id 的排队任务不会盲目拉起。

### 人工停止

人工停止会抑制同一目标、同一场直播的自动重启。再次显式 `record` 可重新申请，或待确认下播后进入下一场。普通扫描轮询不会立即把用户刚停止的任务拉起。

长期自动开关与本场意图分开保存。关闭自动录制不取消已经排队、录制或等待失败重试的本场；开启开关也不解除人工抑制。按主播停止必须携带当前非空场次，在没有活跃任务的退避期也可取消本场重试；请求执行前已换场则失败，不停止新场。按旧任务 ID 停止终态任务不会影响新任务。移除仅停用监控、取消意图并停止可控任务，历史记录与录像保留。

手动开录先查询当前开播状态，仅 LIVE 才建立意图；下播、UNKNOWN 或超时不会留下预约。已有排队、启动中或录制中任务返回原任务，停止中或待对账返回冲突。自动开关通过 `PATCH /api/targets/{id}` 的 `{auto_record: bool}` 指定目标值。

### 失败处理（2026-11-10 起）

主播在播期间不需要人工 `unblock` 或 `record`，该命令和 `--max-attempts` 参数已删除（[ADR 0015](adr/0015-auto-retry-while-live-without-manual-unblock.md)）。任务失败后按退避重试：间隔从 5 秒起按次翻倍，最长 5 分钟，不限次数；任务收到首个 `segment_started` 后失败计数清零。

| Worker 结果 | 调度处理 |
| --- | --- |
| 人工 `stop` | 本场抑制 |
| 9 目标无效 | 目标 `note` 记为 `needs_fix: 原因`，结束本场意图，不再自动录任何场次；显式 `record` 查询确认 LIVE 后才解除，重复 `add` 不解除 |
| 0 且设置了 `--total-duration` | 正常完成，本场抑制 |
| 15 登录强阻断 | Worker 在退出前尝试关闭抖音，不重开首页；正常回收后实例直接回到 `idle`，任务退避重试；需对账的仍保留占用 |
| 20 设备不可用 | 实例转为 `offline` 并立即触发一次实例状态刷新，确认未开机后按需拉起；任务退避后可分配到其他空闲实例 |
| 10、18、30 及其他 | 退避重试；是否下播只看调度器的两次确认，身份核验不通过照样不开录 |
| 主控正常退出（`scheduler_shutdown`） | 不抑制，重启后照常开录 |

调度器每个扫描周期扫描一次 `MuMuManager` 返回的全部本机实例：新发现实例默认记为“未启用”（`enabled=0`），已存在于数据库中的启用选择在重启与周期扫描中保持保留（仅命令行显式传入可选 `--instances` 预设时，才按该预设覆盖初始启用列表）。在线（Android 已启动）且无任务的实例记为 `idle`，未启动记为 `offline（android_not_started）`；仅 `enabled=1` 且 `idle` 的实例会被派发录制任务。当存在可立即派发的 `pending` 任务且无可用 `idle` 槽位时，调度器按 [ADR 0019](adr/0019-scheduler-on-demand-instance-boot.md) 每次串行最多拉起 `1` 台已启用未开机实例进入 `booting`（期间任务留在 `pending` 且拒绝停用该实例，不自动关机）；开机失败按 30 秒起翻倍至 300 秒封顶冷却并优先轮转其他健康实例，外部手动开机或控制台重新启用即清零冷却。宿主机不再发现的旧实例若无活跃任务或 `needs_reconcile` 占用：未启用时随同步自动清理，仍启用则标为 `offline（not_discovered）` 直至停用清理；正在录制、开机中或待对账中的实例拒绝停用且保留记录。总览 `instance_counts` 与实例条带只计入已启用及 `reconcile` 实例。

持续失败会每隔最多 5 分钟占用一次实例，失败原因见 `status` 中任务的 `error_reason`、`exit_code` 和事件日志。Worker 运行期恢复只受“5 分钟内最多 2 次”的滚动窗口限制，超过时以 30 退出，交给调度器退避。

Worker 取得实例锁且建立 ADB 客户端后，退出时先停止采集与封口，再向该 serial 执行一次 `am force-stop com.ss.android.ugc.aweme`（默认命令超时 4 秒），命令回收后才释放锁；不重开首页、不清数据、不关闭模拟器。关闭失败只记含实例、serial 和完整错误详情的警告，不改变原任务退出码，不阻断实例复用。未拿锁、未连上设备或外部强杀未进入收尾时不执行。下一单照常导航、消解弹窗并严格核验身份，不能把 `idle` 当作关闭抖音成功的证明。见 [ADR 0020](adr/0020-worker-cleanup-force-stop-douyin.md)；实机关闭和冷启动再录仍见 T10。

实例扫描命令失败、超时或返回结构无效时保留原实例记录；只有成功扫描才允许清理失联旧行。显式 `--instances` 会启用指定编号并停用无占用的预设外实例，有占用的保留；同一预设重启不清空已启用实例的开机退避。该预设不是运行期白名单，界面选择仍可动态修改。

开机命令单次硬超时最多 10 秒，完整开机流程默认截止时间为 120 秒。停服会中断重试等待并在后台开机调用结束后释放主控锁；不关闭已启动的模拟器。停服中断记录为 `offline / boot_interrupted`，不增加失败退避，重启后重新探测真实状态。以上修正的隔离验证见[审查修正验证](证据/验证/20261112-实例控制与按需开机审查修正验证.md)。

有切片损失但后续恢复成功的任务可以记录为 `finished_with_warnings`，不是“全部录像完整”。事件冲突、事件流未收齐、最后切片校验失败等不能伪报成功。

### 运行期纠偏与证据覆盖

开录和主动纠偏都会重新核对目标。运行中每约 5 秒只读检查直播 Activity，连续发现离开直播页时先封口并标记受影响片段，再重定位和继续录制；强取证操作不写进正在录制的视频。普通串行切片到期后，距离上次强核验达到配置间隔时再做强复核。恢复与原有故障恢复共用 5 分钟滚动窗口。

事件包含 `room_navigation` 的 navigate / observe / correct_wrong_room / target_ready 等步骤，以及实际观测房间、UID、证据来源和时间。心跳中的 verified 指最近一次可靠核验，不代表每一帧持续验证。仍处于相同 LivePlayActivity 的意外切房可能要等后续强复核才发现。

### 持续采集与切片终态

每个已开始切片对应一个终态。只有任务最后一个成功完成的末段可以带 `is_final=true`；最终段失败时不伪造成功末片。任务完成由进程退出、输出消费完成及切片对账共同决定，不能只看一条 `is_final`。

采集会话通过 Windows 命名管道发送 MKV，ffmpeg 使用 stream copy 按关键帧分装。只有 CSV 完成清单确认封口后才进行异步校验，最多四个待校验片；校验失败报告 aborted，不伪报成功。正常停止先排空采集输出，再封装末片、完成校验和事件交付。断电/强杀下未封口文件保留，不能保证最后一片可播放。

### 重启对账

主控重启时核对 PID、创建时间、命令中的 job_id 和可能的关联录制进程：

- 关联进程已消失：重放 NDJSON 补齐事件，按其中的终止事件（没有则按 30 `interrupted_host_restart`）记录结果，结束时间取该事件的时间（没有则为对账时刻），不抑制本场，按退避续录（新任务、新目录）。
- 进程仍存活且确认属于本任务：任务置为 `stopping`（`error_reason=waiting_old_worker_exit`），槽位保留。旧 Worker 向 stdout 写事件失败时会按停止请求封口退出，事件继续写入 NDJSON；新主控发现进程消失后按上一条续录。120 秒仍未退出转为 `needs_reconcile`（`old_worker_did_not_exit`）。
- 归属无法确认：保持 `needs_reconcile`，槽位不归还，不杀未知进程。可在处理后用 `reconcile job_id` 重新核对。

当前不提供无缝接管旧 Worker stdout 的能力。

## 2026-11-06 持续分段与遮挡恢复

Worker CLI、SDK 和调度 CLI 只使用持续采集，没有 `--recording-mode` 和 `--overlap-duration` 参数。依赖 Windows 命名管道、scrcpy、ffmpeg、ffprobe；缺失依赖明确失败，不静默切回旧方式。配置 `--segment-duration` 是目标切片时长，实际切点由关键帧决定，不保证每片精确等长；源时间轴保持连续，文件内时间戳归零不等于重新采集。

计划切片不会重启 scrcpy。仅故障、目标重新定位或最终停止结束采集会话。

`capture_session` 事件公开每个采集代际的采集/封装 PID，用于核对计划切片是否重启。`segment_started` / `finished` / `aborted` 契约不变；物理切片轮转不重置看门狗健康证据和任务恢复预算。心跳 `file_size_mb` 在连续模式表示该采集会话的累计传输量，不是当前单片大小。

`capture_startup` 记录准备阶段检查/拒绝/退出，包含阶段、尝试次数、实际焦点 Activity、原因、异常详情和诊断目录。启动成功的 `capture_session` 以及被拒绝准备的收尾事件补充 `capture_launch_at`（调用采集进程启动的时刻）、`first_media_observed_at`（首次观察到可见媒体进度的时刻）；正式会话还记录 `surface_verified_at`。这些均是宿主机观测时间，不冒充第一帧的精确拍摄时间；`segment_started` 是正式登记时间，原始媒体可能已经包含启动等待期间的画面。运行期登录采样日志保留实际 Activity、代际与观测时间，便于与 Android 事件和原片对齐。

导航取证不再点击“预计空白”的直播中部坐标。直播面板识别改用窗口管理器状态（2026-11-08 起，不再使用 UIAutomator）：只有挂在 LivePlayActivity 上、非基础窗口、且持有输入焦点的抖音窗口才算遮挡面板（事件中 `overlay_kind=live_panel_window`）。每次按 BACK 前都重新读取焦点，关闭后必须读到焦点回到直播基础窗口才算成功。不会点击关注、充值、礼物发送或右上直播退出 X。运行期每约 10 秒执行一次只读窗口探针（单次约 0.4 秒），发现面板后记录 `overlay_recovery` 及可能受影响的切片质量警告，关闭面板时保持采集进程不变；已录到的遮挡区间原样保留，不能宣称从未出现遮挡。

焦点不明或在系统窗口上时不发送 BACK，也不当作确认无遮挡。画在直播基础窗口内部的浮层不会形成独立窗口，当前无法识别。开录/重新定位时验证真实房间身份，连续分段本身不打开主播资料页；相同 LiveActivity 内换房的及时发现能力仍需专项加强与实测，不能承诺逐帧身份保证。

### 录制期间的冻结检测与切片质量标记（2026-11-09 起）

录制期间（RECORDING 状态）不向模拟器截图，只做前台 Activity 与窗口状态两类 ADB 查询；开录前的导航、身份核验、画面确认以及遮挡恢复期间仍会截图。画面冻结检测改用录像流（[ADR 0013](adr/0013-freeze-detection-from-captured-stream.md)）：字节桥在把 MKV 交给封装进程的同时，非阻塞地复制一份给独立的分析 ffmpeg（灰度 160×288 小图）。分析一路的队列上限约 8 MB，满了只丢分析数据，不影响录像写入。

- 冻结：分析进程 10 秒没有新帧时，先换一个分析进程核实：新进程 5 秒内出帧，算分析进程卡住；仍无帧且录像字节还在流入，才按冻结处理，冻结时间从最后一帧算起。录像文件停止增长也算冻结。冻结按 10/20/45 秒分级重新定位。
- 画面静止（2026-11-10 起）：仍有新帧但画面上中部变化低于 0.003（平台提示页、主播长时间不动）不算冻结。静止满 10 秒给当前切片打 `static_picture` 质量标记（同一段静止每片只标一次）；满 120 秒且仍在直播页时重新定位一次（原因 `static_picture_timeout`），之后仍静止只继续标记，画面恢复变化才重新计时。真正卡在加载动画上的播放器最长约 2 分钟才处理。
- 分析失效：分析进程退出、管道断开或队列溢出时自动重启，连续重启 3 次仍失败则给切片打 `visual_check_unavailable` 质量标记，录制继续，此后只靠文件增长检测判断卡死；之后每 60 秒重试一次，恢复后停止标记。
- 低帧率：60 秒平均帧率低于 12 fps 时打 `low_frame_rate` 质量标记。同一次持续异常对每个切片只标一次；60 秒平均持续不低于 12 fps 满 60 秒才算恢复，之后再低于才重新标记。
- 心跳 `fps` 为最近 10 秒实际帧率；分析没有连续覆盖 10 秒（刚开录、刚重启、不可用）时为空。
- `stream_monitor` 事件记录分析进程的启动、失效、核实结果与恢复（含 `analyzer_pid`），用于排查。
- 调度端把同一切片先后收到的质量标记（遮挡、低帧率、画面静止、画面检查不可用）都保存在 `risk_json` 列表中。
- 录制中设备离线：恢复开始或重建采集失败时用 `adb get-state` 检查，确认离线以 20（`device_offline`）退出。
- 心跳 `segment_elapsed_sec` 为当前切片已录秒数（按录像时间轴），换片后归零。设置 `--total-duration` 时由封装 ffmpeg 在录像时间轴上截止，最后一片恰好在总时长处封口，不再多出尾片。

当前验证边界见 [持续采集与遮挡恢复验证](证据/验证/20261106-持续采集与遮挡恢复验证.md)。持续分段已完成真实 MuMu 测试片验证；完整直播遮挡恢复因实例渲染驱动崩溃尚未验收，不应把自动化测试通过当成实播全部通过。

## 定位等待时限与慢页面（2026-11-06）

Worker 和调度器 `run` 均支持 `--navigation-timeout 300`（默认300秒，60～900秒）；SDK 使用 `WorkerLaunchSpec.navigation_timeout_sec`。它限制一次目标定位流程，不包括模拟器冷启动、工具准备，也不占用 `--total-duration` 的实际录制时长。网络或设备较慢时可显式增大，成功即开录，不会固定等待整个时限。

默认给取证后返回、排除已知遮挡和两次截图预留45秒；各次重试共享总截止时间。单次主动取证不超过60秒；页面未知时先复检，不立即当作错房。确认目标之后只等待当前画面，明确离开页面时才作废证据并重新导航。严格身份规则不变，不能靠延长时间放行明确不匹配。

`room_navigation` 的 `phase`、`elapsed_sec`、`remaining_sec`、`stage_budget_sec` 可区分慢加载、探针不可读、确实错误页面与预算耗尽。停止仍可中断等待；正在执行的单个外部命令有短超时，取消时仅用有限清理时间退出本流程打开的页面。

本次实际验证和未测范围见 [开录预算与慢页面容错验证](证据/验证/20261106-开录预算与慢页面容错验证.md)。
