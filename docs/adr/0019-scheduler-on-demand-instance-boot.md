# 0019 调度器按需自动拉起已启用实例，不自动关机

## Status
accepted（2026-11-12 访谈确定，替代 [ADR 0015](0015-auto-retry-while-live-without-manual-unblock.md) 中“调度器不自动开关模拟器 / 不处理崩溃后开机”条款；已按 [20261112 按需开机方案](../../archive/docs/方案/20261112-调度器按需自动开机实例实施方案.md) 完成实现、隔离回归与 [2026-11-13 台式机 T8 实机验收](../证据/验证/20261113-T8按需开机与T10冷启动再录实机验证.md)）

## Context
在启用 [ADR 0018](0018-console-instance-selection-and-cleanup.md) 后，使用者已可在控制台按需切换参与录播的实例（`enabled`），但调度器派单仍只选择 `status='idle'` 的实例，导致已启用但尚未开机的 MuMu 实例处于 `offline（android_not_started）` 时无法承接开播任务，在无人值守场景下（含冷启动或模拟器崩溃离线后）仍需人工提前开机。

## Decision
1. **按需开机、只开不关**：仅当存在可派发的 `pending` 任务且当前没有已启用 `idle` 槽位时，调度器才按需自动启动已启用且本机未开机（`android_not_started`）的实例；开机就绪进入 `idle` 后不自动关机，后续任务可直接复用热实例。
2. **开机归属调度器与 `booting` 状态**：自动开机由调度器后台独立执行，任务保留在 `pending` 等待实例就绪后再正式认领与核验派发（不消耗任务自身失败次数 `attempts` 或拉长主播重试退避）。实例状态 `booting` 表示“开机中”，期间禁止直接停用。应用清理改由 [ADR 0020](0020-worker-cleanup-force-stop-douyin.md) 规定的 Worker 收尾负责。
3. **并发限制与冷却退避**：单机同时最多拉起 `1` 台实例串行开机，避免多开冷启动抢占宿主机资源及 `MuMuNxMain` 并发启动竞争。单台实例开机失败按逐步加长、最长 `300` 秒（30s → 60s → 120s → 240s → 300s 封顶）的冷却退避，不设永久熔断上限；多台实例并存时优先尝试未在冷却的其他已启用离线实例；人工手动开启或控制台重新启用即清零冷却。
4. **统一开关边界**：只要实例仍处于「已启用」状态，无论是初次未开机、运行崩溃掉线还是被人为关闭后回到未开机状态，有任务需求且冷却结束后均允许再次自动开机；若不希望调度器拉起某台实例，直接在控制台停用即可。

## Considered Options
- **勾选启用即保持常驻开机**：消除开播启动延迟，但无任务期间长期空耗宿主机 CPU/GPU 与内存。
- **空闲超时自动关机**可以节省资源，但可能频繁冷启动模拟器或误关正在手动操作的实例。后续采用了由 Worker 在任务结束时关闭抖音的方案，同一实例下一单冷启动再录已通过台式机验证。[Worker 收尾决定](0020-worker-cleanup-force-stop-douyin.md) · [T10 实机验收](../证据/验证/20261113-T8按需开机与T10冷启动再录实机验证.md)
- **直接把任务派给 Worker 顺便执行 `launch_player`**：改动更少，但会把任务绑定到离线/可能损坏的实例、误记任务失败退避、显示语义混淆为录制启动中，且难以控制串行并发开机。
- **沿用 `offline` 加原因字段而不新增 `booting` 状态**：顶层枚举不变，但总览计数会将正在自动开机的实例计入离线，排障和筛选直观性不如独立 `booting` 状态。
- **连续开机失败 N 次永久停拉需人工重置**：违背无人值守自愈原则，退避封顶 5 分钟已可避免死循环占满资源。

## Consequences
- `GET /api/instances`、`GET /api/overview` 的实例状态集合新增 `booting`；前端总览卡片与实例页标签、筛选及禁用保护需同步支持 `booting`。
- 已删除实例（`not_discovered`）与未启用实例（`enabled=0`）仍绝不会被自动拉起。
- 实施时需同步关注宿主机唤醒与并发重启保护（例如 [待办 K13](../待办.md) 中 `MuMuNxMain` 冷启动与 UU 远程拉起边界）。
