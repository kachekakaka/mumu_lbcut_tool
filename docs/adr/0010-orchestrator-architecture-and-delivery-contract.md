# 0010 调度平台架构、容灾切机与切片上传交付契约

为了实现对多台 MuMu 模拟器和多直播间的高可靠并发编排，调度平台（Orchestrator）采用基于 FastAPI 的内嵌 Web 控制台与 RESTful API 的单进程常驻主控架构。采用 SQLite 持久化任务与切片元数据，并支持通过 YAML 批量导入监控主播；调度策略采用先进先出（FIFO）无抢占排队；容灾机制采取“优先切机漂移，原实例后台 ADB 强杀复位；无空闲则原地自愈”；切片产物不执行本地强制物理删除，而是通过标准 HTTP Webhook 契约对接外部上传服务（如 biliup 上传服务），实现录播控制与视频发布的清晰解耦。

## Context
随着录播 Worker（执行单元）的成熟，系统需要一套工业级的上层调度平台，解决多模拟器并发分配、开播批量巡检、风控阻断自愈、切片交付等实际运营问题。以往单体录屏软件要么缺乏多开协调，要么直接在录制器内部耦合大文件上传逻辑，导致职责过载且极易因网络或鉴权异常阻塞主录制管线。

## Decision Details
1. **形态与交互**：调度平台基于 FastAPI 架构，自带 RESTful HTTP API 与内嵌轻量现代化单页 Web 控制台（单进程统一启动，避免引入 Node.js/Nginx 运维负担），集中提供“模拟器槽位墙、主播监控大厅、录播任务监控、切片与上传记录”四大核心控制面板。
2. **任务与存储管理**：采用本地 SQLite 单文件数据库记录任务生命周期、切片路径与投递状态；支持从本地 YAML 文件批量导入初始重点监控主播。
3. **资源调度**：当并发开播主播数超过当前可用模拟器实例上限时，采用先进先出（FIFO）排队机制，绝不强行中断或拆碎正在进行的在播录制。
4. **容灾与切机漂移**：当 Worker 上报 `LOGIN_BLOCKED`（退出码 15）或异常时，调度器优先检查是否有健康空闲实例：若有，立即将该主播录制秒级漂移至新实例，并将原故障实例置为维护态并在后台通过 ADB 强杀抖音应用（`am force-stop`）复位备用；若无空闲实例，则在原实例原地重启抖音重试。
5. **切片交付契约**：调度平台不负责本地视频文件的物理删除，而是作为上游生产者，通过 HTTP Webhook POST 请求（包含主播名、房间号、切片绝对路径、时长、时间戳等标准 JSON 载荷）向外部上传服务（如 biliup 服务）投递切片，支持“每切片即刻投递”与“整场下播聚合投递”双模，并提供投递失败重试机制。

## Considered Options
- **前后端分离部署**：API 与独立前端工程分离虽灵活，但对单机录播工具而言运维部署成本过高，最终选择 FastAPI 一体化内嵌单页。
- **本地强制删除轮转 vs 外部上传服务对接**：用户明确需要保留录播切片并由外部专用服务（如 biliup）负责 B 站投稿，因此调度平台聚焦于切片元数据投递，不越权执行本地物理删除。
- **故障原地暴力重启 vs 动态切机漂移**：单实例在遭遇抖音设备风控时原地重启往往无法自愈；通过多开实例池动态切换，既能秒级抢救直播内容，又能在后台平滑复位故障实例。
