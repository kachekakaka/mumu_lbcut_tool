# 0015 主播在播期间不限次数自动重试，取消人工解封

## Status
accepted（2026-11-10 讨论确定并在[录制自动恢复与运行期误判修正方案](../../archive/docs/方案/20261110-录制自动恢复与运行期误判修正方案.md)中实施；实机验证见[录制自动恢复台式机实机验证](../证据/验证/20261111-录制自动恢复台式机实机验证.md)）

## Context
调度器原先在多处等待人工介入：登录强阻断（退出码 15）隔离实例，要 `unblock`；设备不可用（20）的实例即使重新上线也一直是离线，同样要 `unblock`；身份核验失败（18）、Worker 自报未开播（10）、主控重启或正常退出都会抑制本场，要手动 `record`；同一场启动失败满 3 次后也停止重试。Worker 内部还有“整场最多恢复 3 次”的上限。无人值守时，一次临时故障就可能让整场直播漏录。

## Decision
主播仍在播时，失败任务按逐步加长、最长 5 分钟的退避自动重试，不设次数上限；只有人工停止、目标移除、调度器确认下播、目标配置错误（退出码 9）会结束对本场的自动录制。登录强阻断后由调度器关闭并冷启动抖音（不清数据、不登录），实例直接回到空闲；离线实例重新在线后自动回到空闲；调度器不自动开关模拟器。身份核验失败同样重试，但严格核验不放宽。Worker 只保留“5 分钟内最多恢复 2 次”的滚动限制，超过即退出交给调度器退避。

## Consequences
- 持续失败的情况（如客户端改版导致每次都定位失败）会每 5 分钟占用一次实例，靠 `status` 和事件日志发现，不再自动停下。
- 删除 `unblock` 命令、实例 `blocked` 状态和 `--max-attempts` 参数。
- 归属无法确认的残留进程仍保留人工对账，不杀未知进程。
- 调度器不处理模拟器崩溃后的开机；需要时另行决定。
