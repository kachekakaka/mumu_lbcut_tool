## 1. 背景与问题陈述 (Context)

在原有实现中，后台 `StallWatchdog` 线程直接跨线程调用 `WorkerPipeline.stop_segment()` 和 `start_segment()` 进行切片自愈，而主控制线程同时保留自己的切片计时与切片索引变量。这造成了严重的并发数据竞争（F-03）：切片文件大小基线重置错乱、切片索引不一致、NDJSON 开始/结束事件乱序以及新旧看门狗线程重叠运行。

## 2. 决策内容 (Decision)

实行**录制管线单写者原则（Single-writer Pipeline Pattern）**：
1. **控制权独占**：录制管线（`WorkerPipeline`）的所有生命周期操作（创建、切片切换、强制终止）以及外部 NDJSON 切片事件的发射，严格由 Worker 主线程单线程串行执行；
2. **纯观察者看门狗与动作队列**：`StallWatchdog` 退化为纯观察者，仅负责周期采样与卡顿研判；当判定需要自愈切片或致命退出时，仅向线程安全的 `queue.Queue` 投递结构化动作请求（如 `ACTION_RECYCLE_SEGMENT`、`ACTION_FATAL_STALL`）；
3. **主线程 Tick 驱动**：主控制循环在每个心跳轮询周期（如 1 秒）优先消费动作队列，顺序完成旧切片封口校验、切片序号递增、新切片启动及代际基线重置，并及时响应 `scrcpy` 进程退出状态（F-02）。

## 3. 权衡与后果 (Consequences)

- **正面影响**：根除了多线程直接操作管线导致的状态撕裂、事件错位与死锁风险；切片编号与事件时序绝对单调递增；保证了新切片基线重置与进程句柄更新的原子性。
- **负面影响与取舍**：看门狗请求的执行延迟取决于主循环 tick 粒度（通常在 1 秒以内），但在录制运维场景下 1 秒内的响应延迟完全可接受且极大提升了确定性。
