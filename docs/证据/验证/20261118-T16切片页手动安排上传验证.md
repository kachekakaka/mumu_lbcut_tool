# T16 切片页手动安排上传验证

2026-11-18，Windows、Python 3.11、Edge 和生产构建的控制台网页。mumu 为基于 `5fb3325` 的本次未提交工作区，Core 为基于 `8994642` 的现有 Bilibili 工作区。使用独立的控制台库、Core 库和 Windows 部署登记，Core API 由实际无窗口宿主启动，上传由独立 Worker 调用 Core 仓库的 Bilibili 协议夹具。录像为合成的两份 MP4，账号和稿件回执为测试数据。

## 浏览器与 Core 联验

| 编号 | 隔离测试记录 |
| --- | --- |
| mumu 安排 | `12cbafd9-da00-4cc4-9bb0-9498d7afd181` |
| Core 作品 | `12f4ea9c-b41f-4335-803c-2857f726731a` |
| Core 任务 | `38f628a7-8e21-4380-b8cd-60b09bfa7d81` |

1. 同目录放入 `000001.mp4` 和 `000002.mp4`。两个标签页从实际切片列表打开第一片的弹窗，打开时 Core 作品列表为空。双击确认后，第二标签页以不同确认编号提交相同内容，两份确认共用一条 mumu 安排。冻结清单与 Core 任务只包含第一片。相邻片保留，目录未生成 `upload.yaml`。
2. 让 Core 成功登记，再在 mumu 侧丢弃登记响应。同一 mumu 进程点击「继续原安排」，登记使用相同的请求 Key 与正文。Core 收到一次提交并创建任务后，注入 mumu 在 SQLite 关联写回前强制退出，退出码为 79。此时可直接从 Core 按作品查到唯一任务，本地安排仍在提交阶段。
3. 将第一片从原文件名移走，重启 mumu。恢复时按原作品查询任务列表，找到唯一匹配后查原任务详情和 Worker 状态。打开原切片详情，页面显示原 mumu 安排编号以及 Core 任务编号，任务仍为「已排队，等待 Worker」。这段恢复通过出站请求日志核对，方法均为 GET，Core 仍只有一项任务。
4. 把合成片放回测试目录原位，启动独立上传 Worker。相同 Core 任务变为 `SUCCEEDED`，切片详情显示夹具回执 `BV1test00001` / `123`。夹具收件目录只有一份结果，整个浏览器场景中向 Core 仅登记两次、提交一次。

本次材料位于仓外临时目录 `20261118-t16-core-verification/run-73f2c4ec/`。其中 `result.json` 汇总三种编号和恢复请求，`mumu-core-attempts.jsonl` 在请求发出前记录方法及路由，`mumu-core-requests.jsonl` 记录已获回包的请求和测试正文。`recovered.png` 与 `succeeded.png` 分别展示重启后恢复的任务以及相同任务的夹具回执。

## 自动化覆盖

定向测试使用真实 SQLite 和可控 Core 回包。核对旧弹窗不能跨部署提交，即使两个部署提供相同账号；超时、协程取消或派发权过期后可以继续，旧回包和旧查询结果不能覆盖后续状态；多页唯一匹配才关联，分页失败或多条匹配时保持待核对；首次明确拒绝可显式修订并使旧弹窗失效，经历超时后收到相同拒绝仍保留原安排。收到旧提交回执中的任务编号后，立即通过 GET 使用当时的最新状态。

Python 全量回归通过 700 项。最后补入分页身份冲突和已关联任务查不到的用例后，T16 定向测试通过 19 项。前端测试通过 44 项，TypeScript 检查、生产构建、Git 空白检查及仓内文档链接检查均通过。
