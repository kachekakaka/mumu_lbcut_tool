## 原因与修复

scrcpy 从 MuMu 取得的 AAC-LC 包写入 MKV SimpleBlock 时没有关键包标记。FFmpeg 6.0 将 AAC 视为帧内编码，解复用时会自动补关键标记；新版取消了这个通用假设，因为 xHE-AAC 存在依赖其他帧的包。对应上游变更为 [40bd6d8](https://github.com/FFmpeg/FFmpeg/commit/40bd6d835575bb8176774be5824ef07b71623d1e)，不是简单的“9.0.2 不支持音频”。

当 stream copy 尚未开始时，分装器默认跳过非关键包；该输入的 AAC 包始终没有关键标记，因此音频全部被跳过，输出仍可能退出 0。原来的媒体校验正确发现缺轨并拒绝成功交付。

`continuous_pipeline.py` 在 `-c copy` 后增加输出选项 `-copyinkf:a`，只允许音频初始非关键包进入输出；视频仍保留关键帧起点和切片规则。音视频继续直接复制，不增加重编码。配置与部署入口统一见[固定媒体工具部署](../../最小调度运行说明.md#固定媒体工具部署)，不在本记录维护另一份路径契约。

## 同源样本对照（真实采集输入的离线重放）

诊断先保存未经重新封装的 scrcpy MKV 字节，再用相同输入隔离版本与参数。该样本含 1264 个 H.264 包和 1062 个 AAC 包。

| 对照 | 结果 |
| --- | --- |
| FFmpeg 6.0，原命令 | 3 个切片都有音视频 |
| FFmpeg 9.0.2，原命令，文件及管道输入 | 视频正常，音频包全部缺失 |
| FFmpeg 9.0.2，加 `-copyinkf:a`，文件及管道输入 | 3 个切片都有音视频；音频包数 473、474、115，共 1062 |
| 修复输出与 6.0 对照 | 提取的各片 ADTS 音频字节完全一致；逐流 DTS 单调；两版本分别完整解码 3 片均通过 |
| 仅给原输入的 1062 个 AAC 包补关键标记 | 9.0.2 原命令恢复全部音频包 |
| 仅清除正常重封装输入的 561 个 AAC 关键标记 | 9.0.2 原命令再次丢音轨 |
| 按原始块节奏重放约 22.6 秒 | 修复后的实际命名管道链路保留双轨 |

这组结果把原因定位到 AAC 包标记与 stream-copy 起始门禁，不是 Android 外放静音、音频编码器不可用或文件/管道差异。解码验证使用 `-fps_mode passthrough -enc_time_base:v demux`；最初将旧版 `-1` 时间基写法用于 9.0.2 的探针报参数错误，修正探针后复测通过，原失败材料保留。
