默认启动脚本最后调用 `app_process`，现场符号链接指向 `app_process64`。`native-after.stdout.txt` 和本次 PID 13760 的 `tombstone-own-dump.stdout.txt` 显示：工具进入 `Shutting down VM` 后，`Shutdown thread` 在 `exit → __cxa_finalize` 的回调过程中触发 SIGSEGV，首帧地址无法归属到有效模块。135 的帮助命令也在相同退出路径发生 SIGBUS。可确认故障位于当前 MuMu Android 15 环境的 **64 位进程退出清理路径**，与 token、主播、XML 路径无关；尚不能确认具体故障库或认定所有 MuMu/Android 15 环境均如此。

[AOSP DumpCommand 源码](https://android.googlesource.com/platform/frameworks/testing/+/refs/heads/main/uiautomator/cmds/uiautomator/src/com/android/commands/uiautomator/DumpCommand.java)显示导出和断开自动化连接之后才打印完成提示，与本次“先生成文件、后退出崩溃”的观察相符；原生崩溃的 logcat/tombstone 解读方法见 [Android 官方说明](https://source.android.com/docs/core/tests/debug/native-crash)。现场镜像实现以实际日志为准，不把上游源码等同于厂商二进制。

32 位路径使用系统已有程序和同一套 Java 工具，没有下载工具或调用模型。三个 dump 结果的节点数量及桌面控件合理；桌面广告有轮播，跨时刻普通 XML 的全部节点属性并非完全一致，未声称逐字一致。32 位路径是已实测的候选修正方式，尚未接入 `scripts/_device.py` 或 `src/worker/popup_bypasser.py`，也未完成接入后的回归；现有 Worker 已有“非零时读取本次有效 XML”的容错，不能据其可用性把原生命令崩溃标为正常。

收尾见 `finish.json`：仅删除本轮三个成功的 32 位设备临时 XML，64 位失败材料保留；实例 2 开机、实例 3 关闭、抖音无 PID、无残留 Worker/scrcpy。UI dump 本身不使用登录 token 或模型 token；若把 XML 交给模型分析，输入和分析过程另计模型 token。
