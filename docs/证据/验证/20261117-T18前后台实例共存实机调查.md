## 结论

1. **后台会话可以实际采集音画。** 本轮冷启动的 MuMu 主程序和实例 0 均位于 Windows 会话 0，安卓就绪、ADB 可用，并完成受控音画录制。
2. **有一条前后台共存的成功路径，但不能概括为任意启动顺序都可靠。** 后台先启动，再在桌面会话直接启动实例 2，两个实例均可连接 ADB；隔离 scrcpy 监听端口并错开启动后，两路同时录制成功。
3. **普通启动命令不能兑现指定会话。** 前台主程序先运行时，后台请求启动的实例仍落入会话 1；后台主程序先运行时，桌面请求启动的实例仍落入会话 0。
4. **直接启动的实例不一定被管理命令正确识别。** 实例 2 在会话 1 中安卓就绪并完成录制，但会话 0、会话 1 调用 `MuMuManager info -v all` 均报告它未启动。不能把直接启动可行当成现有调度器可以直接接入。
5. 本轮的“后台”是**实例运行在非交互会话**。后台实例仍有 `main_wnd`、`render_wnd`，没有证明“只运行安卓引擎、不创建模拟器窗口”。

## 对后续方案的约束

- “运行方式”与 `foreground/bottom/offscreen/hidden` 窗口呈现方式分开，后台不能直接映射成隐藏窗口。
- 启动需要核对实际实例进程、会话、权限和安卓就绪，不能只确认命令返回 0；需要明确主程序已存在时的行为。
- 直接实例入口必须补齐发现、归属、状态查询、关闭及重新接管能力，不能继续仅依赖当前 `info -v all` 判断实例是否运行。
- 混合采集需要补查并发连接与端口分配；本轮重试参数不能直接作为业务代码修复结论。
- 前台先启动再加入后台、不同启动顺序、主程序重启、注销／重启、真实直播长测和异常恢复仍需验证。

以上为调查得出的方案约束，不是已批准实施的新方案；后续实施已暂缓，恢复推进时仍需依据上述未验项评估，不把本轮可行性结果当成功能验收。
