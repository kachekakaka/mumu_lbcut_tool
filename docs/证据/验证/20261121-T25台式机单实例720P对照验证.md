# T25 台式机单实例竖屏 720P 对照验证

2026-11-21，在台式机 `DESKTOP-VPIBHSS` 的 `D:\mumu_test` 目录实测。只使用空闲且未启用调度的 MuMu 实例 2（lb3）。同一直播间在两档设置下均能录出约 63 秒、含声音的竖屏 720P 成片，录制中打开资料卡后都自动关卡并留在原房间。固定片源各录成两次，CPU 和 GPU 的变化方向不一致。首次切到 720P 后有一次采集启动失败。本轮建议保留现有实例设置。

## 环境和对照方法

- 台式机为 Windows 11、GeForce GTX 1660 SUPER、Android 15。受测代码来自这台机器 11 月 20 日实测时部署的 `D:\mumu_test\real-auto-post-20261120-68c91d\mumu_lbcut_tool`，副本未带 Git 元数据。按相对文件名与统一换行后的正文比对，台式机与当前工作区的 `src/worker`（24 个 Python 文件）和 `src/mvp`（12 个）两组 CRC32 均对应相同。直播用该副本的 Worker 入口，固定片源用同一套连续采集管线。录像与逐次日志保存在台式机。
- 原设置为 MuMu 手机预设 `phone.2`，原生 1080×1920、480 DPI。对照档通过 MuMu 设置为原生 720×1280、320 DPI，重启后从 Android 的 `wm size` 和 `wm density` 核对。两档逻辑宽度都是 360 dp，保持同一实例、帧率上限 60 和相同采集参数。实例 0 原已开机，测试继续保留当时的后台负载。
- 资源对照用同一段 720×1280、30 fps 的动态测试图和 550 Hz 声音，两档均在同一相册播放器播放，每次采集约 34 秒。约每两秒取样，表中是各轮第 4 到 31 秒之间的中位数。实例 CPU 以整机逻辑核心总量为分母，内存取该实例进程树的专用字节数。宿主 CPU、宿主已用内存、显卡利用率和显存包含其他进程。
- 实播从已有实测名单选同一在播房间。每档设定录制 63 秒、约 25 秒一片。测试脚本先确认场次号和主播 UID，再点一次左上角头像。识别、关闭资料卡与录制封口均用原程序。两场直播的实际画面与声音随时间变化，资源比较只采用固定片源。

六个正式 MP4 均为 720×1280、H.264 视频及 48 kHz AAC 音轨，逐片完整解码成功。两轮 Worker 都正常退出，第三片均为唯一尾片，未中止切片。两轮都只在前两片报告了本次注入的资料卡遮挡，未报低帧率。

抽看两档首片第 8 秒，1080P 样本是多人连麦画面，720P 样本是单人主画面。两张都能看清画面内容，左上主播名和「关注」文字可辨，未见黑屏或画面被裁掉。直播内容已经变化，无法据此给两档的人脸细节排出优劣。对照抽帧在台式机 `comparison-review.webp`。

720P 还单独验证了完整资料页的备用取证。第一次在直播 Activity 刚出现时尚未读到身份，测试在点击前结束。复测先走 Worker 正常的进房确认，再在测试进程内让快速身份读取返回空结果。程序实际点击头像进入资料页，从新打开的页面读到匹配的主播 UID 和场次号（`fresh_profile_intent`），返回后原房间双标识仍匹配，页面无遮挡。详情在台式机 `profile-720-follow.json`。

录制期遮挡用 Android 的焦点、所属 Activity 及窗口类型来判断，确认仍是可关闭的面板才发返回键。头像备用点击按屏幕宽高比例换算。只有卡片明暗判断的小块取样使用固定的 10 像素半径。两档成片尺寸相同的原因是 scrcpy 把录制长边限制为 1280，FFmpeg 直接封装视频流。[窗口识别](../../../src/worker/live_overlay.py) · [头像定位与取样](../../../src/worker/navigator.py) · [采集参数](../../../src/worker/continuous_pipeline.py)

## 固定片源和资源占用

四轮成功样本各取到 13 个有效采样点。表格按实际录制顺序排列。MiB 为 1024² 字节。

| 安卓分辨率 / 样本目录 | 宿主 CPU | 实例 CPU | 整卡 GPU | 整卡显存（MiB） | 实例专用内存（MiB） | 宿主已用内存（MiB） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1080P · `fixed-1080` | 42.9% | 5.87% | 18% | 4663 | 7221 | 24314 |
| 720P · `fixed-720b` | 48.2% | 6.13% | 20% | 4664 | 7266 | 26306 |
| 1080P · `fixed-1080b` | 45.4% | 5.87% | 21% | 4731 | 7149 | 24254 |
| 720P · `fixed-720c` | 42.0% | 5.70% | 17% | 4653 | 7005 | 24010 |

四轮的每段均能完整解码，实际帧率为 29.89～30.29 fps。固定片源抽帧与原片的中央色带一致，四轮的分列 RGB 平均绝对偏差为 5.5～6.3（按 0～255 计）。该指标只比较大面积色彩。首组的 CPU、GPU 和实例内存小幅上升，第二组方向相反，单实例短测没有量出可重复的资源节省。

## 失败样本和收尾

- 第一次重启后 MuMu 管理器已就绪，测试脚本立即接 ADB 失败。随后恢复原设置，复测改为等待该实例的专属 ADB 端口和 Android 启动完成，再读安卓物理尺寸。
- 在首次确认原生 720P 后，`fixed-720` 的 scrcpy 以 `0xC0000005` 退出，FFmpeg 未读到有效的输入流头，未生成成片。此轮保留为失败样本。同一实例随后的直播录制与两轮固定片源都成功，第二次切到 720P 后的首轮固定片源也成功。单次退出的原因仍未确定，应在考虑批量切换时一并复核。[待办 T25](../../待办.md#t25-竖屏-720p-单实例对照)
- 结束时逐项对照原始 MuMu 参数，已恢复到 `phone.2`、1080×1920、480 DPI。最终查询实例已关机、调度仍禁用、无任务。本次未向上传平台交单。其他面板和多实例长录未纳入本次对照。

## 原始材料

台式机目录为 `D:\mumu_test\t25-720p-20261121-d0dcd7b9`。两场短录各在 `live-1080`、`live-720`，其中 `result.json` 与 `media.json` 对应每个已封口 MP4，`events.ndjson` 记录 Worker 事件，`observations.ndjson` 和同目录截图记录注入前、打开和返回后的页面。`fixed-*` 保留各轮原始采样、解码日志与抽帧；`original-settings.json`、`guest-720.json`、`guest-1080b.json`、`restored.json` 可核对安卓实际尺寸与恢复状态。
