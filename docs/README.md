## 文档职责与入口

| 位置 | 唯一正文职责 | 创建时机 |
| --- | --- | --- |
| [docs/需求说明.md](需求说明.md) | 已确认的目标、行为、边界和验收要求；明确标记尚未实现的部分 | 需求需要持久维护时 |
| `docs/设计说明.md` | 当前架构、模块职责、数据与接口约束，以及代码和测试入口 | 技术设计确定后 |
| [docs/待办.md](待办.md) | 未完工作、已知缺陷、未验证事项及对应依据 | 出现需跨任务跟踪的事项时 |
| [CONTEXT.md](../CONTEXT.md) | 已有领域词汇表：易混概念及业务术语，不重复实现参数；不另建重复术语正文 | 已有，按概念变化维护 |
| [docs/方案/](方案/) | 待审阅、待实施、实施中、待验证或暂停的专项方案 | 用户要求或同意编写方案时 |
| `docs/证据/验证/YYYYMMDD-任务名称.md` | 需要长期保留的验证摘要、环境、结果、未测项与外部材料位置 | 形成有留存价值的验证结论时 |
| [docs/adr/](adr/) | 仍有效的重大取舍、原因和影响 | 存在值得长期解释的设计决定时 |
| `tests/README.md` | 已建立的测试入口、场景、隔离方法及结果判定方式 | 测试体系建立后 |
| `archive/docs/方案/` | 已退出活动管理的方案 | 满足下文归档条件时 |
| `archive/docs/adr/` | 已失效或被替代的设计决定 | 决定失效或被替代时 |

方案描述本次改动如何实施，不能长期代替现行需求或设计；证据记录实际发生的结果，不能把计划当成结果。证据摘要注明日期、受测版本或代码状态、环境、验证范围、结果及未测项；没有提交号时如实记录，不以日期或文件名冒充版本依据。合成验证与真实环境验证分别标注。

详细日志、截图及大文件使用根 README 约定的仓外临时目录。仓内证据只保留必要摘要及材料位置，并避免私人数据和凭证；需要保留的证据材料在清理前先确定保留去向，不能因目录名为 tmp 就自动删除。

后续续作优先查看已有待办和相关设计入口，按任务读取。新想法和未确认需求进入待办，不直接描述为已实现功能；已有缺陷也不能改写为正确需求。完成事项在现行文档和证据中承接后移出待办，未解决或未验证事项继续保留。

## 方案创建与交付

1. 仅在用户要求或同意编写方案时创建专项方案；普通小改动不强制新增方案。
2. 方案放入 `docs/方案/`，使用创建日期命名：`YYYYMMDD-任务名称.md`。同一任务持续修订原文件，记录最后更新日期，不按每次修改另建副本；同名文件已存在于活动或归档目录时增加序号，避免归档覆盖。
3. 方案至少写明：背景与目标、范围与非目标、实施路径和主要取舍、涉及文件或模块、步骤与依赖、验收标准、风险与待确认事项。
4. 文件开头标注创建日期、最后更新日期及当前状态：草案、待确认、待实施、实施中、待验证或暂停。获准实施后记录授权范围和实际日期；实施授权及方案交付后的操作边界统一遵循 [AGENTS.md](../AGENTS.md#实施与验证)。
5. 已授权实施时，在方案中记录必要状态和结果引用；现行行为、设计和剩余工作分别同步到对应文档，避免在方案里长期维护第二份项目事实。

## 方案归档时间与位置

方案退出活动管理后，移动到仓库根目录下的 `archive/docs/方案/`，保留原文件名，不在活动目录留下内容相同的副本。归档有以下类型，必须明确区分：

| 归档类型 | 何时可以归档 | 归档前应记录 |
| --- | --- | --- |
| 完成 | 约定范围已实施，约定的必要验证已完成且满足验收标准 | 实际完成日期、结果摘要和验证依据 |
| 被替代 | 新方案已明确承接原方案，替代关系已经确认 | 替代原因、新方案链接及已做／未做部分 |
| 取消 | 用户明确取消该项工作 | 取消日期、原因、已产生改动及遗留影响 |
| 余项转交 | 用户确认结束本专项，未完事项已有明确去向 | 已完成范围、未完／未测事项及对应待办或后续方案链接 |

仅暂停的方案保留在 `docs/方案/`，标明暂停原因和恢复条件。有未完成的必要验证时保持“待验证”，不能以“完成”归档。被替代、取消或余项转交归档只表示退出活动管理，不表示功能已验收。

完成判定以本专项的约定范围为准：纯文档专项完成其内容及导航检查后，可以完成归档，不必等待范围外的产品验收；但文档归档不能关闭尚未完成的产品验证。仅写出或通过实施方案，也不等于方案所规划的代码工作已经完成。

归档依次完成以下步骤：

1. 将最终适用的需求、设计、验证结论及剩余工作同步到各自正文；不关闭尚未解决的问题。
2. 在方案开头补充归档日期、归档类型、最终状态、结果依据及后续去向；没有对应事项时明确注明不适用。
3. 查找指向原路径的引用，确认目标不存在同名文件后移动；若存在冲突，保留两份原件并核对来源，不覆盖。修正方案内部相对链接和其他文档的反向引用，更新现行导航。
4. 检查文件位置、链接和事实一致性；只有完成这些收尾后才宣称归档完成。归档过程中是否继续执行遵循 AGENTS.md 的方案交付边界。

归档正文原则上冻结，仅修复必要链接或追加带日期的更正说明，不改写历史版本、失败和未测事实。重新开展已归档任务时，新建活动方案并链接历史方案，历史材料保留原状态。

## ADR 生命周期

ADR 的有效性与方案是否完成分开判断：仍适用的决定留在 `docs/adr/`；失效或被替代后移到 `archive/docs/adr/`，注明日期、原因及替代依据。新编号按活动与归档两处的最大编号递增，两处都为空时从 `0001` 开始，不复用旧编号。

仅部分失效时，不把仍有效的约束一并归档；先在现行文档或后续决定中明确承接有效部分。移动前后按方案归档相同的要求检查同名冲突和链接。

## 文档维护与检查

- 移动、重命名或删除文档前先查反向引用，操作后检查修改文件及引用来源；归档目录属于长期文档，应进入 Git。
- 链接可访问与内容符合实际分别判断。外部证据暂不可访问时标记无法核验，不把它当成验证通过，也不直接断言材料已删除。
- 当前未建立专用自动文档检查命令，按改动范围检查内容、相对链接和 Git 差异。未跟踪文件不会出现在普通 `git diff` 中，需要单独检查其完整内容；后续确立工具后再补充真实可用的命令。
